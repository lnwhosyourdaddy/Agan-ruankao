第 39 小时 · 微服务系统分析与设计 · 组件、事务与反模式

第 20 章微服务是案例分析的六大方向之一（综合知识 0 题，但案例常考）。
CAP/BASE 与分布式事务是本章必考点，也是面试与论文的高频话题。
本学时覆盖 20.1 微服务 vs 单体 + 20.2 九原则六模式（DDD 限界上下文）+ 20.3 组件通信与分布式事务 + 20.4 测试与反模式。

考情定位

四块必拿：① CAP 三选二（C 一致性 · A 可用性 · P 分区容错，实践必保 P，只剩 CP 或 AP）；② 分布式事务四方案（2PC 强一致但阻塞 / TCC 业务侵入 / Saga 补偿 / 可靠消息）；③ DDD 限界上下文（微服务拆分依据，同术语在不同上下文含义不同）；④ 分布式单体反模式（拆了但仍耦合，比单体更糟）。

记忆口诀

CAP：一致性 C ｜ 可用性 A ｜ 分区容错 P —— 最多取二，实践必保 P。
BASE：基本可用 + 软状态 + 最终一致（对 C 的弱化）。
分布式事务：2PC（强一致·阻塞·单点）｜ TCC（Try/Confirm/Cancel，业务侵入）｜ Saga（本地+补偿，长流程）｜ 可靠消息（吞吐高）。
微服务组件：注册中心（Nacos/Eureka）· 配置中心（Nacos/Apollo）· 网关（Gateway/Zuul）· 熔断限流（Sentinel/Hystrix）· 链路追踪（Sleuth/Zipkin）· 消息（MQ）· 服务网格（Istio）。
反模式：分布式单体（共享数据库 + 共享代码 + 一起部署 = 最糟）。

易错陷阱

BASE 是"最终一致"不是"强一致" —— 看到"BASE 保证数据任何时刻完全一致"直接排除。
2PC 不是"没有缺点" —— 它强一致但同步阻塞 + 协调者单点，别只说优点。
微服务不是"拆得越多越好" —— 过度拆分会导致调用链爆炸、运维成本飙升；判断标准是限界上下文边界，不是代码行数。
"拆分后用分布式事务"是最后手段 —— 优先考虑服务聚合，把强一致部分收敛在一个服务内。

论文可用句

在服务拆分上，我以 DDD 限界上下文为唯一依据而非按技术层拆分——通过领域分析识别出 12 个限界上下文，每个上下文对应一个微服务并独占数据库，彻底避免了"分布式单体"。跨服务的强一致需求（如下单扣减库存）采用 Saga 模式编排：以 TCC 方式对资源做"预留—确认—释放"，最终一致，收单成功率 99.97%；同时按 CAP 权衡选择了 CP 型的一致性方案，保证资金相关操作零差错，库存扣减允许最终一致并由对账任务兜底。

第 20 章知识骨架

20.1 微服务 vs 单体 + 七特征 ⭐

⚔️微服务 vs 单体（优缺点对照）

单体

✅ 部署简单、测试容易、初期快
❌ 耦合高 · 扩展只能整体扩 · 技术栈锁死 · 故障影响大

微服务

✅ 独立部署/扩展 · 技术异构 · 故障隔离 · 团队自治
❌ 分布式复杂度（网络/一致性/运维）· 调试难 · 测试复杂 · 需配套基础设施

定义：将单一应用拆分为一组小服务，每个服务独立进程，通过轻量级通信（HTTP/REST 或 RPC）协作，可独立开发、部署、扩展

📜七特征 + 拆分方法 ⭐

教材七特征：服务自治性 · 单一职责 · 松耦合 · 分布式部署 · 技术异构性 · 弹性和可伸缩性 · 独立演化和部署

拆分方法 ⭐

DDD 限界上下文（最推荐）· 按业务能力 · 按子域；避免按技术层拆（会造成分布式单体）
粒度原则：能独立变更与部署 · 避免频繁跨服务调用；康威定律 = 组织结构决定系统架构

💡 九大特征（冲刺口径）补充：轻量通信 · 去中心化治理 · 去中心化数据管理 · 基础设施自动化 · 容错设计（熔断降级） · 演进式设计 · 围绕业务能力构建。

20.2 九大设计原则 + 六种设计模式 ⭐⭐

📜九大设计原则

① 单一职责 ② 隔离性 ③ 自治性 ④ 弹性 ⑤ 可观察性 ⑥ 可测试性 ⑦ 可维护性 ⑧ 安全性 ⑨ 智能端点与简单消息传递****（端点内重逻辑、端点间轻通信——Unix 哲学）

🧩六种微服务设计模式（教材 20.2.2）

① 聚合器微服务

调用多个服务聚合结果返回（组合查询）

② 代理微服务

不加工直接转发（含安全/路由）——近网关

③ 链式微服务

请求沿链依次处理，响应单一代（耦合高慎用）

④ 分支微服务

按条件分支调用不同服务链（动态路由）

⑤ 数据共享微服务

多服务共享数据库（反模式倾向——过渡态）

⑥ 异步消息微服务

用消息队列通信——解耦削峰、最终一致（最推荐）

💡 记法：聚合/代理/链/分支/共享/异步——组合方式从"紧"到"松"，异步最微服务化。

20.3 核心组件全家桶 + 通信 ⭐⭐⭐

🧰七大组件（给场景认组件）

职责组件
注册发现Nacos / Eureka / Consul
API 网关Spring Cloud Gateway / APISIX（统一入口·鉴权·限流·路由）
配置中心Nacos / Apollo
服务调用OpenFeign / Dubbo / gRPC
熔断限流Sentinel / Hystrix / Resilience4j
链路追踪SkyWalking / Zipkin
消息队列Kafka / RabbitMQ / RocketMQ（异步解耦·最终一致）
服务网格Istio（Sidecar，治理下沉基础设施）

💡 编排链路：Docker 打包 → K8s 编排（Pod/Service/Deployment/HPA 弹性伸缩）→ Istio 服务网格。

📡通信选型 + 数据管理

同步 vs 异步

同步（REST/gRPC）= 强一致/实时
异步（MQ）= 可容忍延迟/削峰解耦

数据管理

每个服务独立数据库（Database per Service）· 避免共享库；跨服务查询 = API 组合 / CQRS 读写分离 / 事件溯源

⚡ 案例锚：问"数据怎么管"——答独立库 + API 组合/CQRS；问"怎么解耦削峰"——答 MQ 异步 + 最终一致。

CAP/BASE + 分布式事务 ⭐⭐⭐（必考）

⚖️CAP 与 BASE

CAP 定理

一致性 C · 可用性 A · 分区容错 P——三选二；分布式系统 P 必选，实际选 CP 或 AP

BASE 理论

Basically Available（基本可用）· Soft state（软状态）· Eventually consistent（最终一致）——AP 的工程化延伸

⭐ 微服务推荐最终一致（BASE）而非强一致——判断题

🔁分布式事务方案（辨识）

2PC 两阶段提交

强一致；性能差、同步阻塞——少用

TCC

Try-Confirm-Cancel 三段业务实现；业务侵入大；一致性较好

Saga

长事务拆分 + 逐段补偿；适合长流程

本地消息表 / MQ 最终一致

微服务最常用——消息表保证本地事务与发消息原子

💡 幂等性 ⭐：重试必须保证多次执行结果一致——用唯一请求号 / 去重表 / 乐观锁（MQ 消费、接口重试的必备）。

20.4 测试 + 反模式 ⭐⭐（易考）

🧪微服务测试策略

测试层次：单元测试 → 集成/契约测试 → 组件测试 → 端到端测试

⚡ 难点 = 服务间依赖 → 解法 = Mock/测试替身 + 契约测试（消费者驱动契约 CDC，Spring Cloud Contract）；端到端成本高 → 优先契约测试

原理：把"服务间接口约定"固化为契约，双方各自按契约验证——解耦测试

💡 运维监控 = 可观测性三支柱（EFK 日志 / Prometheus+Grafana 指标 / SkyWalking 链路）+ 健康检查 + CI/CD·GitOps——呼应 CH15。

🚫反模式（易考简答）

五大反模式

① 分布式单体（拆了但强耦合同步调用——最常见）· ② 共享数据库 · ③ 过度拆分（纳米服务）· ④ 无自动化就上微服务· ⑤ 忽视分布式事务与幂等

对策：按 DDD 拆 + 异步化 + 每服务独立库 + 先建 CI/CD 与可观测性再拆

教材组件：Docker 容器化 + K8s 编排是微服务标配；Istio 服务网格把治理下沉（流量管理/灰度/熔断/可观测）

⚡ 案例锚：问"拆分后为什么更乱"——答分布式单体（按技术层拆 + 同步强耦合）；解法 = 按业务能力重拆 + 异步消息。

章节练习题

章节练习题 已答 0 / 6
1关于 CAP 理论，下列说法正确的是：
A分布式系统最多只能同时满足 C（一致性）、A（可用性）、P（分区容错性）三者中的两个；P 通常必保
BCAP 三者可以同时满足
C三者中 P 最不重要
D三者中 C 最重要
CAP：Consistency（一致性，所有节点同时看到同一份数据）｜Availability（可用性，请求总能得到非错误响应）｜Partition tolerance（分区容错性，网络分区时系统仍能工作）。关键结论：三者不可兼得，最多取二。⚠️ 实践共识：分布式系统"必须保 P"（否则网络分区时系统直接不可用）→ 所以实际只有 CP（放弃 A，如 ZooKeeper、etcd、Redis Cluster 强一致） 或 AP（放弃 C，如 Cassandra、最终一致） 两种选择。这正是"不要被 99.9% 的可用性宣传误导"的原因。
第20章 · 20.3 CAP/BASE
2关于分布式事务的解决方案，下列说法错误的是：
A2PC 是强一致方案，优点是数据不会不一致，缺点是同步阻塞且存在协调者单点问题
BTCC 需要业务实现 Try/Confirm/Cancel 三个接口，属于业务侵入型方案
CSaga 适合长流程业务，通过"本地事务 + 补偿事务"实现最终一致
DBASE 是强一致性方案，保证任何时刻数据都完全一致
分布式事务四类方案对比：① 2PC（两阶段提交）——强一致；准备阶段所有节点投票，都同意才提交；缺点：同步阻塞（节点在此期间不能做其他事）+ 协调者（主事务）单点；3PC 加了预提交降低阻塞但仍同步。② TCC——业务侵入，要实现 Try（预留资源）/ Confirm（确认）/ Cancel（释放） 三接口，可控性最强、性能最好，但开发量大。③ Saga——把长事务拆成多个本地事务 + 补偿事务，无同步阻塞，适合长流程（订单、审批），最终一致。④ 可靠消息最终一致（本地消息表/事务消息）——适合对吞吐要求高的场景。BASE 明确是"最终一致"而非强一致（所以 D 错）。
第20章 · 20.3 分布式事务
3微服务架构中最常见的"反模式"是：
A分布式单体——服务拆分但仍强耦合（共享数据库、共享代码、部署在一起），失去微服务意义
B服务粒度过小
C使用了 API Gateway
D采用了 CI/CD
分布式单体（Distributed Monolith）是最典型的微服务反模式：表面上拆成了多个服务，实际上耦合依旧——共享同一个数据库（每个服务都可读写全表）｜共享代码库（底层 jar/包被多个服务依赖）｜必须一起部署（改一个服务要重新部署全部）。结果：既失去了微服务的独立开发/独立部署/独立伸缩优势，又额外承担了分布式系统的复杂度（网络、分布式事务、最终一致），比单体更糟。⚠️ 根治方向：每个服务独占数据库（Database per Service）+ 限界上下文（DDD）正确划分边界。
第20章 · 20.4 反模式
4DDD（领域驱动设计）中的"限界上下文（Bounded Context）"指的是：
A一个领域模型的边界，同一术语在不同上下文中可以有不同含义，是微服务拆分的依据
B系统最外层的接口层
C数据库的并发控制机制
D代码的命名规范
限界上下文（Bounded Context，DDD 核心概念）：一个领域模型的明确边界。核心洞察：同一个业务术语在不同上下文里含义可能不同——例如"商品"在"销售上下文"指可售卖的商品，在"物流上下文"指实际的物理包裹，在"售后上下文"指退换货对象。限界上下文就是微服务拆分的边界依据：一个限界上下文 ≈ 一个微服务（对应一个数据库），上下文之间通过明确的契约（API/事件）交互。⚠️ "按技术层拆分"（所有 Controller 一个服务）是典型的错误拆分。

A服务注册中心（如 Eureka / Nacos），服务实例启动后注册、调用方按服务名动态发现可用实例
B硬编码 IP 地址
C共享内存的静态表
DDNS 静态解析
服务发现是微服务的核心能力（对应"可发现性"特征）：服务实例启动时向注册中心注册（IP、端口、元数据），调用方按服务名从注册中心获取可用实例列表并负载均衡调用；实例下线时注销/心跳失效。代表组件：Eureka（Netflix，AP）、Nacos（阿里，同时支持注册中心 + 配置中心，国内主流）、Consul（HashiCorp）、etcd（K8s 生态）。⚠️ 与 K8s Service 的区别：K8s 用 Service + DNS 做服务发现（依赖其内部的 etcd），不额外引入注册中心。
第20章 · 20.3 核心组件全家桶
6微服务拆分后，原单体中的一次跨模块事务（如"下单扣库存 + 生成订单"）应如何处理：
A通过 Saga / TCC / 可靠消息等最终一致性方案处理，接受短暂不一致
B直接在本地用数据库事务解决
C放弃事务不做处理
D用分布式锁串行化所有请求
这是微服务转型最核心的技术难题：服务拆分后原本的本地事务被拆到不同服务、不同数据库中，不能再用本地事务保证。三条解决路线：① 尽量避免——通过服务聚合/编排把强一致的部分收敛到一个服务边界内（推荐优先）；② 补偿型——Saga（本地事务 + 补偿事务）、TCC（Try/Confirm/Cancel），实现最终一致；③ 消息型——可靠消息最终一致（本地消息表 / RocketMQ 事务消息），适合对吞吐敏感的场景。核心原则：先问"能不能不改成分布式事务"，再考虑怎么改。
