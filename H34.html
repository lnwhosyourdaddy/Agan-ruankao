至此第二篇「关键技术」15 章全部收官。

考情定位

四块必拿：① 转换三策略（直接=风险高成本最低 / 并行=风险最低成本最高 / 分段=最常用）；② ETL 三步（抽取 → 转换清洗 → 装载，转换最易出错）；③ 高可用（消除单点 + 自动故障转移，不是堆硬件）；④ 可观测性三支柱（Metrics + Logs + Traces）。

记忆口诀

转换三策略：直接（一刀切，风险高成本低）｜并行（双跑，风险低成本高）｜分段（分批，最常用）。
ETL：E 抽取 → T 转换清洗（最耗时易错）→ L 装载；迁移必做比对校验 + 备份 + 回滚预案。
高可用：消单点 + 自动切流 + 快速恢复（限流/降级/熔断/回滚）——不是堆服务器。
可观测三支柱：Metrics（指标告警）· Logs（日志定位）· Traces（链路追踪找瓶颈）。

易错陷阱

并行转换风险最低但成本最高（两套系统双份人力），直接转换反之。
"堆硬件冗余"不等于高可用——有单点或 MTTR 过长，再多服务器也到不了 99.99%。
监控 ≠ 可观测性：监控是"看护已知问题"，可观测性是"探索未知问题的能力"。

论文可用句

在系统切换上，考虑到该系统承载全省 200 万用户的实时交易，我否掉了直接转换（风险不可接受），也未采用全量并行转换（两套系统并行 3 个月的人力成本超出预算），最终选择分段转换：先按业务域将查询类功能（只读、无写风险）切换至新系统，运行两周无异常后，再按地市批次逐步切换交易类功能，每批切换后保留 72 小时观察窗并保留快速回切开关。数据迁移采用 ETL 方式，重点投入在转换清洗环节（统一了 17 类历史脏数据的编码映射），并完成三轮试迁移与全量比对校验，最终切换期间业务零中断、数据零丢失。

第 15 章知识骨架

15.7 新旧系统转换 · 三策略 + 数据迁移 ⭐

🔀三种转换策略

① 直接转换

旧停新立即上，无过渡；人力费用最省；适用新系统不复杂/旧系统完全不能用；风险最大——转换前必须详细严格测试 + 应急措施

② 并行转换 ★最常用

新旧并行一段时间（2~3 个月到 1 年），旧系统结果作校核；风险小、可比较性能、人员得到培训；缺点 = 人力费用消耗大、周期长、难控制新旧数据变化

③ 分段转换

直接 + 并行结合，分期分批；大系统适用、平稳费用不高；按功能/部门/机器设备分阶段；缺点 = 周期过长、需求变化影响新系统稳定、需开发新旧系统接口

💡 转换前准备：数据准备 · 文档准备 · 人员培训 · 设备安装 · 系统试运行（输入真实数据比对输出）。

📦数据转换和迁移（原则：数据不丢失）

  • 三方法：① 切换前工具迁移（ETL 抽取转换装载——最主要最快捷；一次迁移风险低强度大、分次迁移解决数据量大与宕机时间短的矛盾但需同步）· ② 切换前手工录入（期初数据无历史来源时；耗人力出错率高）· ③ 切换后新系统生成（按已迁原始数据生成结果数据，减少迁移量）
  • 三阶段：迁移前准备（7 项：数据源说明/数据字典/差异分析/表映射/ETL 工具/测试计划/应急措施）→ 转换与迁移（ETL = 抽取 → 转换（含清洗）→ 装载）→ 迁移后校验
  • 清洗：清二义性/重复/不完整/违反业务逻辑规则的垃圾数据（抽取前清洗为主）；校验 = 质量分析（完整性/一致性/总分平衡/记录条数/特殊样本）+ 新旧系统查询对比

15.8 系统演进 + 冲刺补充（高可用/可观测性）⭐

🧗系统扩展 vs 系统集成

可扩展性 = 添加新功能的能力；动态可扩展（运行中加功能不影响其他部分）/静态可扩展（须停机重启）；提高方法 = 架构中减少构件间耦合

扩展 = 深度维护——重点在设计阶段（研究扩展点附近环境、细致回归测试）；延伸型扩展/新建型扩展
集成 = 广度维护——重点在分析阶段（业务关联点、避免过度耦合）；需高层协调、重接口与全流程测试

回归测试不能"改头测头，改脚测脚"——要全面回归

🔭冲刺补充 · 2026 论文新方向落点

可观测性三支柱

Logging 日志（发生了什么；EFK/ELK）· Metrics 指标（聚合数值；Prometheus+Grafana）· Tracing 链路追踪（请求走了哪些环节；SkyWalking/Jaeger）——口诀"日志·指标·链路"；MTTR 的核心是快速定位，靠可观测性

监控四层 + 高可用手段

基础设施 → 中间件 → 应用 → 用户体验（APM/首屏）；告警分级 P0~P3
高可用 = 冗余（主备/双活/多活）· 心跳检测 · 熔断（断路器三态：闭合/打开/半开）· 降级 · 限流 · 弹性伸缩 · 灰度发布

容灾与备份

RPO = 容忍丢多少数据（决定备份频率）· RTO = 容忍停多久（决定恢复速度）；灾备等级 = 本地 → 同城 → 异地 → 两地三中心；备份 = 全量/增量/差异

DevOps / DevSecOps / 信创

DevOps = 开发运维一体化（CI/CD/IaC/GitOps/容器化）；DevSecOps = 安全左移；ITIL 五管理 = 事件/问题/变更/配置/发布
信创迁移四层 = 芯片（鲲鹏/海光/飞腾）→ OS（麒麟/统信）→ 数据库（达梦/人大金仓）→ 中间件（东方通）；迁移六步 = 评估→设计→迁移→双轨→灰度→回滚预案

全章易错辨析 TOP 10

1MTTF vs MTBF：MTBF = MTTF + MTTR（间隔含修复时间）

2可用度 A = MTBF/(MTBF+MTTR)；几个 9 换算 99.9%≈8.76h/年

3MTTA = 告警触发到确认的时间（响应能力），不是修复时间

4故障管理五活动：监视（基础，大多数故障在此发现）→调查→排查恢复→收尾（+预防）

5维护四类占比：完善性 ~50% 最大；预防性 = "今天方法学用于昨天系统满足明天需要"

6可维护性度量：外部 = MTTR；内部 = McCabe 环路数（复杂性间接度量）

7遗留系统四策略：高高改造｜低高继承（并行切换）｜高低集成（封装孤岛）｜低低淘汰

8转换三策略：直接最省风险最大｜并行最常用（校核旧系统）｜分段按功能/部门/设备

9RPO vs RTO：RPO = 丢多少数据；RTO = 停多久

10扩展 vs 集成：深度维护重点在设计 vs 广度维护重点在分析（需高层协调）

💡 补充三陷阱：MTBF 不含计划内维护停机 · 数据迁移原则 = 数据不丢失（三方法 ETL/手工/生成） · DevSecOps = 安全左移。

全章速记卡 · 考前 5 分钟

🧮公式卡（必背）

  • MTBF = MTTF + MTTR（间隔 = 无故障 + 修复）
  • 可用度 A = MTBF / (MTBF + MTTR)
  • MTTR = 修复总时间 ÷ 维修次数（例：120min/6 = 20min）
  • MTBF = 总运行时间 ÷ 故障数（例：1000h/2 = 500h）
  • MTTF = 正常运行总时间 ÷ 故障数（不可修复件寿命）
  • MTTA = 告警到确认总时间 ÷ 事件数（响应能力）
  • 几个 9：99%≈87.6h｜99.9%≈8.76h｜99.99%≈52.6min｜99.999%≈5.26min/年
  • 失效率 R(t) = e^(−λt)，MTTF = 1/λ
  • 遗留系统技术水平：OR =（P₁ORH+P₂ORS+P₃OAF+P₄ORA）/4

🔢数字卡

  • 运维占生命周期 60%~80%；50% 维护工作量花在理解软件上
  • 认证 4 方式：用户名密码/IC 卡/动态密码/USB Key（强双因子）
  • 网络管理 5 功能：性能/故障/配置/计费/安全
  • 故障管理 5 活动：监视/调查/排查恢复/收尾（+预防）；原因 7 类
  • 数据库故障 3 类：事务/系统/介质（副本+日志恢复）
  • 维护性 6 子特性；维护 4 类占比：20/25/50/5%（完善性最大）
  • 评价 3 方面：性能/效益/建设；权重 3 法：主观/客观/组合
  • 遗留系统 4 象限 4 策略：淘汰/继承/改造/集成
  • 转换 3 策略：直接/并行（最常用）/分段；迁移 3 方法；ETL = 抽取转换装载
  • 高可用 7 手段；断路器 3 态；可观测 3 支柱；监控 4 层；信创 4 层

🔗场景对应卡

  • "修 bug" → 改正性；"换新 OS/数据库" → 适应性；"加新功能" → 完善性；"提高未来可维护性" → 预防性
  • "告警到确认" → MTTA；"两次故障之间" → MTBF；"不可修复件寿命" → MTTF
  • "技术落后但业务离不开" → 继承（并行切换）
  • "局部良好但信息孤岛" → 集成（封装）
  • "大系统平稳切换" → 分段转换；"新旧并行校核" → 并行转换
  • "期初数据无历史来源" → 手工录入；"减少迁移量" → 切换后生成
  • "容忍丢多少数据" → RPO；"容忍停多久" → RTO
  • "请求走了哪些环节" → Tracing；"聚合数值" → Metrics；"发生了什么" → Logging
  • "断路器三态" → 闭合/打开/半开；"两地三中心" = 生产+同城+异地

⚖️对比卡

  • MTTF（不可修复件） vs MTBF（可修复系统间隔） vs MTTR（修复） vs MTTA（应答）
  • 改正性（修 bug） vs 适应性（换环境） vs 完善性（加功能最大） vs 预防性（防未来）
  • 直接转换（最省最险） vs 并行（最常用费人） vs 分段（平稳周期长）
  • 一次迁移（风险低强度大） vs 分次迁移（解决量大宕机短、需同步）
  • RPO（数据丢失容忍） vs RTO（时间容忍）
  • 全量/增量/差异备份
  • 扩展（深度/设计/回归测试） vs 集成（广度/分析/高层协调）
  • 动态可扩展（不停机） vs 静态可扩展（停机重启）
  • DevOps（CI/CD 自动化） vs DevSecOps（安全左移）
  • 经济效益（直接） vs 社会效益（间接难评）

本章最核心三句话：① A = MTBF/(MTBF+MTTR)，MTBF = MTTF + MTTR，MTTA 只管告警到确认　② 维护四类完善性占比最大 ~50%，预防性 = 今天方法学用于昨天系统满足明天需要　③ 遗留系统四象限：高高改造、低高继承、高低集成、低低淘汰

C分段转换（分模块逐步切换）
D三者风险相同
三种转换策略：① 直接转换（一刀切）——某时刻直接停用旧系统启用新系统；成本最低、最简单，但风险最高（一旦新系统出问题没有退路）；适用于小系统或低风险场景。② 并行转换——新旧系统并行运行一段时间（数周至数月），比对结果一致后再停用旧系统；风险最低（有旧系统兜底），但成本最高（两套系统同时维护、双倍人力）。③ 分段转换（渐进式）——按模块/按区域/按用户分批切换；风险与成本居中，是大型系统最常用的方式。
第15章 · 15.7 新旧系统转换 · 三策略
2新旧系统转换中的数据迁移，"ETL" 三个字母分别代表：
A抽取（Extract）→ 转换（Transform）→ 装载（Load）
B加密 → 传输 → 加载
C导出 → 测试 → 上线
D评估 → 测试 → 上线
ETL = Extract（抽取）→ Transform（转换/清洗）→ Load（装载）：① 抽取——从旧系统/多种数据源读取原始数据；② 转换——清洗、去重、格式统一、编码映射、业务规则换算（这是数据迁移中最耗时、最容易出错的环节）；③ 装载——写入新系统。数据迁移关键步骤：数据盘点 → 字段映射 → 清洗转换 → 试迁移 + 比对校验 → 正式迁移 → 回滚预案。⚠️ 必做：迁移前后的数据核对（总量、关键字段、抽样比对），以及保留旧数据备份。
第15章 · 15.7 数据迁移
3关于"高可用"设计，下列说法错误的是：
A高可用就是堆硬件冗余，只要服务器足够多就一定能达到 99.99%
B高可用需要消除单点故障（SPOF），并结合冗余、故障转移与健康检查
C可用度通常用"9"的个数衡量（如 3 个 9 = 99.9%）
D缩短 MTTR 与延长 MTBF 都能提高可用度
高可用（HA）的核心公式仍然是 A = MTBF/(MTBF+MTTR)，所以只有两条路：延长无故障时间（MTBF） + 缩短修复时间（MTTR）。关键手段：① 消除单点故障 SPOF——任何组件都要有冗余（多实例、多机房、多活）；② 故障自动转移（健康检查 + 自动切流）；③ 快速恢复机制（限流、降级、熔断、回滚）；④ 容量与演练。⚠️ "堆硬件"只能解决部分冗余问题：如果架构存在单点（如单点数据库写、单点网关）、或 MTTR 很长（无自动化恢复），再多服务器也达不到 99.99%。
第15章 · 15.8 冲刺补充 · 高可用
4关于"可观测性"（Observability）三大支柱，正确的是：
A指标（Metrics）+ 日志（Logs）+ 链路追踪（Traces）
BCPU + 内存 + 磁盘
C监控 + 告警 + 值班
D日志 + 告警 + 报表
可观测性三大支柱：① Metrics 指标——聚合的数值型时间序列（QPS、响应时间、错误率、资源使用率），适合告警与趋势分析；② Logs 日志——离散的事件记录（带上下文的请求日志、错误堆栈），适合定位具体个案；③ Traces 链路追踪——一次请求在分布式系统中流经各服务的完整路径（TraceId / SpanId），适合定位跨服务的性能瓶颈与故障点。⚠️ 与"监控"的区别：监控是"已知问题的看护"（预先定义指标与阈值），可观测性是"未知问题的探索能力"（能在没预想到的故障中快速找到根因）。
第15章 · 15.8 冲刺补充 · 可观测性
5系统演进（System Evolution）的驱动因素通常不包括：
A开发团队的人员离职
B业务需求变化
C技术平台升级
D性能与容量瓶颈
系统演进的驱动因素（为什么系统要变）：① 业务需求变化（新功能、新渠道、新合规要求）｜② 技术平台升级（框架/中间件/数据库版本迭代、信创替代）｜③ 性能与容量瓶颈（用户量增长导致现有架构撑不住）｜④ 技术债累积（可维护性下降，改不动了）｜⑤ 安全与合规要求。⚠️ "团队人员离职"属于项目管理/人力资源范畴，不是系统演进的技术驱动因素（虽然它可能间接导致技术债，但不是演进的直接原因）。
第15章 · 15.8 系统演进
6某系统年可用度目标为 99.9%（三个 9），一年按 365 天计，允许的年停机时间约为：
A约 8.76 小时
B约 52.6 分钟
C约 5.26 分钟
D约 87.6 小时
可用度与允许停机时间的换算（一年 365 天 = 8760 小时）：99%（两个 9） → 允许停机 1% × 8760 = 87.6 小时/年；99.9%（三个 9） → 0.1% × 8760 = 8.76 小时/年；99.99%（四个 9） → 0.01% × 8760 = 0.876 小时 ≈ 52.6 分钟/年；99.999%（五个 9） → ≈ 5.26 分钟/年。⚠️ 记忆锚点：每多一个 9，允许停机时间缩小 10 倍。这是运维题最常见的换算。
