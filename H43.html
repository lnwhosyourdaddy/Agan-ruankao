二、四大高频方向的"必备采分点清单"

① 系统分析与建模（40.9%，绝对第一）

采分点清单（背下来就能踩满）

DFD 四要素：外部实体 · 加工 · 数据流 · 数据存储（画图题必判符号是否正确）
DFD 三铁律（纠错题直接按这三条逐条查）：

  • 父子图平衡 —— 子图的输入/输出数据流数量与名称必须与父图中对应加工一致
  • 加工必须有输入也有输出 —— 只有输入没输出叫"黑洞"，只有输出没输入叫"奇迹"
  • 数据流必须起于或止于加工 —— ⚠️ 外部实体之间、数据存储之间都不能直接连数据流（这是纠错题最高频的答案）

数据守恒：输出能追溯到输入；不凭空产生（奇迹）、不无端丢弃（黑洞）
用例图要素：参与者（Actor）· 用例（Use Case）· 关联关系（包含 include / 扩展 extend / 泛化）
状态图要素：状态 · 转换 · 事件 · 动作
活动图要素：活动 · 判定（分支）· 泳道（责任划分）
需求获取方法：访谈 · 问卷 · 观察 · 文档/资料审阅 · 联合开发（原型法）

② Web / 分布式架构（25%）

采分点清单

REST 五原则（必背）：无状态 · 统一接口 · 可缓存 · 分离关注点 · 最小化协议
缓存三兄弟（2023.11 与高频仿真反复考）：

  • 穿透（查不存在）→ 布隆过滤器 + 缓存空值（短 TTL）
  • 击穿（热点过期）→ 互斥锁单飞 / 逻辑过期异步刷新
  • 雪崩（集体过期）→ TTL 加随机抖动 + 多级缓存

缓存更新策略：

  • Write-Through（同步写库）—— 一致性强、写延迟高 → 适合一致性要求高的场景（订单/资金）
  • Write-Behind（异步批量写库）—— 吞吐极高、可能丢数据 → 适合可容忍丢失的场景（埋点/日志）

CAP：一致性 C · 可用性 A · 分区容错 P，最多取二，实践必保 P
分布式事务：2PC（强一致·阻塞·单点）· TCC（业务侵入）· Saga（补偿）· 可靠消息

③ 面向对象（18.2%）

采分点清单

OOD 三类设计类：边界类（Boundary/界面-外部交互）· 控制类（Control/编排调度）· 实体类（Entity/业务数据）
四种关系：关联 · 依赖 · 泛化（继承）· 实现；关联又分聚合与组合（⚠️ 组合是"整体消亡则部分消亡"）
耦合七级（低→高）：非直接 · 数据 · 标记 · 控制 · 外部 · 公共 · 内容（最坏）
内聚七级（高→低）：功能（最好） · 顺序 · 通信 · 过程 · 时间 · 逻辑 · 偶然（最坏）
设计原则：SOLID（单一职责 / 开闭 / 里氏替换 / 接口隔离 / 依赖倒置）

④ 数据库（18.2%）

采分点清单

范式链（高→低）：1NF → 2NF（拆部分依赖）→ 3NF（拆传递依赖）→ BCNF（所有属性完全依赖）→ 4NF
视图的作用：① 简化复杂查询 ② 提供数据独立性（屏蔽基表变化）③ 提供安全保密（只开放部分行/列）
索引的代价：⚠️ 索引提升查询速度但降低写入（INSERT/UPDATE/DELETE）速度，还占存储空间 → 不是越多越好
分区 vs 分表：分区是单表内的逻辑拆分（同一张表内）；分表是拆成多张物理表
NoSQL 选型：键值（Redis）· 文档（MongoDB）· 列族（HBase）· 图（Neo4j）

三、真题精讲（三道代表性真题逐题拆解）

精讲 ① 2021.5 案例 3 · 微服务数据一致性（2PC 的致命局限）

题目（节选）

某电商平台采用微服务架构，订单服务用 NoSQL，客户服务与支付服务用关系数据库。
李工建议用 2PC 解决订单与支付的数据一致性。
问题 1：用 200 字以内说明 2PC；说明 2PC 是否能解决该问题，并解释原因。

采分点拆解：

小问采分点（答案里必须有的）
① 什么是 2PC两类节点（协调者 + 事务参与者）· 两个阶段（请求/准备 + 提交）· 参与者投票（同意/取消）· 协调者据全体反馈决定提交或中止
② 能否解决不能
③ 为什么⚠️ "大多数 NoSQL 数据库并不支持事务，也就不支持 2PC" —— 题干明确说订单服务用 NoSQL

⚠️ 这道题的真正考点不是"2PC 是什么"，而是"能否用"：

答案的关键转折是题干里的"订单服务使用了 NoSQL 数据库"。
如果考生只背了 2PC 的定义与流程，会顺着题干写"2PC 能解决"——这正是出题人设的陷阱。
命题人把"能不能用"的判断依据（异构存储引擎）藏在了材料里。

关联知识：H39 微服务 · H20 信息安全（二） · H35 Web 架构

同类陷阱识别法：题干出现 "用了 X 技术" + 问 "能否用 Y 方案" → 一定要先检查 X 与 Y 的兼容性/前提条件是否成立。

精讲 ③ 高频仿真 · 电商平台高性能缓存（Web 类的"三兄弟"处置）

题目（节选）

某电商平台"双十二"期间出现 数据库 CPU 过高、缓存击穿、缓存穿透。
优化方案包括：Redis 集群读写分离、哨兵模式、布隆过滤器、Write-Through 策略。
问题 1：与 Memcached 相比，Redis 的两个主要优势是什么？为什么布隆过滤器能有效防止缓存穿透？
问题 2：对比 Write-Through 与 Write-Behind（原理、优劣），并说明本题选择 Write-Through 的原因。
问题 3：针对热点商品大量失效导致的数据库压力，提出两种解决方案并说明优缺点。

采分点拆解：

小问采分点
① Redis 优势数据类型丰富（String/List/Set/Hash/ZSet 等，Memcached 只有 String）· 支持持久化（RDB 快照 + AOF 日志，防丢数据）
① 布隆过滤器多个哈希函数映射到位数组 · 判"不存在"则一定不存在（无假阴）· 判"存在"则可能存在（有假阳）· 能提前拦截必不存在的 ID，止于缓存层不入库
② Write-Through原理：写缓存时同步写数据库 ｜ 优：一致性强 ｜ 缺：写延迟高
② Write-Behind原理：只写缓存，异步批量写数据库 ｜ 优：吞吐量极高 ｜ 缺：可能丢数据
② 选 W-T 的原因⚠️ 电商订单/商品数据对一致性要求极高，不能容忍缓存与库不一致
③ 方案 1互斥锁（Mutex） ｜ 优：实现简单、防止大量请求回源 ｜ 缺：高并发下线程阻塞排队
③ 方案 2逻辑过期 + 异步刷新 ｜ 优：抗高并发强、无阻塞 ｜ 缺：实现复杂、存在短暂旧数据

⚠️ 这道题的三个"陷阱"：

  1. 问"两个优势"就必须写两个（数据类型 + 持久化），只写一个按半分算
  2. "为什么选 W-T"必须结合业务说（一致性要求高）—— 只讲 W-T 的优点不结合题干业务，是本题最大失分点
  3. ③ 问"两种方案"就必须两种，且每个都要说优缺点（只给方案不给缺点 = 只拿一半分）

关联知识：H35 Web 应用系统分析与设计 · H09 数据库系统（一）

第43小时 · 精讲 ① 2PC 的致命局限
2DFD 纠错题中，最常见的错误类型是：
A外部实体与数据存储（或外部实体之间、数据存储之间）直接连数据流
B数据流没有方向
C加工只有输入没有输出
D数据存储用了矩形而不是开口矩形
DFD 三铁律是纠错题的检查清单：① 父子图平衡；② 加工必须有输入也有输出（只有输入无输出 = 黑洞）；③ 数据流必须起于或止于加工。⚠️ 最高频的错误是第三条违反：外部实体之间、数据存储之间都不能直接连数据流（2024.5 案例 2 的第一类错误正是"数据存储→外部实体"有数据流）。答题技巧：答案要"分类 + 指出图中具体位置"两段式（只写规则不指出位置，阅卷人难判采分点），且答案条数要与题干问的"几类"严格对齐。

5布隆过滤器（Bloom Filter）能有效防止缓存穿透的关键原理是：
A通过多个哈希函数映射到位数组；判断"不存在"时一定不存在（无假阴性），可提前拦截必不存在的请求
B它把所有数据都缓存在了内存中
C它能自动删除不存在的 key
D它通过加锁保证缓存与数据库一致
布隆过滤器解决"缓存穿透"的关键是它的"无假阴性"特性：多个哈希函数把元素映射到位数组的多个位上，全部置 1。查询时若所有位均为 0，则该元素一定不存在（因为不存在任何元素能在这些位上都置 1）→ 请求在布隆过滤器处就被拦下，根本不进入缓存与数据库。⚠️ 代价是存在"假阳性"（不存在却被判存在），但这对穿透防护无影响（只是多查一次缓存）。它与缓存三兄弟的对应关系：穿透→布隆过滤器/空值缓存；击穿→互斥锁/逻辑过期；雪崩→TTL 随机抖动/多级缓存。

6关于索引的代价，下列说法正确的是：
A索引提升查询速度，但会降低 INSERT/UPDATE/DELETE 的写入速度并占用存储空间，因此不是越多越好
B索引只影响查询速度，对写入无影响
C索引越多性能一定越好
D索引会自动随数据量增长而最优
索引是典型的"空间换时间"：它用额外的存储与写入时的维护开销（每次 INSERT/UPDATE 都要同步更新索引）换取查询的加速。因此：① 每个索引都会拖慢写入；② 索引占用存储；③ 低区分度的列（如性别、状态）建索引几乎无效（选择性低 → 优化器可能直接全表扫描）；④ 索引不是越多越好，要按高频查询条件选择性建。这是数据库类案例的常见辨析点。
