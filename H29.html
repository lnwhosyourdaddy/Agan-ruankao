第 29 小时 · 系统设计（一）· 结构化设计与面向对象设计

第 13 章真题占比 3.8%（21/557）。本学时覆盖 **13.1 概述 + 13.2 流程设计
+ 13.3 结构化设计 SD + 13.4 面向对象设计**。
耦合七级 / 内聚七级的排序是本章乃至全书最经典的排序题，务必一字不差背下来。

考情定位

四块必拿：① 耦合七级排序（非直接 → 数据 → 标记 → 控制 → 外部 → 公共 → 内容，越低越好）；② 内聚七级排序（功能 → 顺序 → 通信 → 过程 → 时间 → 逻辑 → 偶然，越高越好）；③ 高内聚低耦合总原则（方向相反，别记成"都高"）；④ SOLID 五大原则（尤其开闭与依赖倒置）。

记忆口诀

耦合七级（低→高 = 好→坏）：非直接 · 数据 · 标记 · 控制 · 外部 · 公共 · 内容。
内聚七级（高→低 = 好→坏）：功能 · 顺序 · 通信 · 过程 · 时间 · 逻辑 · 偶然。
总原则：内聚要高，耦合要低（方向相反！）。
SOLID：S 单一职责 ｜ O 开闭（扩展开放、修改关闭）｜ L 里氏替换 ｜ I 接口隔离 ｜ D 依赖倒置（都依赖抽象）。

易错陷阱

顺序内聚 vs 过程内聚：顺序有数据流（前一输出=后一输入），过程只有执行次序。
内容耦合是最坏的耦合（直接访问对方内部），功能内聚是最好的内聚。
依赖倒置 = 高层不依赖低层，二者都依赖抽象——不是"高层依赖低层"（那是传统分层）。

论文可用句

在详细设计阶段，我以高内聚、低耦合为验收标准组织模块：对外暴露的接口只传必要的数据参数（数据耦合），禁止跨模块直接读写对方内部状态（杜绝内容耦合）；模块内部按单一职责划分，目标达到功能内聚。对于规则频繁变化的折扣计算，采用策略模式将算法族封装为可互换的策略对象，新增促销类型时只需增加一个策略类（对扩展开放、对修改关闭），上线以来未修改过任何既有折扣代码。

第 13 章知识骨架

13.1 系统设计概述 · 两阶段与七项内容

🏗️概要设计 vs 详细设计

概要设计（总体结构设计）

把功能需求分配给软件模块，确定模块功能与调用关系 → 形成系统结构图 SC（模块结构图）

详细设计

为每个具体任务选择技术手段和处理方法——模块内部算法与数据结构

💡 定位：系统分析 = "做什么"；系统设计 = "怎么做"（物理设计阶段，系统实施的铺垫）。

🗂️详细设计七项内容

网络设计（选结构/布线/节点权限）· 代码设计（唯一化/规范化/系统化；分类 = 线分类法（最常用）/面分类法；编码 = 顺序码/数字码/字符码/混合码）

输入/输出设计（完整性正确性一致性）· 处理流程设计（模块内部执行过程）

数据存储设计（统筹安排 + 文件数据结构；概念→逻辑→物理）

用户界面设计（黄金三原则）· 安全性和可靠性设计（运行环境控制 + 数据处理控制）

💡 代码设计原则：唯一性 · 合理性 · 可扩展性 · 简单性 · 适用性 · 规范性 · 系统性；有标准代码先遵循标准。

13.2 处理流程设计 · 流程与工作流

🌊流程六要素 + 定义/实例

业务流程（ISO 9000）= 一组将输入转化为输出的相互关联的活动

⭐ 六要素：输入资源 · 活动 · 活动的相互作用（结构）· 输出结果 · 用户 · 价值

流程定义 = 业务过程的形式化表示（活动、切换规则、任务等）；流程实例（工作） = 流程定义的运行实例（一次具体的流程操作）

工作流（WFMC）= 能完全或部分自动执行的业务过程，按过程规则在不同执行者之间传递和执行

🧩活动 · 所有者 · 工作项

活动

流程定义的基本要素；有输入、处理、输出；可由人完成也可系统自动触发

活动的所有者

有权决定该活动是否结束的参与者（如审批的主管）；推动流程前进或退回

流程的所有者

有权整体控制流程实例执行的参与者——通常是流程发起人

工作项

流程实例中活动的参与者将要执行的工作（如一张课程申请单）；有编号可定位

工作流管理系统 WFMS · 六模块五接口 ⭐

⚙️三大基本功能

① 工作流建模——定义工作流（人和计算机都能"理解"）

② 工作流执行——遵循模型创建和执行实际工作流（多工作项）

③ 业务过程的管理和分析——监控进度/数据状态/工作分配与均衡

💡 例：考勤 + 信息交流 + 日报周报集成 = OA 系统就是一类 WFMS。

🏛️工作流参考模型 WRM：六模块 + 五接口

  • 六模块：① 工作流执行服务（核心，可含多个引擎）② 工作流引擎（为流程实例提供运行环境并解释执行）· ③ 流程定义工具（图形化定义流程）· ④ 客户端应用（用户操作界面，客户端调用执行服务）· ⑤ 被调用应用（执行服务调用，如文档处理程序）· ⑥ 管理监控工具（状态查询/挂起/恢复/销毁）
  • 五接口：① 工作流定义交换（定义工具↔执行服务）② 客户端应用接口 ③ 调用应用接口 ④ WFMS 互操作接口 ⑤ 系统管理和监控接口

⚡ 辨析：客户端应用是客户端调服务；被调用应用是服务调它——方向相反！

流程设计工具 · 图形/表格/语言三分类

🧰七种工具

📐图形工具（5 种）

  • 程序流程图 PFD：直观易学；缺点 = 符号不规范、箭头随意转移控制（违背结构化）→ 只能用 5 种基本控制结构组合嵌套
  • IPO 图（IBM）：描述每个模块的输入、处理、输出；主体 = 处理过程说明；配合数据字典
  • N-S 盒图：没有箭头、不能随意转移；作用域明确、结构化特征强烈；缺点 = 问题复杂时图很大
  • PAD 问题分析图（日立）：自上而下、自左向右执行；引导使用结构化方法，可机械变换成程序
  • 判定树：树形表达逻辑判断——左根加工名、中条件、右行动，比表格直观

📋表格 + 语言工具

  • 判定表（表格工具）：四部分 = 左上条件说明 / 左下行动说明 / 右上条件组合（T/F/空白）/ 右下对应动作（Y/空白）

—— 右半部分每一列 = 一条规则；适合多条件多结果的紧凑表达（教材折扣策略例）

  • PDL 过程设计语言（语言工具）：又称结构化语言/伪代码——自然语言词汇 + 结构化程序语法；外层语法描述结构（IF-THEN-ELSE/WHILE-DO）、内层语法用自然语句描述操作

—— 不可执行；可逐步求精；不必考虑语法错误

💡 辨析：条件少而直观用判定树；条件多而组合复杂用判定表；算法细节精确交流用 PDL。

13.3 结构化设计 SD · 模块化三原则 ⭐

🧱SD 思想与模块属性

  • SD：面向数据流的设计——以 SRS + DFD + 数据字典为基础；自顶向下、逐步求精、模块化
  • 模块三基本属性：功能（做什么）· 逻辑（内部怎么做）· 状态（使用环境与条件）；描述时先定外部特性（模块名/参数表/影响），再定内部特性（代码与内部数据）
  • 信息隐蔽：封装实现细节成"黑盒"；抽象：抽取本质特性——过程抽象/数据抽象/控制抽象

📏模块划分三原则

① 大小适中

过大分解不充分、过小调用频繁——实现代码 1~2 页 / 50~200 行易维护

② 扇入扇出合理

扇出 = 直接调用的下级模块数（过大 → 加中间层）；扇入 = 调用它的上级数（大 = 复用度高）；理想结构 = 顶层扇出大、中间扇出少、底层扇入大；平均 3~4，不超过 7

③ 深度宽度适当

深度 = 层数（过多 → 合并简单模块）；宽度 = 同层模块最大数（越大越复杂，受扇出影响最大）

耦合七级（模块之间 · 越低越好）⭐⭐⭐

🔗从低到高 · 理想 = 数据耦合，最差 = 内容耦合

① 非直接耦合

无直接关系，靠主模块控制调用

② 数据耦合 ★理想

借参数表传递简单数据（基本类型）

③ 标记耦合

传递记录信息（数据结构）——整个结构都传过去

④ 控制耦合

传递控制信息（开关量），影响对方内部逻辑

⑤ 外部耦合

访问同一全局简单变量（非数据结构、不经参数）

⑥ 公共耦合

访问同一公共数据环境（全局数据结构/共享通信区/公共覆盖区）

⑦ 内容耦合 ★最差

直接访问对方内部数据 / 不经正常入口进入 / 代码重叠 / 多入口

⚡ 排序口诀：非数标控外公内——考试给场景判级别："传参数基本类型" = 数据；"传整个结构体" = 标记；"传开关" = 控制；"goto 进别人内部" = 内容。

内聚七级（模块内部 · 越高越好）⭐⭐⭐

🧲从高到低 · 理想 = 功能内聚，最差 = 偶然内聚

① 功能内聚 ★理想

只完成一个单一功能，各部分协同缺一不可

② 顺序内聚

处理元素相关且必须顺序执行——前一部分输出 = 后一部分输入

③ 通信内聚

所有处理元素集中在同一数据结构区域上

④ 过程内聚

处理元素相关，按特定次序执行

⑤ 瞬时（时间）内聚

任务须在同一时间间隔内执行（如初始化模块）

⑥ 逻辑内聚

完成逻辑上相关的一组任务（如"各类输出"放一起）

⑦ 偶然（巧合）内聚 ★最差

完成毫无关系或松散关系的任务

⚡ 排序口诀（从高到低）：功顺通过瞬逻偶；从低到高倒过来背。内聚越高 → 通常耦合越低（但不是绝对）——设计目标 = 高内聚、低耦合。

💡 场景判级："初始化一堆变量" = 时间；"按固定次序干几件事但无数据传递" = 过程；"同一份数据反复加工" = 通信；"前一步输出喂后一步" = 顺序。

系统结构图 SC · 四种模块 + 三种类型

🗺️SC 组成与四种模块

  • SC 组成 4 部分：模块（矩形，已定义模块用双纵边矩形）· 调用关系（箭头 = 调用方指向被调用方）· 通信（短箭头表传递方向与内容）· 辅助控制符号（菱形 = 条件调用、弧形箭头 = 循环调用）
  • 四种模块：传入（从下属取数据传给上级）· 传出（从上级取数据传给下属）· 变换/加工（上级取数 → 加工 → 送回上级；大多数计算模块）· 协调（协调管理所有下属，应在较高层出现）

SC 中不能再分解的底层模块 = 原子模块；全部加工都由原子模块完成 = 完全因子分解（最好的系统）

🔀三种 SC 类型

变换型 SC（变换流）

信息沿输入通道 → 变换中心（主加工） → 输出通道；结构分输入、变换、输出三大部分；物理输入→逻辑输入→变换→逻辑输出→物理输出

事务型 SC（事务流）

信息到达事务中心，按事务类型在若干活动流中选一个执行；三层 = 事务层 · 操作层 · 细节层；活动流呈辐射状，可共享操作/细节模块

混合型 SC

大系统 DFD 常为两者混合——变换分析为主、事务分析为辅，对不同部分分别映射

💡 判型口诀：一条主干加工 = 变换型；按类型分叉多路 = 事务型。

13.4 面向对象设计 OOD · 三类设计类

🧬OOD 基本思想

OOD 是 OOA 的延续；基本思想 = 抽象 · 封装 · 可扩展性（可扩展性靠继承与多态实现）

任务：设计软件类 → 对象持久化与数据库映射 → 定义接口 → 设计交互

类职责分解为属性（封装数据） + 方法（封装行为）；设计类是 OOD 中最重要、最复杂最耗时的部分

🎭三种设计类（同 OOA 三类对象）

实体类

映射需求中的实体，保存需永久存储的信息；业务领域术语命名（名词）；一定有属性，不一定有操作

控制类

控制用例工作；由动宾结构转化（"身份验证"→"身份验证器"）；用例执行时产生、执行完毕消亡；通常没有属性，一定有方法

边界类

位于系统与外界交接处（窗体/报表/打印机/协议/传感器）；每个参与者与用例交互至少一个边界类；既有属性也有方法；报表可作边界类

⚡ 记忆锚：实体 = 属性必有；控制 = 方法必有；边界 = 都有。

对象持久化与 ORM

💾持久化与阻抗失配

对象只能存在内存中 → 永久保存需持久化（保存到数据库/永久存储设备）

  • 持久层：专注数据持久化的逻辑层——实现业务逻辑与数据逻辑的解耦、降低耦合
  • 为什么要 ORM：对象有关联和继承；关系数据库是二维表，无法直接表达多对多关联和继承 → 需要对象/关系映射 ORM（重要且烦琐耗时）

用缓存降低访问数据库频率（保证缓存与数据库同步）

🧰四大持久化技术框架

CMP 容器管理持久化

由 EJB 容器管理实体 EJB 持久化；ORM 管 POJO；CMP 遵守复杂 J2EE 规范、只能跑在 EJB 容器、移植性差

Hibernate

ORM 解决方案；功能全面（重量级）

iBatis

Java 对象到 SQL 的映射；手动写 SQL；小巧、上手快——不需要复杂功能时最灵活简单

JDO

SUN 制定的对象持久化标准 API；透明存储；可在任何数据底层运行（关系库/文件/XML/对象库）——比 JDBC 更通用

SOLID 五大设计原则 ⭐⭐（必考辨识）

📜面向复用的原则 · 提高可维护性与可复用性

S 单一职责 SRP

一个类只有一条引起它变化的原因

O 开闭 OCP

对扩展开放、对修改关闭；通过添加抽象层（接口/抽象类）实现——其他原则的基础

L 里氏替换 LSP

用基类对象的地方一定适用于子类，行为无变化；反过来不成立

I 接口隔离 ISP

用多个专门接口，不用单一总接口；每接口承担相对独立的角色

D 依赖倒置 DIP

抽象不依赖细节，细节依赖抽象——针对接口编程；开闭原则的主要机制（Spring/COM/CORBA 背后原则）

⚡ 关系链：开闭是目标（基础），依赖倒置是主要机制；里氏替换保证继承可替换；单一职责和接口隔离管"小而专"。

💡 其他原则：组合/聚合复用（优先组合少继承：Has-A 用组合、Is-A 用继承；继承 = 白盒复用破坏封装、组合 = 黑盒复用）· 迪米特/最少知识（少相互作用；松耦合类、降访问权限、不变类、最少引用四注意）· DRY · KISS · YAGNI

耦合七级（从低到高 = 从好到坏）：① 非直接耦合（两模块无直接关系，靠上级模块调用，最理想）→ ② 数据耦合（传简单数据参数）→ ③ 标记耦合（传整个数据结构/记录）→ ④ 控制耦合（传控制标志，决定对方内部逻辑）→ ⑤ 外部耦合（共享同一个外部环境，如全局变量/文件）→ ⑥ 公共耦合（共享同一公共数据区）→ ⑦ 内容耦合（直接访问对方内部数据或代码，最坏）。设计目标：尽量用数据耦合，少用控制/公共耦合，杜绝内容耦合。
第13章 · 13.3 耦合七级
2模块内聚的七个级别中，内聚度最高（最理想）的是：
A功能内聚
B顺序内聚
C时间内聚
D偶然内聚
内聚七级（从高到低 = 从好到坏）：① 功能内聚（模块内所有成分共同完成一个功能，最理想）→ ② 顺序内聚（前一成分的输出是后一成分的输入）→ ③ 通信内聚（各成分操作同一数据集）→ ④ 过程内聚（按特定顺序执行，但无数据传递）→ ⑤ 时间内聚（同一时间执行，如初始化模块）→ ⑥ 逻辑内聚（若干逻辑相似的功能放一起，靠参数选）→ ⑦ 偶然内聚（成分间无联系，纯偶然拼凑，最坏）。⚠️ 易混：顺序 vs 过程——顺序有数据流，过程只有执行次序。
第13章 · 13.3 内聚七级
3关于耦合与内聚的设计原则，正确的是：
A追求高内聚、低耦合
B追求低内聚、高耦合
C内聚与耦合越高越好
D内聚与耦合越低越好
模块设计的总原则：高内聚、低耦合（这是软件工程最经典的口号之一）。高内聚 = 模块内部各成分围绕单一职责紧密协作（理想是功能内聚）；低耦合 = 模块之间依赖尽可能少且简单（理想是非直接/数据耦合）。⚠️ 两者方向相反：内聚要高，耦合要低，别记成"都高"或"都低"。
第13章 · 13.3 模块化三原则
4SOLID 原则中，"开闭原则"（OCP）的含义是：
A对扩展开放、对修改关闭（新需求靠新增代码实现，不改已有代码）
B对所有情况都开放
C只对内部开放
D软件应当完全封闭
SOLID 五大原则：S 单一职责（SRP，一个类只有一个引起它变化的原因）｜O 开闭（OCP，对扩展开放、对修改关闭，靠抽象与多态实现）｜L 里氏替换（LSP，子类必须能替换父类且不破坏程序正确性）｜I 接口隔离（ISP，客户端不应依赖它不需要的接口，接口要小而专）｜D 依赖倒置（DIP，高层不依赖低层，二者都依赖抽象；抽象不依赖细节，细节依赖抽象）。⚠️ 开闭原则是面向对象设计的核心目标，也是设计模式存在的根本理由。

5工作流管理系统（WFMS）的六个模块与五个接口中，接口的标准化是为了：
A实现不同 WFMS 产品之间的互操作与集成
B提高单个模块的运行速度
C减少代码量
D统一编程语言
WFMS 六模块：过程定义工具 · 过程定义 · 工作流执行服务（工作流引擎）· 工作流客户端应用 · 被调用的应用 · 管理与监控工具。五接口（WfMC 定义的 WAPI）：接口1 过程定义导入导出 · 接口2 客户端与引擎 · 接口3 被调用应用 · 接口4 引擎间互操作 · 接口5 管理与监控。⚠️ 五个接口标准化的目的就是让不同厂商的产品能互操作与集成（避免被单一厂商锁定）。

6面向对象设计中，关于"持久化类"与 ORM，下列说法正确的是：
AORM 将对象模型与关系模型做映射，使对象可直接存取关系数据库，无需手写 SQL
BORM 会显著降低性能，应当完全不用
C持久化类必须继承某个特定基类
DORM 只能用于 NoSQL 数据库
ORM（对象关系映射）：把对象模型与关系数据模型做映射，使业务代码可以像操作对象一样存取数据库，由框架自动生成 SQL。持久化类是需要存入数据库的实体类。权衡：优点是开发效率高、屏蔽 SQL 差异；代价是复杂查询的性能与灵活性不如手写 SQL（N+1 查询、无法精细调优），所以复杂报表类场景仍应手写 SQL 或做混合方案。
