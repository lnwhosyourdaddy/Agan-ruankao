先说清一个诚信与用法边界

本章用一套虚构的真实项目语境（呼叫中心/智能语音）做演练，目的是让知识点"有处可挂"。

方向 ① 系统分析与建模（40.9%，必须练到条件反射）

场景演练 1：需求获取冲突（对应 2025-04~05 需求调研）

老陶（十年老坐席）说"新系统这也不对那也不对"，小黄（新坐席）说"老系统太慢"，郑专员要求"先满足合规"，
洪经理要"尽快上线"。你是甘工，用什么方法获取需求、如何化解冲突？

采分点答案骨架：

  • 需求获取方法（采分点）：访谈（一对一 + 群体）· 问卷 · 观察（跟班）· 文档审阅 · 联合开发/原型
  • 冲突化解（采分点）：老陶是信息源（最懂业务）不能忽视；小黄是受影响用户要听；

郑专员有一票否决权必须先满足合规；洪经理的进度诉求用分阶段交付满足

  • 落到"需求跟踪矩阵（RTM）"：需求来源 → 设计 → 实现 → 测试全链路可追溯（解决合规追溯与验收争议）

场景演练 2：DFD 纠错（40.9% 方向里最常考）

某项目的 DFD 中出现"数据存储 → 外部实体"的数据流、加工只有输入没有输出。
指出错误类型并解释规则。
✅ 采分点：① 外部实体与数据存储之间不能有数据流（数据流必须起于或止于加工）；
② 加工必须有输入也有输出（只有输入无输出 = 黑洞）。答时要"分类 + 指出图中位置"两段式。

方向 ② Web / 分布式架构（25%）

场景演练 3：双十一压测崩库（对应 2025-11 压测失败 + 高频仿真原题）

双十二压测发现数据库 CPU 100%、大量缓存击穿与穿透。给出优化方案并说明取舍。

采分点答案骨架（按"由外到内"五层答，这是标准答题顺序）：

层次措施解决什么
① CDN商品详情页静态化 + CDN挡掉大部分读请求
② 反向代理Nginx 缓存挡重复读
③ 分布式缓存Redis 集群（读���分离 + 哨兵）热点数据
④ 本地缓存Caffeine单机重复读
⑤ 数据库读写分离 / 分库分表治本

穿透 → 布隆过滤器 + 空值缓存；击穿 → 互斥锁 / 逻辑过期；雪崩 → TTL 随机抖动。
缓存写策略：订单类一致性要求高 → Write-Through；埋点日志类可容忍丢失 → Write-Behind。
⚠️ 不要写"调大连接池" —— 那是让请求排队，不是解决压力。

场景演练 4：CAP 取舍（对应微服务/多活场景）

甲方徐总监要求"多活 + 数据强一致"，卢总说"资源不够"。你怎么解释 CAP 并给方案？

采分点：CAP 最多取二，实践必保 P（分区容错） → 只能 CP（放弃可用性，如 ZooKeeper/Redis Cluster 强一致）
或 AP（放弃一致性，如 Cassandra 最终一致）。⚠️ "既要强一致又要高可用"是外行话 ——
答题时把这句点出来，就是采分点。

方向 ③ 面向对象（18.2%）

场景演练 5：模块拆分争论（对应 2025-08~10 模块划分争论，彭工反对打补丁）

彭工坚持"每个模块独立"，陈工说"这样开发慢，先共用一个工具类"。用耦合内聚分析这件事。

采分点：

  • 高内聚低耦合是总原则（方向相反：内聚要高、耦合要低）
  • "共用一个工具类"= 公共耦合（共享同一公共数据区，耦合度高，要避免）；

若只是传简单参数 = 数据耦合（可接受）

  • 内聚七级最好的是功能内聚，最坏是偶然内聚
  • 单元测试可行性也是判据（高内聚模块可独立测试）

方向 ④ 数据库（18.2%）

场景演练 6：数据之痛（对应冲突库第 10 条：同一客户四个编码）

客户信息在不同系统里有四套编码，报表口径不一。给出数据治理方案。

采分点：

  • 主数据管理（MDM）：建立统一客户主数据标准，是数资源规划的典型应用
  • 数据分类分级 + 主数据分发机制
  • ODS 贴源 → DWD 清洗 → DWS 汇总 → ADS 应用 四层分层，口径统一在 DWS 层收敛
  • ⚠️ 徐总监关心的"架构统一、主数据"正是信息资源规划（IRP）的标准答案

方向 ⑤ 软件工程过程（11.4%）

场景演练 7：进度 vs 质量（对应冲突库第 2 条，李工 vs 丁工）

甲方要求 2026-01 迎峰度夏前必须上线，李工要按期，丁工守缺陷门禁不肯放行。你怎么处理？

采分点：

  • GB/T 8566 生命周期与过程：确认双方在哪个过程产生分歧（通常是确认测试与运行之间）
  • 质量保证 QA（过程审计、预防）vs 质量控制 QC（产品检查、发现） —— 丁工守的是质量门禁
  • 应对：分阶段上线（先试点单区域）+ 明确遗留问题清单与责任 + 风险上报 PMO（詹工）
  • ⚠️ 别写"让质量让步"——正确表述是"分级放行 + 风险可见 + 遗留清单签字确认"

方向 ⑥ 项目管理（2.3%，但 PERT 与挣值必须会）

场景演练 8：关键路径与挣值（最高性价比的计算题）

给出活动工期（三点估算）问关键路径；给出 PV/EV/AC 问偏差并预测 EAC。

采分点：

  • PERT 期望工期 = (O + 4M + P) / 6，标准差 = (P − O) / 6
  • 关键路径 = 最长路径，其上活动总时差 = 0；总时差 = LS − ES
  • 挣值四指标：CV = EV − AC（负=超支）· SV = EV − PV（负=落后）· CPI = EV/AC（<1 超支）· SPI = EV/PV（<1 落后）
  • EAC = BAC / CPI（按当前绩效推算）

> ① 压测发现大促话务量下数据库 CPU 打满，缓存大量失效；

> ④ 某第三方业务系统接口变更未提前通知，导致工单推送中断。

案例背景

【说明】

某全国连锁药店企业在新冠肺炎疫情期间，紧急推出在线口罩预约业务系统。该业务系统为普通用户提供口罩商品查询、购买、订单查询等业务，为后台管理人员提供订单查询、 订单地点分布汇总、物流调度等功能。该系统核心的关系模式为预约订单信息表。

推出业务系统后，几天内业务迅速增长到每日10万多笔预约订单，系统数据库服务器 压力剧增，导致该业务交易响应速度迅速降低，甚至出现部分用户页面无法刷新、预约订单 服务无响应的情况。为此，该企业紧急成立技术团队，由张工负责，以期尽快解决该问题。

    经过分析，张工认为当前预约订单信息表存储了所有订单信息，记录已达到了百万级别。系统主要的核心功能均涉及对订单信息表的操作，应首先优化预约订单信息表的读写性能，建议针对系统中的SQL语句，建立相应索引，并进行适当的索引优化。

    针对张工的方案，其他设计人员提出了一些异议，认为索引过多有很多副作用。请用100 字以内的文字简要说明索引过多的副作用。
    参考答案
    • 常见的索引副作用有：
    • （1）过多索引会占用大量存储空间；（2）更新语句会引发索引更新，过多索引更新开销较大；（3）过多索引导致索引的历史统计信息过多。（4）索引过多导致查询优化器需要评估组合增多。（5）聚集索引的变化会导致非聚集索引的同步变化。

真题 18考点 · 面向对象设计 设计类识别、类关系、状态图⭐⭐⭐

案例背景

【说明】

某软件公司为某企业开发一套在线办公自动化系统，以提升企业管理服务的质量和效率。公司决定采用面向对象方法开发该系统，张工负责对员工请假审批业务进行了分析，具体描述如下：

企业员工通过请假申请页面提出请假申请后，首先由部门经理进行审核，若请假理由不合理，部门经理拒绝请假申请，将申请退回给员工，员工对请假申请表进行修改再次提交，或放弃请假申请。

若请假理由合理，且请假天数小于等于3天，则部门经理直接批准请假申请，生成请假批准单，申请结束。

若请假天数大于3天，则在部门经理批准请假申请后，需要提交给副总经理审核批准。副总经理若认为该申请合理，则审核通过，生成请假批准单，流程结束；若副总经理认为申请不合理，则拒绝请假申请，将请假申请退回给员工。
题目（逐问展开答案）
  • 1
    识别设计类是面向对象设计过程中的重要环节之一，设计类表达了类的职责，即该类所承担的任务。请用300字以内的文字说明设计类通常包含哪3种类型，以及每种类型的主要职责，并从题干描述案例涉及的具体类为每种类型的设计类举出两个实例。
    参考答案
    🔴 核心
    • 设计类分为实体类、控制类、边界类三类：
    • 「实体类」：负责映射业务实体，持久化存储业务数据，实例：员工信息类、请假申请表类；
    🟡 支撑
    • 「控制类」：管控用例专属的业务控制逻辑，实例：请假提交控制类、请假审批控制类；
    🟢 加分
    • 「边界类」：封装系统内外交互的信息流、接口，实例：请假申请页面类、请假批准单类。
  • 2
    识别类之间的关系是面向对象分析过程中的重要环节之一，常见的类之间关系包括泛化关系、关联关系、聚合关系、组合关系等。请用300字以内的文字对泛化关系和关联关系的内涵进行描述，并根据题干具体类的描述为这两种关系各举出一种实例。
    参考答案
    🔴 核心
    • 「泛化关系」：表示父类（通用抽象）和子类（特殊细化）的继承关系，子类复用父类属性与行为。实例：员工（父类）和部门经理（子类），部门经理是员工的特殊岗位类型。
    🟡 支撑
    • 「关联关系」：表示不同类的实例之间长期存在的业务结构联系。实例：员工类和请假记录类，一个员工可以产生多条请假记录，二者存在业务关联。

真题 28考点 · 农业物联网 IoTDB 与 Netty 架构⭐⭐⭐

案例背景
某单位拟建设农业物联网项目，主要建设内容如下：

数据采集：接入多种通信协议与多种农业传感器（如温湿度、土壤墒情、光照、CO₂ 等），实现多源异构农业数据的统一采集与上报。

物联网平台：建设统一的物联网平台，负责设备接入、数据汇聚、存储与下发。

技术选型：采用 IoTDB 作为时序数据库存储传感器数据，使用 Netty 实现高性能网络通信，使用 Kafka Cluster 作为消息中间件，实现采集数据与下游业务的解耦与流式处理。

请结合上述场景回答下列问题。
题目（逐问展开答案）
  • 1
    简述时序数据库的典型特点，并说明本项目为何选用时序数据库（如 IoTDB）存储农业传感器数据。
    参考答案
    • 1. 时序数据库的典型特点
    • 按时间组织与高写入：数据按时间戳有序写入，写多读少或按时间范围查询为主，适合传感器、监控等场景。
    • 高压缩比：针对时间序列采用列式存储与专用压缩算法（如 Delta 编码、Gorilla 等），在保证精度的前提下显著降低存储与 IO。
    • 时序查询与聚合：支持按时间范围、降采样、滑动窗口、多序列对齐等时序特有查询与聚合。
    • 多序列/多测点模型：天然支持“设备 × 测点 × 时间”的多维建模，便于按设备、按测点统一管理。
    • 可扩展与高可用：多数产品支持分布式、副本与故障转移，便于随数据量和并发增长做水平扩展。
    • 2. 本项目为何使用时序数据库
    • 农业传感器数据本质是按时间产生的测点序列，具有强时间属性、写多读少、按时间查询与聚合等典型时序特征，与时序数据库的存储和查询模型高度匹配。选用 IoTDB 等时序库可以：提高写入与查询性能、通过压缩降低存储成本、利用内置时序函数做统计与告警，并便于与大数据/AI 平台集成，实现农业数据的统一管理与智能分析。
    • *解析
    • 考察 IoT 场景下的专用数据库选型。
  • 2
    从扩展性、稳定性等多方面简述本项目采用 Netty 作为网络通信框架的原因。
    参考答案
    • 采用 Netty 作为网络通信框架的原因
    • 高性能：基于 NIO 和事件驱动模型，可用少量线程处理大量并发连接，适合物联网海量设备接入；通过内存池、零拷贝等机制提高吞吐量、降低资源消耗。
    • 扩展性强：采用 ChannelPipeline、ChannelHandler 模块化设计，可灵活增加协议解析、编解码、加密、业务处理等功能，便于接入不同类型的农业传感器和通信协议。
    • 稳定可靠：提供连接管理、心跳检测、空闲检测、异常处理等机制，能够应对设备断线、网络波动和突发流量等物联网场景。
    • 开发方便：提供完善的网络通信 API 和编解码机制，支持 TCP、UDP、HTTP、WebSocket 等协议，可降低网络通信开发复杂度。
    • 成熟度高：开源生态和社区成熟，经过大量高并发、分布式系统实践验证，便于长期维护和演进。
    • *解析
    • 考察高性能网络通信框架。
