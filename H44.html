第 44 小时 · 案例分析专项（三）· 六大方向专项与场景实战

本学时是案例专项的收官，目标是把「22 章知识 + 三学时答题方法」合成实战能力。
做法：① 按实测分布给六大方向各配"必备采分点 + 典型陷阱"；
② 用一套真实项目语境（呼叫中心/智能语音）串起 22 章，做场景化演练。

先说清一个诚信与用法边界

本章用一套虚构的真实项目语境（呼叫中心/智能语音）做演练，目的是让知识点"有处可挂"。
但考场答题必须按题目给定的场景作答——把"自家项目"套进答案属于跑题，是案例科第一大忌。
本章正确定位：平时演练熟悉度 + 积累"业务细节素材"，不是答案模板。

方向 ① 系统分析与建模（40.9%，必须练到条件反射）

场景演练 1：需求获取冲突（对应 2025-04~05 需求调研）

老陶（十年老坐席）说"新系统这也不对那也不对"，小黄（新坐席）说"老系统太慢"，郑专员要求"先满足合规"，
洪经理要"尽快上线"。你是甘工，用什么方法获取需求、如何化解冲突？

采分点答案骨架：

  • 需求获取方法（采分点）：访谈（一对一 + 群体）· 问卷 · 观察（跟班）· 文档审阅 · 联合开发/原型
  • 冲突化解（采分点）：老陶是信息源（最懂业务）不能忽视；小黄是受影响用户要听；

郑专员有一票否决权必须先满足合规；洪经理的进度诉求用分阶段交付满足

  • 落到"需求跟踪矩阵（RTM）"：需求来源 → 设计 → 实现 → 测试全链路可追溯（解决合规追溯与验收争议）

场景演练 2：DFD 纠错（40.9% 方向里最常考）

某项目的 DFD 中出现"数据存储 → 外部实体"的数据流、加工只有输入没有输出。
指出错误类型并解释规则。
✅ 采分点：① 外部实体与数据存储之间不能有数据流（数据流必须起于或止于加工）；
② 加工必须有输入也有输出（只有输入无输出 = 黑洞）。答时要"分类 + 指出图中位置"两段式。

方向 ② Web / 分布式架构（25%）

场景演练 3：双十一压测崩库（对应 2025-11 压测失败 + 高频仿真原题）

双十二压测发现数据库 CPU 100%、大量缓存击穿与穿透。给出优化方案并说明取舍。

采分点答案骨架（按"由外到内"五层答，这是标准答题顺序）：

层次措施解决什么
① CDN商品详情页静态化 + CDN挡掉大部分读请求
② 反向代理Nginx 缓存挡重复读
③ 分布式缓存Redis 集群（读���分离 + 哨兵）热点数据
④ 本地缓存Caffeine单机重复读
⑤ 数据库读写分离 / 分库分表治本

穿透 → 布隆过滤器 + 空值缓存；击穿 → 互斥锁 / 逻辑过期；雪崩 → TTL 随机抖动。
缓存写策略：订单类一致性要求高 → Write-Through；埋点日志类可容忍丢失 → Write-Behind。
⚠️ 不要写"调大连接池" —— 那是让请求排队，不是解决压力。

场景演练 4：CAP 取舍（对应微服务/多活场景）

甲方徐总监要求"多活 + 数据强一致"，卢总说"资源不够"。你怎么解释 CAP 并给方案？

采分点：CAP 最多取二，实践必保 P（分区容错） → 只能 CP（放弃可用性，如 ZooKeeper/Redis Cluster 强一致）
或 AP（放弃一致性，如 Cassandra 最终一致）。⚠️ "既要强一致又要高可用"是外行话 ——
答题时把这句点出来，就是采分点。

方向 ③ 面向对象（18.2%）

场景演练 5：模块拆分争论（对应 2025-08~10 模块划分争论，彭工反对打补丁）

彭工坚持"每个模块独立"，陈工说"这样开发慢，先共用一个工具类"。用耦合内聚分析这件事。

采分点：

  • 高内聚低耦合是总原则（方向相反：内聚要高、耦合要低）
  • "共用一个工具类"= 公共耦合（共享同一公共数据区，耦合度高，要避免）；

若只是传简单参数 = 数据耦合（可接受）

  • 内聚七级最好的是功能内聚，最坏是偶然内聚
  • 单元测试可行性也是判据（高内聚模块可独立测试）

方向 ④ 数据库（18.2%）

场景演练 6：数据之痛（对应冲突库第 10 条：同一客户四个编码）

客户信息在不同系统里有四套编码，报表口径不一。给出数据治理方案。

采分点：

  • 主数据管理（MDM）：建立统一客户主数据标准，是数资源规划的典型应用
  • 数据分类分级 + 主数据分发机制
  • ODS 贴源 → DWD 清洗 → DWS 汇总 → ADS 应用 四层分层，口径统一在 DWS 层收敛
  • ⚠️ 徐总监关心的"架构统一、主数据"正是信息资源规划（IRP）的标准答案

方向 ⑤ 软件工程过程（11.4%）

场景演练 7：进度 vs 质量（对应冲突库第 2 条，李工 vs 丁工）

甲方要求 2026-01 迎峰度夏前必须上线，李工要按期，丁工守缺陷门禁不肯放行。你怎么处理？

采分点：

  • GB/T 8566 生命周期与过程：确认双方在哪个过程产生分歧（通常是确认测试与运行之间）
  • 质量保证 QA（过程审计、预防）vs 质量控制 QC（产品检查、发现） —— 丁工守的是质量门禁
  • 应对：分阶段上线（先试点单区域）+ 明确遗留问题清单与责任 + 风险上报 PMO（詹工）
  • ⚠️ 别写"让质量让步"——正确表述是"分级放行 + 风险可见 + 遗留清单签字确认"

方向 ⑥ 项目管理（2.3%，但 PERT 与挣值必须会）

场景演练 8：关键路径与挣值（最高性价比的计算题）

给出活动工期（三点估算）问关键路径；给出 PV/EV/AC 问偏差并预测 EAC。

采分点：

  • PERT 期望工期 = (O + 4M + P) / 6，标准差 = (P − O) / 6
  • 关键路径 = 最长路径，其上活动总时差 = 0；总时差 = LS − ES
  • 挣值四指标：CV = EV − AC（负=超支）· SV = EV − PV（负=落后）· CPI = EV/AC（<1 超支）· SPI = EV/PV（<1 落后）
  • EAC = BAC / CPI（按当前绩效推算）

事件管理领域措施（答满 2 条即得分）

1综合演练题中"数据库 CPU 打满 + 缓存大量失效"这一事件，最贴合的解决方案组合是：
A五层缓存（CDN→Nginx→Redis→本地缓存→读写分离）+ TTL 随机抖动防雪崩 + 互斥锁防击穿 + 布隆过滤器防穿透
B调大数据库连接池，让更多请求排队
C把缓存全部改成同步写库（Write-Through）保证一致
D直接扩容数据库从 1 主 1 备升到 4 主 4 备
"CPU 打满 + 缓存失效"要分清是哪一类失效：雪崩（大量 key 同时过期）→ TTL 加随机抖动打散 + 多级缓存；击穿（热点 key 过期）→ 互斥锁单飞或逻辑过期异步刷新；穿透（查不存在）→ 布隆过滤器 + 空值缓存。⚠️ 真正的治本手段是由外到内分层缓存（把读请求挡在数据库之外）+ 读写分离。B 项"调大连接池"是错误示范：它只是让更多请求排队等数据库，并没有减少数据库实际要处理的查询量，反而可能因线程切换加剧恶化。

2某项目面临"甲方要求按时上线"与"测试负责人坚持守缺陷门禁"的冲突。下列处理方式最恰当的是：
A分级放行——分阶段上线（先试点单区域）+ 明确遗留问题清单与责任 + 风险上报 PMO
B让质量让步，按期上线，缺陷留到下一版本
C坚持不放行，即使错过迎峰度夏节点
D要求测试负责人签字承担全部延期责任
进度与质量的冲突是案例高频场景。正确处理公式："不放水，也不硬扛，而是分级放行 + 风险可见"——① 分阶段上线（先试点单区域，降低爆炸半径）；② 明确遗留问题清单并双方签字确认（把风险显性化，而不是隐性带过）；③ 风险上报 PMO（詹工这个角色的价值所在）。⚠️ 错误做法：让质量让步（把风险带到生产）或坚持不放行（违约且不可接受）。⚠️ 术语要点：这是确认测试与运行之间的质量门禁问题，涉及 QA（过程审计、预防）vs QC（产品检查、发现） 的区分。
第44小时 · 方向⑤ 软件工程过程
3第三方业务系统未提前通知接口变更，导致工单推送中断。下列措施中"最不能解决根本问题"的是：
A加一个接口调用的监控告警，能第一时间发现中断
B在合同或接口协议中明确变更须提前 N 个工作日书面通知
C建立变更管理流程（CCB），所有变更需评审与授权
D推动双方建立接口版本管理与灰度切换机制
区分"治标"与"治本"：加监控告警属于事后发现（缩短 MTTR），不解决根本问题（接口变更仍未被通知）。根本措施是"事前约定 + 流程约束"：② 合同/协议中明确变更提前告知义务与违约责任（法律与商务层面）｜③ 变更管理流程（CCB） 约束内部变更 ｜④ 接口版本管理 + 灰度切换（技术上让变更可平滑过渡）。⚠️ 这条正是项目故事线里"第三方甩锅"冲突（冲突库第 6 条）的标准答案——案例常问"如何从管理上避免此类风险"，答案是契约化 + 流程化 + 技术兜底 三层。
第44小时 · 综合演练题 · 事件④
4甲方要求"多活部署且数据强一致"，技术总监说资源不够。系统分析师最恰当的回应是：
A说明 CAP 最多取二，实践必保分区容错，因此强一致与高可用不可兼得，需二选一并给出取舍理由
B同意强一致，放弃可用性，因为可用性可以后补
C同意高可用，放弃一致性，因为数据可以后补
D告诉甲方 CAP 理论已经过时，不必考虑
CAP 是案例的经典采分点：Consistency（一致性）· Availability（可用性）· Partition tolerance（分区容错），三者最多取二。⚠️ 实践共识：分布式系统"必须保 P"（否则网络分区时系统直接不可用）→ 实际只剩 CP（放弃可用性，如 ZooKeeper/etcd/Redis Cluster 强一致）或 AP（放弃一致性，如 Cassandra 最终一致 + 补偿/对账兜底）。回应甲方的话术是："P 是底线，我们可以保 P；C 和 A 需要您选一个优先级——若保 C（资金/工单强一致）就用 CP，若保 A（呼叫接续高可用）就用 AP + 最终一致 + 对账兜底。"

5关于本章"阿甘场景"的正确用法，下列说法正确的是：
A平时演练熟悉度、把真实项目当素材库；考场必须按题目给定场景作答，套自家项目属跑题
B考场答题时直接把本章的项目细节写进答案，会更真实
C本章的场景可以直接套用到任何题目
D本章内容是标准答案模板，考试直接用
这是一条诚信与方法论的边界：本章用一套虚构的真实项目语境（呼叫中心/智能语音）让知识点"有处可挂"，目的是降低理解成本、积累业务细节素材。⚠️ 但案例科的评分依据是"答案是否回应了题目给定的场景与设问"——把自家项目套进答案属于跑题，是案例科第一大忌（参考 H42：跑题是最大风险，摘要/论述维度占 30 分且是及格线所在）。正确用法：① 平时演练用真实项目建立熟悉度；② 积累项目细节作为"举例"的素材；③ 考场严格按题干场景改写后再作答。
第44小时 · 用法边界
6面对"某客户在不同系统里有四套编码、报表口径不一"的问题，最根本的解决方向是：
A建立主数据管理（MDM）与统一的主数据标准，在数仓分层中把口径收敛在汇总层
B要求各系统统一导出格式为 Excel
C增加一张对照表人工维护映射关系
D让报表开发人员每次手工核对
"同一实体多套编码、口径不一"是数据治理的经典命题，根本方向是 ① 主数据管理（MDM）：为客户、产品等核心实体建立唯一权威数据源与统一标准，并向各系统分发；② 数据分类分级明确哪些是主数据、哪些是业务数据；③ 在数仓分层中让口径收敛——ODS 贴源保留各系统原始码，DWD 做映射与清洗，DWS 层按统一口径汇总，ADS 直接消费 DWS。⚠️ B/C/D 都是治标（人工核对成本高、口径仍不统一、无法规模化）。关联知识点：信息资源规划（IRP）五层规划、数据仓库分层、集成数据视图。
