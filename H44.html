方向 ① 系统分析与建模（40.9%，必须练到条件反射）

场景演练 1：需求获取冲突（对应 2025-04~05 需求调研）

老陶（十年老坐席）说"新系统这也不对那也不对"，小黄（新坐席）说"老系统太慢"，郑专员要求"先满足合规"，
洪经理要"尽快上线"。你是甘工，用什么方法获取需求、如何化解冲突？

采分点答案骨架：

  • 需求获取方法（采分点）：访谈（一对一 + 群体）· 问卷 · 观察（跟班）· 文档审阅 · 联合开发/原型
  • 冲突化解（采分点）：老陶是信息源（最懂业务）不能忽视；小黄是受影响用户要听；

郑专员有一票否决权必须先满足合规；洪经理的进度诉求用分阶段交付满足

  • 落到"需求跟踪矩阵（RTM）"：需求来源 → 设计 → 实现 → 测试全链路可追溯（解决合规追溯与验收争议）

场景演练 2：DFD 纠错（40.9% 方向里最常考）

某项目的 DFD 中出现"数据存储 → 外部实体"的数据流、加工只有输入没有输出。
指出错误类型并解释规则。
✅ 采分点：① 外部实体与数据存储之间不能有数据流（数据流必须起于或止于加工）；
② 加工必须有输入也有输出（只有输入无输出 = 黑洞）。答时要"分类 + 指出图中位置"两段式。

方向 ② Web / 分布式架构（25%）

场景演练 3：双十一压测崩库（对应 2025-11 压测失败 + 高频仿真原题）

双十二压测发现数据库 CPU 100%、大量缓存击穿与穿透。给出优化方案并说明取舍。

采分点答案骨架（按"由外到内"五层答，这是标准答题顺序）：

层次措施解决什么
① CDN商品详情页静态化 + CDN挡掉大部分读请求
② 反向代理Nginx 缓存挡重复读
③ 分布式缓存Redis 集群（读���分离 + 哨兵）热点数据
④ 本地缓存Caffeine单机重复读
⑤ 数据库读写分离 / 分库分表治本

穿透 → 布隆过滤器 + 空值缓存；击穿 → 互斥锁 / 逻辑过期；雪崩 → TTL 随机抖动。
缓存写策略：订单类一致性要求高 → Write-Through；埋点日志类可容忍丢失 → Write-Behind。
⚠️ 不要写"调大连接池" —— 那是让请求排队，不是解决压力。

场景演练 4：CAP 取舍（对应微服务/多活场景）

甲方徐总监要求"多活 + 数据强一致"，卢总说"资源不够"。你怎么解释 CAP 并给方案？

采分点：CAP 最多取二，实践必保 P（分区容错） → 只能 CP（放弃可用性，如 ZooKeeper/Redis Cluster 强一致）
或 AP（放弃一致性，如 Cassandra 最终一致）。⚠️ "既要强一致又要高可用"是外行话 ——
答题时把这句点出来，就是采分点。

方向 ③ 面向对象（18.2%）

场景演练 5：模块拆分争论（对应 2025-08~10 模块划分争论，彭工反对打补丁）

彭工坚持"每个模块独立"，陈工说"这样开发慢，先共用一个工具类"。用耦合内聚分析这件事。

采分点：

  • 高内聚低耦合是总原则（方向相反：内聚要高、耦合要低）
  • "共用一个工具类"= 公共耦合（共享同一公共数据区，耦合度高，要避免）；

若只是传简单参数 = 数据耦合（可接受）

  • 内聚七级最好的是功能内聚，最坏是偶然内聚
  • 单元测试可行性也是判据（高内聚模块可独立测试）

方向 ④ 数据库（18.2%）

场景演练 6：数据之痛（对应冲突库第 10 条：同一客户四个编码）

客户信息在不同系统里有四套编码，报表口径不一。给出数据治理方案。

采分点：

  • 主数据管理（MDM）：建立统一客户主数据标准，是数资源规划的典型应用
  • 数据分类分级 + 主数据分发机制
  • ODS 贴源 → DWD 清洗 → DWS 汇总 → ADS 应用 四层分层，口径统一在 DWS 层收敛
  • ⚠️ 徐总监关心的"架构统一、主数据"正是信息资源规划（IRP）的标准答案

方向 ⑤ 软件工程过程（11.4%）

场景演练 7：进度 vs 质量（对应冲突库第 2 条，李工 vs 丁工）

甲方要求 2026-01 迎峰度夏前必须上线，李工要按期，丁工守缺陷门禁不肯放行。你怎么处理？

采分点：

  • GB/T 8566 生命周期与过程：确认双方在哪个过程产生分歧（通常是确认测试与运行之间）
  • 质量保证 QA（过程审计、预防）vs 质量控制 QC（产品检查、发现） —— 丁工守的是质量门禁
  • 应对：分阶段上线（先试点单区域）+ 明确遗留问题清单与责任 + 风险上报 PMO（詹工）
  • ⚠️ 别写"让质量让步"——正确表述是"分级放行 + 风险可见 + 遗留清单签字确认"

方向 ⑥ 项目管理（2.3%，但 PERT 与挣值必须会）

场景演练 8：关键路径与挣值（最高性价比的计算题）

给出活动工期（三点估算）问关键路径；给出 PV/EV/AC 问偏差并预测 EAC。

采分点：

  • PERT 期望工期 = (O + 4M + P) / 6，标准差 = (P − O) / 6
  • 关键路径 = 最长路径，其上活动总时差 = 0；总时差 = LS − ES
  • 挣值四指标：CV = EV − AC（负=超支）· SV = EV − PV（负=落后）· CPI = EV/AC（<1 超支）· SPI = EV/PV（<1 落后）
  • EAC = BAC / CPI（按当前绩效推算）

4甲方要求"多活部署且数据强一致"，技术总监说资源不够。系统分析师最恰当的回应是：
A说明 CAP 最多取二，实践必保分区容错，因此强一致与高可用不可兼得，需二选一并给出取舍理由
B同意强一致，放弃可用性，因为可用性可以后补
C同意高可用，放弃一致性，因为数据可以后补
D告诉甲方 CAP 理论已经过时，不必考虑
CAP 是案例的经典采分点：Consistency（一致性）· Availability（可用性）· Partition tolerance（分区容错），三者最多取二。⚠️ 实践共识：分布式系统"必须保 P"（否则网络分区时系统直接不可用）→ 实际只剩 CP（放弃可用性，如 ZooKeeper/etcd/Redis Cluster 强一致）或 AP（放弃一致性，如 Cassandra 最终一致 + 补偿/对账兜底）。回应甲方的话术是："P 是底线，我们可以保 P；C 和 A 需要您选一个优先级——若保 C（资金/工单强一致）就用 CP，若保 A（呼叫接续高可用）就用 AP + 最终一致 + 对账兜底。"
