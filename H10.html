H10 数据库系统（二）· 范式与事务并发控制 1 / 18

第 10 小时 · 数据库系统（二）· 范式与事务并发控制

本学时覆盖 5.2 范式链（1NF→2NF→3NF→BCNF→4NF）+ 模式分解 + 5.3 事务与并发控制。
这是整个数据库章的计算与辨析核心，也是最容易拉开分差的一块。

考情定位

五块必拿：① 范式链递进关系（1NF⊂2NF⊂3NF⊂BCNF⊂4NF）；② 2NF 拆部分依赖、3NF 拆传递依赖、BCNF 全属性完全依赖；③ ACID 四性（尤其"一致性不是独立机制"）；④ 并发三类问题（丢失修改/不可重复读/脏读，不含死锁）；⑤ 三级封锁协议与两段锁。

记忆口诀

范式链口诀："2NF 拆部分，3NF 拆传递，BCNF 全都要。"
ACID：原子（全做全不做）· 一致（前后满足约束）· 隔离（并发互不干扰）· 持久（提交不丢）。
三级封锁：一级写前 X 锁到结束；二级再加读前 S 锁到结束；三级读 S 锁立即释放 + 写 X 锁立即释放。

易错陷阱

"3NF 属于 2NF、也属于 1NF"——链是单向塔，越高条件越严。反方向都不成立（4NF 不一定是 BCNF，BCNF 一定是 3NF）。
二级/三级封锁协议都不能保证"不可重复读"以外的全部——三级仍允许脏读。
死锁不属于并发一致性问题的标准三类，它是并发控制的另一条支线。

5.2 规范化为什么需要 ⭐

设有关系模式 R(SNAME, CNAME, TNAME, TADDRESS)，属性分别是学生姓名、选修课程名、任课教师姓名、任课教师地址。

这个模式只有 4 个属性，却是性能很差的模式。

① 数据冗余

某门课有 100 个学生选修，关系里就出现 100 个元组，教师姓名和地址重复出现 100 次

② 修改异常

改这个教师的地址，要改 100 个元组，否则出现地址值不一致

③ 插入异常

不知道听课学生名单，这个教师的任课情况和家庭地址就无法入库，否则要在学生姓名处插空值

④ 删除异常

某门课任课教师要更换，原来这位教师的地址会随之丢失

产生异常的根本原因：关系模式中属性值之间的联系。

在 R 中，学生与课程有直接联系，教师与课程有直接联系，而教师与学生无直接联系 —— 这就产生了异常。

解决办法：把 R 分解为

R1(SNAME, CNAME) 和 R2(CNAME, TNAME, TADDRESS)

即可消除上述存储异常。

四个异常口诀：冗余 → 修改难 → 插不进 → 删丢数（这四类异常是判断"要不要规范化"的标准论据）

函数依赖与键 ⭐⭐

设 R(U) 是属性 U 上的关系模式，X、Y 是 U 的子集。若对 r 中任意两个元组 u、v，只要有 u[X]=v[X] 就有 u[Y]=v[Y]，则称 X 函数决定 Y，或 Y 函数依赖于 X，记作 X → Y。

完全函数依赖

X→Y，且对 X 的任何一个真子集 X′，X′→Y 都不成立
Y 必须靠整个 X 才能定

部分函数依赖

X→Y，但 Y 不完全函数依赖于 X
只用 X 的一部分就能定 Y

传递函数依赖

X→Y（Y 不是 X 的真子集），Y→X 不成立，Y→Z，则称 Z 对 X 传递函数依赖
例：Sno→Dno→Dname

🔑候选键的定义

若 X → U 在 R(U) 上成立，并且不存在 X 的任一真子集 X′ 使 X′ → U 成立，则称 X 是 R 的一个候选键。

也就是说，X 的值唯一决定关系中的所有元组。

  • 有多个候选键时，选一个作主键
  • 两个关系拥有公共属性集，且公共属性在一个关系中是主键，则它是另一个关系的外键

🗺️求候选键的图示法

第 1 步把函数依赖画成有向图：顶点是属性，弧是依赖关系

第 2 步找入度为 0 的属性集，以它为起点尝试遍历全图：

  • 能遍历所有结点 → 它就是候选键
  • 不能 → 把一些中间顶点（有入度也有出度）并进来，直到能遍历全部

候选键求解 · 例题精讲 ⭐⭐

题目：给定关系 R(A₁, A₂, A₃, A₄) 上的函数依赖集
F = { A₁→A₂, A₃→A₂, A₂→A₃, A₂→A₄ }，求 R 的候选键。

🕸️第一步：画函数依赖有向图

✅第二步：从入度 0 出发遍历

入度 0 的顶点A₁（只有出度，没有入度）

从 A₁ 出发A₁→A₂　继续 A₂→A₃、A₂→A₄
四个顶点全部遍历到

结论R 的候选键 = A₁（单个属性）

通用口诀：只出现在左部的必是候选键成员；只出现在右部的必不是；两边都不出现的必是；两边都出现的要试。

⚠️ 若入度 0 的属性集不能遍历全图，就要把"既当左部又当右部"的中间顶点并进来继续试，直到能遍历全部顶点为止。

范式链总览 ⭐⭐

🪜逐级加码：每一级消除一类依赖

1NF

第一范式

属性只包含原子值
每个分量不可再分

2NF

第二范式

在 1NF 上
每个非主属性完全依赖候选键
消除部分函数依赖

3NF

第三范式

在 2NF 上
消除非主属性对候选键的
传递函数依赖

BCNF

BC 范式

在 3NF 上
每个决定因素都包含候选键
消除主属性的部分与传递依赖

4NF

第四范式

在 BCNF 上
消除非平凡多值依赖

口诀：1 不可分 · 2 去部分 · 3 去传递 · BCNF 决定因素含码 · 4 去多值

⚠️ 教材原话：实际应用中，一般只要达到 3NF 就够了。

1NF 与 2NF 详解 ⭐

①第一范式 1NF

在关系模式 R 中，当且仅当所有属性只包含原子值，即每个分量都是不可再分的数据项，则称 R 满足 1NF。

反例：教师职称情况关系（系名称，高级职称人数）

"高级职称人数"下面还分"教授""副教授"——这不是一个原子属性，所以不满足 1NF。

改法：拆成"教授"和"副教授"两个属性，就满足 1NF。

②第二范式 2NF

当且仅当关系模式 R 满足 1NF，且每个非键属性（非主属性）完全依赖于候选键时，称 R 满足 2NF。

即：消除非主属性对候选键的部分函数依赖

反例：选课关系 SC(Sno, Cno, Grade, Credit)

  • (Sno, Cno) → Grade
  • Cno → Credit　← 只用候选键的一部分就能定 Credit

候选键是 (Sno, Cno)，所以 Credit 部分依赖于候选键 → SC 不满足 2NF

改法：拆成 SC1(Sno, Cno, Grade) 和 SC2(Cno, Credit)

判断标准：候选键是"组合键"时，才可能出现部分依赖。候选键是单属性，一定满足 2NF。

3NF 详解 ⭐

当且仅当关系模式 R 满足 2NF，且 R 中消除了非键属性传递依赖于候选键时，称 R 满足 3NF。

即：消除非主属性对候选键的传递函数依赖

📋教材例题：学生关系 S

S(Sno, Sname, Dno, Dname, Location)　分别代表：学号、姓名、所在系、系名称、系地址

SnoSnameDnoDnameLocation
S01张三D01计算机系1号楼
S02李四D01计算机系1号楼
S03王五D01计算机系1号楼
S04赵六D02信息系2号楼

🔍判断过程

第 1 步写出函数依赖：
Sno → (Sname, Dno, Dname, Location)
Dno → (Dname, Location)

第 2 步确定候选键：Sno

第 3 步找传递依赖：
Sno → Dno → Dname
Sno → Dno → Location

结论Dname 与 Location 是非键属性，同时传递依赖于候选键 Sno → 不满足 3NF

改法：拆成

S1(Sno, Sname, Dno) 和 S2(Dno, Dname, Location)

BCNF 与 4NF 详解 ⭐

③BCNF（BC 范式）

如果关系模式 R 满足 1NF，且 R 中没有属性传递依赖于候选键时，称 R 满足 BCNF。

等价判别：每个函数依赖的左部都必须包含候选键

教材例题：关系模式 P(C, S, T, R)

F = { C→T, ST→R, TR→C }

① 求候选键：(S,T) 和 (S,C)

② 主属性有 S、T、C；非主属性只有 R

③ 检查每个左部：C→T 中 C 不包含任何候选键 ❌

④ 结论：P 不满足 BCNF

⚠️ BCNF 的完整条件：所有非键属性对每个候选键都完全函数依赖；所有键属性对每个不包含它的候选键也完全函数依赖；没有任何属性完全函数依赖于非键属性。

④4NF（第四范式）

第四范式是 BCNF 的推广，是针对有多值依赖的关系模型所定义的规范化形式。

  • 多值依赖：R(U,F) 满足 1NF，X、Y 是 U 的非空子集，Z = U−X−Y 也非空，若任取一组值对 (x,z) 都可决定一组 y 值，且此决定与 z 值无关，就称 Y 多值依赖于 X，记作 X →→ Y。
  • 4NF 定义：R 满足 1NF，若对任一多值依赖 X→→Y，X 必包含 R 的候选键，则称 R 满足 4NF。
  • 教材例题：QY(ypm, bm, sccj) —— 用品名、部门、生产厂家

对 ypm 的一个值，不论 sccj 取什么值，总有一组确定的 bm 对应，所以 ypm →→ bm，同样 ypm →→ sccj。

QY 是全码关系（所有属性合起来才是候选键）→ 不满足 4NF

改法：拆成 QY1(ypm, bm) 和 QY2(ypm, sccj)

关系模式分解 ⭐

如果某关系模式存在修改异常等问题，可以通过分解来解决问题。把关系模式分解成几个子关系模式，需要考虑两件事：
是否保持函数依赖 和 是否是无损联接。

✅① 无损联接分解

形式定义：R 分解成 δ = {R₁, …, R_K}，如果对 R 中每个满足 F 的关系 r 都有

r = πR₁(r) ⋈ πR₂(r) ⋈ … ⋈ πR_K(r)

则称 δ 相对于 F 是无损联接分解，否则称为损失联接分解。

判定定理（只分解成两个时最常用）：

设 ρ = {R₁, R₂} 是 R 的分解，则 ρ 无损联接的充要条件是

(R₁ ∩ R₂) → (R₁ − R₂)　或者　(R₁ ∩ R₂) → (R₂ − R₁)

两个条件只要任意一个成立即可

🔒② 保持函数依赖

设 δ = {R₁, …, R_K} 是 R 的一个分解，F 是 R 上的函数依赖集，δ 中每个 Rᵢ 上的函数依赖集是 Fᵢ。

如果 {F₁, F₂, …, F_K} 与 F 是等价的（即相互逻辑蕴涵），则称分解 δ 保持函数依赖。

如果分解不能保持函数依赖，则 δ 的实例上的值就可能有违反函数依赖的现象。

两个质量标准：无损联接 = "拆了还能拼回原样"（必保）；保持函数依赖 = "原来的约束没丢"（尽量保，但两者可能冲突）

5.3 事务的 ACID 特性 ⭐⭐

DBMS 运行的基本工作单位是事务。事务是用户定义的一个数据库操作序列，这些操作要么全做，要么全不做，是一个不可分割的工作单位。

A · 原子性（Atomicity）

事务是数据库的逻辑工作单位，事务的原子性保证事务包含的一组更新操作是原子不可分的——这些操作是一个整体，不能部分地完成。

C · 一致性（Consistency）

使数据库从一个一致性状态变到另一个一致性状态。例：转账中各账户金额必须平衡。
一致性与原子性密切相关；一致性在逻辑上不是独立的，它由事务的隔离性来表示。

I · 隔离性（Isolation）

一个事务的执行不能被其他事务干扰。要求即使有多个事务并发执行，看上去每个事务是按串行调度执行一样。
这一性质也称为可串行性——系统允许的任何交错操作调度等价于一个串行调度。

D · 持久性（Durability）

也称为永久性。事务一旦提交，改变就是永久性的，无论发生何种故障，都不应该对其有任何影响。

口诀：原子（全做或全不做）· 一致（状态对状态）· 隔离（并发互不扰）· 持久（提交即永久）

并发带来的三类问题 ⭐

⚠️数据库的并发操作会带来数据不一致问题

① 丢失修改

事务 A 与事务 B 从数据库中读入同一数据并修改，事务 B 的提交结果破坏了事务 A 提交的结果，导致 A 的修改被丢失。

教材例子：T1 读 A=10 → A=A−5 → 写回；T2 也读 A=10 → A=A−8 → 写回。

③ A=A−5 被 ④ A=A−8 覆盖掉，完全不起作用

② 读"脏"数据

事务 A 修改某数据并写回磁盘，事务 B 读取同一数据后，事务 A 因某种原因被撤销，A 已修改的数据恢复原值，B 读到的数据就与库中数据不一致——这就是"脏数据"。

教材例子：T1 读 A=20 → A=A+50 → 写回 70；T2 读 A=70；然后 T1 ROLLBACK，A 恢复为 20。

T2 读到的 70 就是脏数据。

③ 不可重复读

事务 A 读取数据后，事务 B 执行了更新操作，事务 A 使用的仍是更新前的值，造成数据不一致。

教材例子：T1 读 A=20、B=30，求和 =50；中间 T2 把 A 改成 70；T1 再读 A=70、B=30，求和 =100。

两次计算都没错，但验算对不上——这就是不可重复读。

⚠️ 第四类问题"幻读"（教材本节未单列，但考试常考）：同一查询条件，第二次查询多了或少了行——别的事务对这一批数据做了插入或删除。

口诀：丢改 · 脏读 · 不可重复 · 幻读

封锁与三级封锁协议 ⭐⭐

🔒两种封锁

X 封锁（排他型）

事务 T 对数据 A 加了 X 锁后，只允许 T 读取和修改 A；其他事务要等 T 解除 X 封锁后，才能对 A 加任何类型的锁。
只允许一个事务独锁，具有排他性

S 封锁（共享型）

事务 T 对 A 加了 S 锁后，允许 T 读取 A 但不能修改；在所有 S 封锁解除之前，决不允许任何事务对 A 加 X 封锁。
允许并发读，但不允许修改

💡 X 封锁要求太严，S 封锁是对它的"适当从宽"。

📜三级封锁协议：各解决什么 ⭐

协议加锁规则解决了什么
一级事务 T 在修改数据 R 之前必须先加 X 锁，直到事务结束才释放✅ 防止丢失修改✅ 保证事务 T 是可恢复的❌ 不能保证可重复读、不能防脏读
二级一级 ＋ 事务 T 在读取 R 之前先加 S 锁，读完即可释放 S 锁✅ 防止丢失修改✅ 防止读脏数据❌ 不能保证可重复读
三级一级 ＋ 事务 T 在读取 R 之前先加 S 锁，直到事务结束才释放✅ 防止丢失修改✅ 防止读脏数据✅ 能保证可重复读

口诀：一级防丢改 · 二级加防脏读 · 三级再加防不可重复读。

差别就在"读锁什么时候放"——读完就放（二级）还是事务结束才放（三级）。

两段锁协议 2PL 与封锁粒度

✌️两段锁协议（2PL）

所有事务必须分两个阶段对数据项加锁和解锁：

  • ① 扩展阶段：在对任何数据进行读、写操作之前，首先要申请并获得对该数据的封锁
  • ② 收缩阶段：在释放一个封锁之后，事务不能再申请和获得任何其他封锁
  • ✅ 保证：若并发执行的所有事务均遵守两段锁协议，则对这些事务的任何并发调度策略都是可串行化的。
  • ❌ 代价：遵守两段锁协议的事务可能发生死锁。
  • 死锁的定义：多个用户申请不同封锁，由于申请者均拥有一部分封锁权，而又需等待其他用户拥有的部分封锁，而引起的永无休止的等待。

📏封锁粒度

封锁粒度是指被封锁数据对象的大小。在关系数据库中，封锁粒度有：

属性值 · 属性值集 · 元组 · 关系 · 某索引项（或整个索引）· 整个关系数据库 · 物理页（块）

粒度小并发性高
开销大

粒度大并发性低
开销小

口诀：粒度小 → 并发高、开销大；粒度大 → 并发低、开销小。综合平衡、合理选取最重要。

数据库的完整性

🧩三类完整性 ⭐

① 实体完整性

要求主键中的任一属性不能为空。空值是"不知道"或"无意义"的值。
原因：元组的区分依据主键值，主键取空就无法标明元组的存在

② 参照完整性

若 R 含与另一关系 S 的主键 PK 对应的属性组 FK，则 R 中每个元组在 FK 上的值必须是 S 中某个元组的 PK 值，或者为空值
合理性：外键只能引用 S 中真实存在的主键

③ 用户定义的完整性

针对某一具体数据库的约束条件，反映某一具体应用所涉及的数据必须满足的语义要求
前两类适用于任何关系型 DBMS，这一类是应用特有的

📐完整性约束条件

完整性约束条件是指对数据库中数据本身的某些语法或语义限制、数据之间的逻辑约束，以及数据变化时应遵守的规则。一般以谓词逻辑形式表示。

作用对象可以是关系、元组或属性三种。

静态约束（最重要的一类）

反映数据及其之间的固有逻辑特性，包括：

· 静态属性级约束（数据类型、格式、取值范围、空值等）

· 静态元组级约束

· 静态关系级约束（实体完整性、参照完整性、函数依赖约束、统计约束）

动态约束

数据变化应遵守的规则，反映数据库状态变迁的约束，包括：

· 动态属性级约束（修改属性定义时、修改属性值时）

· 动态元组级约束

· 动态关系级约束

💡 完整性控制机制两个功能：定义功能（提供定义约束条件的机制）＋ 检查功能（检查操作请求是否违背约束）。

按检查时机分：立即执行约束（语句执行完立即检查）／延迟执行约束（整个事务结束后再检查）。

触发器：比完整性约束功能强得多。完整性约束查出违反时仅给出提示；触发器不仅提示，还会自动进行某些操作以消除负面影响。

· 前面的事件 = 触发事件（一般是完整性约束条件的否定）

· 后面的事件 = 结果事件（一组用以消除不良影响的操作）

· 除完整性保护外，还有安全性保护功能

数据库的安全性

数据库系统的安全性在技术上依赖两种方式：一种是 DBMS 本身提供的用户身份识别、视图、使用权限控制和审计等管理措施；另一种是靠应用程序来实现对数据库访问的控制和管理。

🛡️DBMS 提供的五种安全措施

措施说明
用户标识和鉴别最外层的安全保护措施，可以使用用户账户、口令和随机数检验等方式
存取控制（数据授权）对用户进行授权，包括操作类型（查找、更新、删除等）和数据对象的权限
密码存储和传输对远程终端信息用密码传输
视图的保护通过视图的方式进行授权
审计使用一个专用文件或数据库，自动将用户对数据库的所有操作记录下来
  • 权限角色三类：数据库登录权限类 · 资源管理权限类 · DBA 权限类
  • 用户标识与鉴别的两种方式：口令认证 和 强身份认证（可结合数字证书、智能卡、指纹识别等）

访问控制粒度的四层次（由大到小）：数据库级 → 关系级 → 元组级 → 属性级

⚠️ 审计 ≠ 跟踪：

  • 跟踪——满足系统调试需要，记录往往只用于分析，不长久保存
  • 审计——一种安全检查措施，把运行状况和用户行为以日志形式记录并保存，作为稽查用户行为的证据

身份认证是事前防范，审计是事后监督。

备份与恢复技术 ⭐

💾备份的两种分类口径

按实现方式分

  • 物理备份（在操作系统层面对数据文件备份）→ 又分 冷备份 / 热备份
  • 逻辑备份（利用 DBMS 自带工具备份数据库内容）

按数据量分

  • 完全备份：将整个数据库中的数据备份
  • 增量备份：备份上一次备份（含完全/增量/差异备份）后发生变化的数据
  • 差异备份：备份上一次完全备份后发生变化的所有数据

一般一个备份周期 = 一个完全备份 + 多个增量或差异备份

❄️冷备份（静态备份）

将数据库正常关闭，在停止状态下把数据库文件全部复制下来。

  • 优点：非常快速（只需复制文件）；容易归档；容易恢复到某个时间点；能与归档方法结合做"最佳状态"恢复；低度维护、高度安全。
  • 缺点：单独使用时只能恢复到某一时间点；备份全过程数据库必须停下；磁盘空间有限时要复制到磁带，速度慢；不能按表或按用户恢复。
  • 教材原话：冷备份是数据库备份中最快和最安全的方法。

🔥热备份（动态备份）

利用备份软件，在数据库正常运行的状态下把数据文件备份下来。

  • 优点：可在表空间或数据库文件级备份、时间短；备份时数据库仍可使用；可达到秒级恢复；可对几乎所有数据库实体做恢复。
  • 缺点：不能出错，否则后果严重；若热备份不成功，所得结果不可用于时间点的恢复；难于维护，不允许"以失败告终"。
  • 逻辑备份：Oracle 用 exp/imp，Sybase 用 dump/load database。数据量大到 TB 级时力不从心，需结合物理备份。

日志文件与数据恢复 ⭐⭐

事务日志是针对数据库改变所做的记录，记录针对数据库的任何操作，并保存在独立文件中。事务一开始就处于记录状态，直到提交或回滚后才结束记录。每条记录的主要内容有：事务标识 · 操作类型 · 更新前的旧值（插入时为空）· 更新后的新值（删除时为空）。

⚠️ 先写日志原则（WAL）：写数据库和写日志是两个不同的操作，有可能在两个操作之间发生故障。为了安全，应该先写日志文件，再写数据库的修改。

🔧三种故障的恢复策略 ⭐⭐

故障类型恢复手段要点
事务故障UNDO由系统自动完成，对用户透明（不需要 DBA 参与）。步骤：反向扫描日志找该事务的更新操作 → 执行逆操作 → 直到读到事务开始标记
系统故障UNDO + REDO系统重启时自动完成。步骤：正向扫描日志 → 已提交的事务记入 Redo 队列；未完成的事务记入 Undo 队列 → 对 Undo 队列做撤销、对 Redo 队列做重做
介质故障（与病毒破坏）重装副本 + REDO① 装入最新的数据库后援副本，恢复到最近一次备份时的一致状态② 从故障点反向扫描日志，找出已提交事务记入 Redo 队列③ 从起始点正向扫描，按 Redo 队列重做已完成的任务

口诀：事务故障只 UNDO · 系统故障 UNDO+REDO · 介质故障重装+REDO

有检查点的恢复：检查点记录含"建立检查点时所有正在执行的事务清单"及各事务最近一条日志的地址。从最后一个检查点开始正向扫描 → 新开始的事务入 U 队列，已提交的事务从 U 移到 R 队列 → 对 U 做 Undo、对 R 做 Redo。

数据库性能优化

对集中式数据库的性能优化，可以从 硬件升级 · 数据库设计 · 索引优化策略 · 查询优化 四方面入手。

①硬件升级

  • 处理器：更高频率，或单处理器升级为多处理器
  • 内存：容量扩充 → 更多数据保存在缓冲区 → 减少磁盘 I/O
  • 磁盘子系统：换高速磁盘减少读盘等待；合理分布 I/O 到多个设备，减少资源竞争、提高并行能力
  • 网络：带宽升级

②数据库设计（反规范化）

规范化程度越高，冗余越少，但关系被不断拆解 → 频繁连接 → 连接最耗时，成为性能制约因素。因此反规范化可改善性能。

常用措施：

  • 将常用的计算属性（总计、最大值等）存储到实体中
  • 重新定义实体，减少外部属性或行数据的开支
  • 将关系水平或垂直分割，提升并行访问度

③索引优化策略

  • 选经常查询、不常更新的属性建索引——避免对经常更新的属性建索引
  • 一个关系上索引过多会影响 UPDATE / INSERT / DELETE 性能（更新时所有索引都要调整）
  • 分析每个重要查询的使用频率，优先优化用得最多的索引
  • 数据量非常小的关系不必建索引——关系扫描往往更快、消耗资源更少

④查询优化（最重要）

也称为应用程序优化，是数据库性能优化的最后一个环节，同时也是最重要的一个环节——查询语句构造不当，会使之前的优化功亏一篑。

SQL 优化策略：建立物化视图或尽可能减少多表查询；以不相干子查询替代相干子查询；只检索需要的属性；用带 IN 的条件子句等价替换 OR 子句；经常提交（COMMIT）以尽早释放锁。

1设关系模式 R(A,B,C,D)，函数依赖集 F = {A→B, C→D}，则 R 的候选键是：
AAC
BAB
CCD
DBC
A 的入度为 0（没有任何依赖能推出 A）、C 的入度为 0 —— 所以 A、C 必须同时出现在候选键里。验证可达性：A→B 得 B，C→D 得 D，AC 能推出全部四个属性。所以 AC 是候选键（B、D 都不是，因为它们入度不为 0）。⚠️ 单属性 A 只能推出 A、B，推不到 C、D；单属性 C 同理。

2若关系模式 R 属于 3NF，则它一定属于：
A2NF
B4NF
CBCNF
D1NF
范式链是递进包含关系：1NF ⊂ 2NF ⊂ 3NF ⊂ BCNF ⊂ 4NF。所以属于 3NF 一定属于 2NF 也一定属于 1NF。反方向都不成立：属于 4NF 不一定属于 BCNF；属于 BCNF 一定属于 3NF（但 3NF 不一定 BCNF）。记忆：链是单向塔，越高条件越严，向上包含。
第5章 · 5.2 范式链总览
3非主属性对候选键的传递依赖，是下列哪个范式的判定依据：
A3NF
B1NF
C2NF
DBCNF
2NF 判据：非主属性完全依赖于候选键（不能只依赖候选键的一部分）——解决部分依赖问题。3NF 判据：非主属性不传递依赖于候选键（即不能出现 A→B 且 B→C 且 A→C）——解决传递依赖问题。BCNF 更严：要求所有属性（含主属性）对候选键都完全依赖。口诀："2NF 拆部分，3NF 拆传递，BCNF 全都要。"
第5章 · 5.2 3NF 详解
4事务的 ACID 中，"一致性"（Consistency）指的是：
A事务执行前后，数据库都必须处于满足所有完整性约束的正确状态
B事务一旦提交就不能回滚
C多个事务并发执行互不干扰
D事务的各个操作都不能中途失败
ACID 四性：原子性 A（Atomicity，不可分割，全做或全不做）｜一致性 C（Consistency，执行前后都满足完整性约束）｜隔离性 I（Isolation，并发事务互不干扰）｜持久性 D（Durability，提交后永久保存、崩溃不丢）。⚠️ 一致性不是独立机制，它是 A+I+完整约束共同保证的结果。
第5章 · 5.3 事务的 ACID 特性
5并发事务带来的三类问题不包括：
A死锁
B丢失修改
C不可重复读
D脏读
并发三类问题（标准表述）：丢失修改（Lost Update）、不可重复读（Non-repeatable Read）、读"脏"数据（Dirty Read）。死锁不属于并发一致性问题的标准三类，它属于事务的并发控制要单独处理的问题（防死锁）。四者区分：丢失修改 = 两个写互相覆盖；不可重复读 = 同一事务两次读同一行值不同；脏读 = 读到了别的事务未提交（之后会回滚）的数据。
第5章 · 5.3 并发带来的三类问题
6三级封锁协议中，"一级封锁协议"的要求是：
A事务 T 在修改数据 R 之前必须对 R 加 X 锁，直到事务结束才释放
B事务 T 在读取数据 R 之前必须对 R 加 S 锁，直到事务结束才释放
C读写之前都必须加 S 锁，修改前升级为 X 锁，事务结束释放
D不需要任何锁
一级封锁：只防丢失修改——修改前加 X 锁（写锁），事务结束才释放（不是"读完就放"）。二级封锁：一级 + 读前加 S 锁（直到结束才释放）——防丢失修改 + 脏读。三级封锁：一级 + 读前加 S 锁（立即释放）+ 写前加 X 锁（立即释放）——防丢失修改 + 不可重复读，仍允许脏读。⚠️ 三级协议不能防止脏读。
