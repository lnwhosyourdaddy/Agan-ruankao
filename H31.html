第 31 小时 · 软件实现与测试（一）· 测试原则与黑盒白盒方法

第 14 章真题占比 2.9%（16/557）。本学时覆盖 14.1 软件实现 + 14.2 测试概述与八原则
+ 14.3 测试分类（黑盒 vs 白盒 / 逻辑覆盖六级）。
测试八原则是必考辨识，白盒逻辑覆盖六级是本章最经典的排序题。

考情定位

四块必拿：① 测试八原则（尤其 ① 只能证明有错、④ 缺陷集群性 80/20、⑤ 杀虫剂悖论要更新用例）；② 白盒覆盖六级排序（语句 → 判定 → 条件 → 判定/条件 → 条件组合 → 路径）；③ 黑盒 vs 白盒（黑盒按需求规格不看结构，白盒按内部逻辑）；④ 黑盒五大方法（等价类 · 边界值 · 因果图/判定表 · 正交 · 场景法）。

记忆口诀

八原则：只能证明有错 ｜ 穷尽不可能 ｜ 尽早介入 ｜ 缺陷集群（80/20） ｜ 杀虫剂悖论（要更新用例） ｜ 依赖测试背景 ｜ 无缺陷谬论 ｜ 上下文相关。
覆盖六级（弱→强）：语句 → 判定 → 条件 → 判定/条件 → 条件组合 → 路径。
黑盒五法：等价类 · 边界值 · 因果图/判定表 · 正交试验 · 场景法。
静态 vs 动态：静态不跑程序（评审/扫描），动态跑程序比输出。

易错陷阱

路径覆盖最强但实践中常不可达（循环导致路径爆炸），常用条件组合覆盖折中。
杀虫剂悖论的对策是"更新用例"，不是"增加执行频率"。
边界值要测"等于 / 刚刚大于 / 刚刚小于"三类，只测边界值本身是不够的。

论文可用句

在测试策略上，我按测试八原则组织工作：基于缺陷集群性（80/20）将 60% 的测试资源投给订单与计费这两个高风险模块；针对"杀虫剂悖论"，每轮迭代都对用例做一次评审更新，并引入探索性测试补充脚本化用例的盲区。白盒侧对核心算法要求达到条件组合覆盖（路径覆盖在含循环的场景不可达），黑盒侧用等价类 + 边界值设计用例，重点覆盖金额边界与并发边界，最终上线后生产环境缺陷密度为 0.8 个/千行。

第 14 章知识骨架

14.1 软件实现 · 程序设计方法与风格

🛠️三种程序设计方法

① 结构化程序设计

自顶向下、逐步求精；单入口单出口；三种基本控制结构 = 顺序 · 选择 · 循环（Bohm & Jacopini 证明）；静态结构与动态执行一致

② 面向对象程序设计 OOP

OOA→OOD→OOP 链条末端——用 OO 语言把 OOD 模型书写下来；支持类/对象/继承/多态/消息 → 提高可靠性可维护性可复用性

③ 可视化程序设计 VP

事件驱动；基本概念 = 表单 · 部件 · 属性 · 事件 · 方法；像搭积木（Eclipse/VS）

✒️语言选择 + 设计风格 + 重用

  • 语言选择：理想模块化机制 · 可读性好的控制/数据结构 · 编译程序能多发现错误 · 独立编译机制；还要考虑用户要求/工具/规模/程序员知识/可移植性/应用领域
  • 程序设计风格四维度：可理解性（有意义标识符/详细注解）· 可复用性（高内聚/接口与实现分开/不用全局变量）· 可扩展性（封装/多态）· 健壮性（预防误操作/参数合法性检查/先测试后优化）
  • 编码规范：命名/格式化/注释/函数长度/错误处理/冗余代码——降维护成本、改善可读性、提高协作效率
  • 代码重用三层次：代码重用 · 设计结果重用 · 分析结果重用；方法 = 用函数/用对象/用模块/用类/利用算法

14.2 测试概述 · 定义与目的 ⭐

🎯IEEE 定义 + 三个误解

IEEE 定义：使用人工或自动手段来运行或测量软件系统的过程——检验是否满足规定需求，找出与预期结果的差异

⚡ 三个错误理解：① 测试目标是"软件能正确完成预期功能" ② 测试 = 证明软件不存在错误 ③ 测试 = 建立"软件做了该做的"——全是本末倒置！

正确姿势：假设程序中存在隐藏错误，通过测试找到尽可能多的错误——逆向思维甚至发散思维

💡 测试发展趋势：测试工作前移（测需求/测设计）· 角色融合 · 独立测试部门 · 测试外包全球化。

🔍测试对象与目的（三视角）

  • 对象：源程序/目标代码 + 各阶段文档（需求/概要/详细设计）+ 配置数据——不只是代码！
  • 用户视角：发现隐藏错误缺陷 → 考虑是否接受产品
  • 开发者视角：表明实现了用户要求
  • 测试人员视角：发现错误 · 预测错误 · 提供可靠性依据 · 做出评价

⚡ 高频原话：测试的目的是发现错误，而不是证明程序无错；好的测试用例 = 能发现尚未发现的错误的用例。

测试八原则 ⭐⭐（必考辨识）

📜教材版原则（精选八条）

①用例必含预期输出——输入描述 + 正确输出描述两部分

②程序员避免测试自己的程序（"破坏性"视角缺失）

③开发组织不测自己开发的软件——第三方客观独立

④耐心细心检查每个测试结果

⑤用例不仅基于有效输入，还要基于无效和意外输入

⑥避免重新设计测试用例——保留与复用

⑦计划测试不应默认假定不会发现错误

⑧不要穷举测试——以最少用例达最大覆盖率

⑨尽早执行、贯穿生命周期（需求阶段缺陷维修成本最低）

⑩追溯到需求——满足用户需求更重要

⚡ 冲刺口径补充版：尽早持续测试 · 用例含预期输出 · 程序员不测自己 · 完全测试不可能（风险优先）· 追溯需求 · 缺陷集群（二八：80% 缺陷在 20% 模块）· 杀虫剂悖论（用例要更新）· 测试是有计划的活动——两套都认识，选择题看选项。

14.3 测试分类 · 黑盒与白盒 ⭐⭐⭐

⬛黑盒测试（功能测试/数据驱动）

把程序看作不能打开的黑盒——完全不考虑内部结构，在程序接口测试；从用户角度检查输入输出对应关系；各阶段都发挥作用，系统/确认测试中不可替代

能发现：功能错误/遗漏 · 输入输出错误 · 数据结构与外部访问错误 · 初始化与终止错误

⭐ 六种用例设计方法：等价类划分 · 边界值分析 · 错误推测 · 因果图 · 判定表驱动 · 正交试验（+功能图/场景法）

边界值分析：错误多发生在边界——重点测 min、min+1、正常值、max−1、max 五点。

⬜白盒测试（结构测试/逻辑驱动）

"盒子可视"——清楚内部逻辑结构；对逻辑路径测试（穷举路径不可能——独立路径数天文数字）；用于高可靠性领域（军工/航天/工控）

方法：代码检查 · 静态结构分析 · 逻辑覆盖 · 基本路径测试 · 域测试 · 符号测试 · 程序变异

四原则：所有独立路径至少测一次 · 逻辑值真伪都测 · 检查内部数据结构有效性 · 循环在上下边界运行

💡 灰盒 = 两者之间：多用于集成测试阶段——关注输入输出正确性，也通过标志/事件/现象关注内部运行状态。

白盒逻辑覆盖六级（由弱到强）⭐⭐⭐

📶发现错误能力递增 · 年年考排序

① 语句覆盖（最弱）

每条语句至少执行一次

② 判定覆盖（分支）

每个判定的每个分支至少执行一次

③ 条件覆盖

每个判定中每个条件取到各种可能值

④ 判定/条件覆盖

同时满足判定覆盖与条件覆盖

⑤ 条件组合覆盖

每个判定中条件的各种组合至少出现一次

⑥ 修改条件判断覆盖 / 路径覆盖（最强）

MCDC：条件可独立影响判定结果；路径覆盖 = 所有路径都执行——用例数爆炸

语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径

💡 白盒"三步法"：① 按功能人工设计基本用例 → ② 统计覆盖率补未覆盖单位 → ③ 自动生成大量用例捕捉"程序员未处理的特殊输入"。条件覆盖单独满足时不一定满足判定覆盖（条件真假取到了、分支可能没走全）。

静态测试 / 动态测试 / 自动化测试

🧐静态测试（不运行程序）

不运行被测程序——分析/检查语法、结构、过程、接口；对象含需求/设计文档 + 源程序

包括：代码检查（走查/桌面检查/代码审查）· 静态结构分析 · 代码质量度量

能发现：不匹配参数 · 不适当嵌套 · 未使用变量 · 空指针引用 · 可疑计算

⚡ 代码检查比动态测试更有效率——能发现 30%~70% 的逻辑设计和编码缺陷；应在编译和动态测试之前进行

💡 优点：发现缺陷早、降返工成本、发现概率高；缺点：耗时长、技术要求高。

🏃动态测试 + 自动化测试

  • 动态测试：运行被测程序，检查运行结果与预期差异——三部分 = 构造测试用例 · 执行程序 · 分析输出
  • 自动化测试：人为驱动 → 机器执行（预设正常与异常条件、评估结果）

适用 / 不适用

✅ 回归 · 性能 · 大量重复；❌ 探索性 · 一次性 · 频繁变更

三层工具链

单元（JUnit）→ 接口（Postman）→ UI（Selenium）；与 CI/CD 集成

A测试只能证明有错，不能证明没错（穷尽测试是不可能的）
B缺陷集群性（80/20 原则）
C杀虫剂悖论
D测试活动依赖于测试背景
测试八原则（教材标准表述）：① 测试显示缺陷的存在（只能证明有错，不能证明没错）｜② 穷尽测试是不可能的（所以要风险与优先级驱动）｜③ 测试尽早介入（缺陷越晚发现修复成本越高）｜④ 缺陷集群性（约 80% 缺陷集中在 20% 模块）｜⑤ 杀虫剂悖论（同一批用例反复执行会"免疫"，要定期评审和更新用例）｜⑥ 测试活动依赖于测试背景（安全关键系统 vs 电商，测试强度不同）｜⑦ 不存在缺陷的谬论（系统无法使用 ≠ 无缺陷）｜⑧ 测试是上下文相关的。⚠️ 最常考的是 ①④（二八定律）和 ⑤（要更新用例）。
第14章 · 14.2 测试八原则
2白盒测试的逻辑覆盖中，覆盖强度由弱到强的正确顺序是：
A语句 → 判定 → 条件 → 判定/条件 → 条件组合 → 路径
B路径 → 条件组合 → 判定/条件 → 条件 → 判定 → 语句
C语句 → 条件 → 判定 → 路径 → 条件组合
D判定 → 语句 → 条件 → 条件组合 → 路径
白盒逻辑覆盖六级（弱 → 强）：① 语句覆盖（每条语句至少执行一次，最弱）→ ② 判定覆盖 / 分支覆盖（每个判定的真假分支各执行一次）→ ③ 条件覆盖（每个条件的所有可能取值至少一次）→ ④ 判定/条件覆盖（同时满足②③）→ ⑤ 条件组合覆盖（每个判定内各条件的所有取值组合都出现）→ ⑥ 路径覆盖（覆盖程序中所有可能的执行路径，最强）。⚠️ 路径覆盖在实践中往往不可达（循环导致路径数爆炸），所以常用条件组合覆盖折中。
第14章 · 14.3 白盒逻辑覆盖六级
3关于黑盒测试与白盒测试，下列说法正确的是：
A黑盒关注功能规格（不考虑内部结构）；白盒关注程序内部逻辑结构
B黑盒看代码，白盒看需求
C两者都只能用于单元测试
D黑盒测试不需要测试用例
黑盒测试（功能测试）：把被测对象当作"黑盒子"，只看输入与输出是否符合需求规格，不关心内部实现。常用方法：等价类划分 · 边界值分析 · 因果图/判定表 · 正交试验 · 场景法。白盒测试（结构测试）：看代码内部逻辑，按程序结构设计用例（逻辑覆盖、路径覆盖、循环覆盖）。⚠️ 黑盒 ≠ 不看需求（它恰恰是按需求测），白盒 ≠ 不看需求（它仍需知道"正确结果是什么"）。
第14章 · 14.3 测试分类 · 黑盒与白盒
4等价类划分与边界值分析中，边界值分析重点测试的是：
A输入域的边界（正好等于、刚刚大于、刚刚小于边界的值）
B输入域的中间值
C随机取值
D所有可能取值
边界值分析是对等价类划分的补充：经验表明大量缺陷发生在输入域的边界上而非中间。所以对每个边界，应取正好等于边界、刚刚大于边界、刚刚小于边界三类值（如范围 [1,100]，则测 0/1/2 与 99/100/101）。⚠️ 两者常结合使用：先划分等价类，再对每个类的边界取边界值。
第14章 · 14.3 黑盒测试方法
5"杀虫剂悖论"指的是：
A同一批测试用例反复执行会发现越来越少的缺陷，需要定期评审和更新用例
B农药残留影响软件质量
C测试人员会疲劳
D缺陷会自动消失
杀虫剂悖论（Pesticide Paradox）：同一批测试用例反复执行，就像反复使用同一种农药——虫子会产生抗药性，用例会"免疫"，发现新缺陷的能力逐渐下降。应对：定期评审、修正和补充测试用例，引入新的测试角度（如探索性测试、变异测试）。这是八原则里最容易被考"该怎么办"的一条。

A静态测试不运行程序（评审/静态分析）；动态测试运行程序并比对实际输出与预期
B静态测试更快，动态测试更慢
C静态测试只用于文档
D两者都需要运行程序
静态测试：不运行被测程序，通过人工评审（需求/设计/代码评审、走查、审查）或静态分析工具（代码规范检查、复杂度度量、缺陷模式扫描）发现问题——能早期发现、成本低。动态测试：实际运行程序，输入测试数据并比对实际输出与预期结果。⚠️ 常见的代码审查、SonarQube 扫描都属于静态测试。
