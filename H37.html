第 37 小时 · 移动应用系统分析与设计 · 架构演进与开发方式选型

第 18 章移动应用是案例题的常客——"给场景选开发方式""指出设计问题"几乎年年出现。
本学时覆盖 **18.1 平台与环境 + 18.3 MVC→MVP→MVVM 演进 + 18.4 五种开发方式选型
+ 18.5 无代码/低代码 + 移动端约束与测试**。

考情定位

四块必拿：① MVC / MVP / MVVM 的递进关系（核心是"View 与 Model 耦合度递减"）；② 五种开发方式选型（原生 / 跨平台 / 混合 / Web / 低代码，按"性能 vs 成本"权衡）；③ 移动端四大约束（资源受限 · 移动性强 · 设备碎片化 · 交互受限）；④ 移动端测试的特殊关注点（碎片化 · 弱网 · 耗电 · 权限合规）。

记忆口诀

架构演进：MVC 直接连（View 可读 Model）｜MVP 中间站（Presenter 中转，解耦）｜MVVM 自动传（数据双向绑定）。
五种开发方式：原生性能最好成本最高 ｜ 跨平台性能接近原生成本低 ｜ 混合开发快性能差 ｜ Web App零成本性能最差 ｜ 低代码非专业自助、适合简单应用。
移动端四约束：资源受限 · 移动性强 · 设备碎片化 · 交互受限。
"被动视图"三收益：可测试 · 可复用 · 可跨平台。

易错陷阱

MVVM 里 View 不直接访问 Model（由 ViewModel 持有并通过绑定同步）——这是与 MVC 最本质的区别。
混合应用（Hybrid）不是"最佳平衡"——它开发快但性能差（WebView 瓶颈）；要"性能+成本"平衡应该选跨平台。
低代码 ≠ 无代码——低代码留了"代码逃生舱"（可扩展），无代码完全没有。

论文可用句

在移动端架构上，我采用 MVVM 而非 MVC：把业务规则下沉到 ViewModel，UI 层保持"被动视图"仅负责渲染与事件转发。ViewModel 是不依赖 Android UI 框架的纯逻辑对象，因此可在 JVM 上直接跑单元测试，核心规则的单测覆盖率从 22% 提升到 78%，回归验证周期由 1 天缩短到 2 小时，同时同一套业务逻辑在 Android 与 iOS 双端复用，减少了约 30% 的重复代码。

18.3 架构演进 · MVC → MVP → MVVM ⭐⭐⭐

🔄演进主线：单体 → MVC → MVP → MVVM → 组件化 →（后端）微服务化

MVC

Model + View + Controller
⚠️ View 与 Model 可直接交互——耦合较重；Controller 只做薄控制

MVP

Model + View + Presenter
View 与 Model 完全解耦（Presenter 中介）；逻辑在 Presenter；缺点 = 接口多

MVVM

Model + View + ViewModel
⭐ 双向数据绑定——数据变视图自动变；解耦最彻底；代表 = Vue/Angular

⚡ 高频辨析：MVC 中 View 可访问 Model（耦合重）；MVP 通过 Presenter 解耦；MVVM 双向绑定自动同步——演进动机 = 不断降低 View 与 Model 的耦合。

💡 移动端分层：表现层（UI）→ 业务层 → 数据层（本地缓存/SQLite + 网络）→ 基础设施（网络/图片/推送/埋点）；模块化/组件化便于复用与并行开发；后端随之微服务化。

18.4 五种开发方式对比与选型 ⭐⭐⭐（案例必考）

📱五种方式 · 六维对比

方式说明性能硬件能力开发效率发布
Native 原生平台原生语言（Swift/Kotlin）最好全部低（双端重复开发）需审核

业务型 App

低频轻应用

18.5 无代码/低代码开发 ⭐⭐（新型考点）

🧱定义 + 优缺点

定义：可视化拖拽 + 配置，无需或少量写代码即可构建应用（低代码 = 少量代码扩展）

优点

门槛低 · 速度快 · 业务人员可参与 · 降低对专业开发依赖

缺点

灵活性受限 · 复杂逻辑难实现 · 平台锁定（vendor lock-in） · 性能与扩展受限 · 可维护性风险

🎯适用边界 + 发布运维

适用 ✅

长尾业务 · 内部工具 · 原型验证 · 简单流程类应用

不适用 ❌

核心业务系统 · 高性能/高定制场景

发布与运维：灰度发布 · 热修复（不重新发版修 bug）· 版本管理（强制/可选更新）· 崩溃监控（Bugly/Firebase）· APM

主流：低代码平台（宜搭/微搭/简道云等）· 无代码测试平台

⚡ 案例锚：问"能否用低代码做核心系统"——答适用边界：长尾可以，核心不行（平台锁定 + 性能受限）。

五种移动开发方式选型（案例必考）：① 原生（Native）——性能最好、体验最佳，但要写两套代码、成本最高、周期最长；② 跨平台（Cross-Platform，如 Flutter/Dart、React Native/JS）——一套代码两端运行，性能接近原生、开发快、成本低，是"性能 + 成本"的最佳平衡（本题答案）；③ 混合（Hybrid，WebView 嵌入原生壳）——开发快但性能差、体验差（有 WebView 性能瓶颈与"白屏"问题）；④ Web App（响应式网页）——免安装、跨平台零成本，但性能最差、离线能力弱、无法访问完整原生能力；⑤ 无代码/低代码——业务人员自助开发、极快，但能力受限、适合简单内部应用。

3关于无代码（No-Code）与低代码（Low-Code）开发，正确的是：
A低代码是可视化拖拽 + 少量代码扩展，比无代码更能满足个性化需求；无代码完全不需要写代码

B为了让代码更短

"被动视图（Passive View）"原则：UI 层只负责渲染数据 + 转发用户事件，不写业务判断。三个收益：① 可测试——Presenter/ViewModel 是纯逻辑对象，不依赖 UI 框架，能在 JVM 上直接跑单元测试（这是移动开发最痛的一个点）；② 可复用——同一套逻辑可复用于不同页面甚至不同平台；③ 可跨平台——业务逻辑与平台 UI 解耦，便于跨平台共享。⚠️ 这是从 MVC 到 MVP/MVVM 演进的根本动因。
