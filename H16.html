第 16 小时 · 软件工程（三）· UML 与形式化方法

本学时覆盖 7.7 UML + 7.8 形式化方法，并附全章易错辨析、速记卡与自测清单。
UML 是案例题与论文的通用语言，这一学时会直接影响下午两科的发挥。

考情定位

三块必拿：① 用例三关系（include / extend / 泛化，箭头方向是最大陷阱）；② 十四种图分 5 类（用例·静态·行为·交互·实现）；③ 四类事物 + 四种关系。

易错陷阱

include 箭头：基础 → 被包含；extend 箭头：扩展 → 基础（方向相反）。
题干出现"每次/必然/一定" → include；"可选/如果…才/特定条件" → extend。这是本章出错率最高的一道题。

7.7 统一建模语言 UML · 它的结构由三部分组成

🏛️UML 结构的三个部分

① 构造块

三种：事物（thing）、关系（relationship）、图（diagram）

② 公共机制

四种：规格说明、修饰、公共分类、扩展机制

③ 规则

五种：命名、范围、可见性、完整性、执行

事物是 UML 的重要组成部分，关系把事物紧密联系在一起，图是多个相互关联的事物的集合。

⚙️公共机制 · 四种

规格说明 — 事物语义的细节描述，它是模型真正的核心

修饰 — UML 为每个事物设置一个简单记号，还可通过修饰表达更多信息

公共分类 — 两组：类与对象（类＝概念，对象＝具体实体）；接口与实现（接口＝契约，实现＝具体内容）

扩展机制 — 三种：约束（扩展构造块语义，允许增加新规则或修改现有规则）、构造型（扩展 UML 词汇，定义新的构造块）、标记值（扩展构造块特性，创建新的特殊信息扩展规格说明）

📏规则 · 五种

规则是构造块如何放在一起的规定：

  • 命名 — 为构造块命名
  • 范围 — 赋予名称特定含义的上下文
  • 可见性 — 怎样使用或看见名字
  • 完整性 — 事物如何正确、一致地相互联系
  • 执行 — 运行或模拟动态模型的含义

🎯UML 的定义（教材）

定义良好、易于表达、功能强大且普遍适用的建模语言。

它的作用域不限于支持面向对象分析和面向对象设计，还支持从需求分析开始的软件开发的全过程。

三个数字：构造块 3（事物/关系/图）｜公共机制 4（规格说明/修饰/公共分类/扩展）｜规则 5（命名/范围/可见性/完整性/执行）

UML 的五个系统视图 ⭐

UML 对系统架构的定义是：系统的组织结构，包括系统分解的组成部分，以及它们的关联性、交互机制和指导原则

逻辑视图

Logical View
= 设计视图

表示设计模型中在架构方面具有重要意义的部分，即类、子系统、包和用例实现的子集。

进程视图

Process View

把可执行线程和进程作为活动类建模，是逻辑视图的一次执行实例，描述并发与同步结构。

实现视图

Implementation View

对组成基于系统的物理代码的文件和构件进行建模。

部署视图

Deployment View

把构件部署到一组物理节点上，表示软件到硬件的映射和分布结构。

用例视图

Use Case View

最基本的需求分析模型。

五视图速记：逻辑看类包，进程看并发，实现看文件，部署看硬件，用例看需求

⚠️ 易混点：

  • 逻辑视图又叫设计视图（一个视图两个名）
  • 进程视图是逻辑视图的一次执行实例——它和逻辑视图是"实例 vs 结构"的关系，不是并列无关

💡 教材还提到：UML 允许在一定的阶段隐藏模型的某些元素、遗漏某些元素，以及不保证模型的完整性，但模型要逐步地达到完整和一致。

UML 的四类事物 与 四种关系 ⭐

🧱四类事物（建模元素）

① 结构事物 · Structural Things（最静态）

有 7 种：类、接口、协作、用例、活动类、构件、节点

  • 类：描述具有相同属性、方法、关系和语义的对象的集合，一个类实现一个或多个接口
  • 接口：类或构件提供特定服务的一组操作的集合，描述对外可见的动作
  • 协作：定义交互的操作，一些角色和其他事物一起工作，这些动作比事物的总和要大
  • 活动类：对象有一个或多个进程或线程，行为与其他事物同时存在
  • 构件：物理上或可替换的系统部分，实现了一个接口集合；节点：运行时存在的物理元素，代表可计算资源

② 行为事物 · Behavioral Things（动态部分）

两种：交互（一组对象之间为达到特定目的而进行的一系列消息交换）和状态机（由一系列对象的状态组成）。

③ 分组事物 · Grouping Things

只有一种：包。包是一种将有组织的元素分组的机制。⚠️ 与构件不同的是，包纯粹是概念上的事物，只存在于开发阶段，而构件可以存在于系统运行阶段。

④ 注释事物 · Annotational Things

UML 模型的解释部分。

🔗四种关系 · 由弱到强

依赖最弱

关联＜

泛化＜

实现最强

关系画法语义
依赖虚线箭头一个事物发生变化会影响另一个事物的语义（最弱，临时性）
关联实线一组对象之间连接的结构关系（可双向/单向，带多重度）
聚合空心菱形整体-部分，部分可独立存在
组合实心菱形整体-部分，同生共死
泛化空心三角实线一般化和特殊化的关系，子可替换父（继承）
实现空心三角虚线一个类指定了由另一个类保证执行的契约（类实现接口）

口诀：依赖 < 关联 < 泛化 < 实现；空心菱形能分开（聚合），实心菱形死一起（组合）

⚠️ 注意：教材的"四种关系"是依赖、关联、泛化、实现；而聚合和组合是"关联"的两种特殊形式。考试如果问"UML 有几种关系"，标准答案是4 种；如果问"关联有哪些变体"，才答聚合与组合。

UML 的十四种图 · 三分类是必考 ⭐

🏗️结构图（静态）· 7 种

① 类图 — 类、接口、协作及关系，静态设计视图；最常见

② 对象图 — 一组对象及关系，类图中事物的静态快照

③ 构件图 — 封装的类和接口、端口，静态设计实现视图；类图的变体

④ 组合结构图 — 结构化类的内部结构

⑤ 部署图 — 运行时处理节点及其中构件的配置，静态部署视图

⑥ 制品图 — 系统的物理结构（文件、数据库等），常与部署图一起用

⑦ 包图 — 模型分解的组织单元及依赖关系

🎬行为图（动态）· 3 种

① 用例图 — 一组用例、参与者及关系，给出系统的静态用例视图；组织和建模系统行为时非常重要

② 状态图 — 描述一个状态机，由状态、转移、事件和活动组成，给出对象的动态视图；对反应式系统建模特别有用

③ 活动图 — 将进程或计算结构展示为控制流和数据流，强调对象间的控制流程

💬交互图 · 4 种

① 顺序图（序列图）— 强调消息的时间次序

② 通信图（协作图）— 强调收发消息对象/参与者的组织结构

③ 定时图（计时图）— 强调消息跨越不同对象的实际时间，而不仅是相对顺序

④ 交互概览图 — 活动图和顺序图的混合物

⚠️ 高频陷阱 1：用例图属于"行为图"，不属于结构图！很多人一看它画的是静态视图就归错了。

⚠️ 高频陷阱 2：顺序图和通信图属于"交互图"，是行为图的进一步细分，不要和用例图混在一个筐里。

口诀：结构七图（类、对象、构件、组合结构、部署、制品、包）

行为三图（用例、状态、活动）

交互四图（顺序、通信、定时、交互概览）

用例三关系 · 最容易错的送分题 ⭐⭐

包含 include

<<include>>

基础用例必定执行被包含的用例。

箭头方向：基础用例 → 被包含用例

例："用户下单" 必定包含 "用户登录"——不登录就下不了单，这是必选的。

扩展 extend

<<extend>>

条件触发时才执行扩展用例。

箭头方向：扩展用例 → 基础用例

（注意方向与 include 相反！）

例："用户下单" 在用优惠券时才扩展出 "使用优惠券"——不用券就不执行，这是可选的。

泛化 generalization

 

父子用例，子继承父。

箭头方向：子用例 → 父用例

例："在线支付" 泛化出 "微信支付"、"支付宝支付"——它们是父子关系，子用例可以替换父用例。

最强辨析：包含 = 必须做；扩展 = 可能做（条件触发）。

题干出现"每次都要""必然""一定" → include；出现"可选""如果…才""特定条件" → extend。

⚠️ 箭头方向是最大陷阱：

include 是"基础 → 被包含"

extend 是"扩展 → 基础"

两个方向相反，画图题最爱考。

UML 各图适用场景速查

图用来描述归类典型题干关键词
用例图系统功能需求、参与者与用例行为图"谁用系统" "系统能做什么"
类图静态结构（类、属性、方法、关系）结构图"类的属性与方法" "类之间的关系"
顺序图按时间顺序的对象交互（强调时序）交互图"消息的先后顺序" "某对象在某时刻做什么"
通信图对象交互（强调结构关系）交互图"对象之间如何连接"
状态图对象生命周期的状态迁移行为图"状态变化" "事件触发" "反应式系统"
活动图业务流程、工作流（类流程图，支持并发）行为图"业务流程" "工作流" "并行处理"
构件图物理构件与依赖结构图"软件构件" "接口与端口"
部署图硬件拓扑与软件部署结构图"服务器节点" "软硬件映射"

顺序图 vs 通信图

两者表达类似的基本概念，但强调点不同：

  • 顺序图强调时序
  • 通信图强调组织结构

在 UML 1.X 中，通信图称为协作图。

状态图 vs 活动图

两者都是行为图，都描述动态视图，但：

  • 状态图关注对象的状态迁移
  • 活动图关注控制流和数据流

活动图对功能建模和业务流程建模特别重要。

案例题怎么选图

题干说"描述业务流程" → 活动图

题干说"描述对象状态变化" → 状态图

题干说"描述消息交互顺序" → 顺序图

题干说"描述系统与外部角色" → 用例图

7.8 软件形式化方法 · 五分类与优缺点

∑定义

形式化方法是建立在严格数学基础上、具有精确数学语义的开发方法。

广义

软件开发过程中分析、设计和实现的系统工程方法

狭义

软件规格和验证的方法

⚖️优缺点

✓ 优点：能够数学地表述和研究应用问题及其软件实现；无歧义、可验证/证明。

✗ 缺点：要求开发人员具备良好的数学基础；大型应用问题的规格说明往往过于细节化，难于为用户和软件设计人员所理解；门槛高、代价大。

📈两个改善实用性的方向

① 形式化方法与图形语言机制相结合 —— 为图形语言机制赋予形式化的语法和语义，兼具图形表示的直观简洁与形式化方法的严谨精确。

② 用 CASE 工具支持形式化软件开发 —— 不仅简化描述工作，还可利用自动证明技术帮助验证软件的数学性质。

🗂️形式化方法的五种分类

  • 面向模型：代表：Z、VDM　—— 用集合/序列等数学结构描述状态
  • 代数方法：代表：OBJ、Larch　—— 用代数公理描述抽象数据类型
  • 进程代数：代表：CSP、CCS、π演算　—— 描述并发与通信
  • 基于逻辑：代表：时序逻辑、一阶逻辑　—— 用逻辑公式规约与证明
  • 网络模型：代表：Petri 网　—— 图形化＋数学，适合并发/分布式

口诀：模型 Z/VDM，代数 OBJ/Larch，进程 CSP/CCS，逻辑时序/一阶，网络 Petri

适用：安全关键 / 高可靠系统（航空航天、轨道交通）

净室软件工程 CSE 与 程序验证

🧪净室软件工程 CSE

软件开发的一种形式化方法，可以开发较高质量的软件。

  • 使用盒结构归约进行分析和建模
  • 将正确性验证作为发现和排除错误的主要机制
  • 使用统计测试来获取认证软件可靠性所需要的信息
  • 理论基础：函数理论 + 抽样理论
  • 四个技术手段：① 统计过程控制下的增量式开发　② 基于函数的规范、设计　③ 正确性验证（CSE 的核心）　④ 统计测试和软件认证

三种抽象层次（按函数理论）：

规范从外部行为视图（黑盒）开始 → 转化为状态机视图（状态盒） → 最后由过程视图（明盒）实现

盒结构基于对象，支持信息隐藏、接口与实现分离。

⚔️程序验证 · 动态方法 vs 静态方法

动态方法

需要将源码编译为可执行文件，再运行软件，通过特定输入考察运行结果。

代表：软件测试（手动测试、自动化测试）

✓ 效率高、错误定位准确

✗ 要求有能运行的环境；不能覆盖所有输入和全部执行路径，只能证明已覆盖部分没问题

静态方法

基于程序源代码分析，无须编译运行，应用场景更广泛。

代表：静态分析、符号执行、定理证明、模型检测

应用门槛较高，一般用于对程序正确性要求较高的场景。

  • 静态分析 Static Analysis：比较轻量级，适用于大规模代码；问题是较高比例的误报，需要逐一人工排查，耗费大量人力。代表引擎：Coverity。
  • 符号执行 Symbolic Execution：可看作更准确的测试方法。用符号值静态执行程序，积累路径条件，再对路径条件做约束求解，判断目标位置的可达性。因需要约束求解且对循环不友好，难以大规模应用。经典工具：KLEE（已加入 LLVM 官方项目列表）。
  • 定理证明 Theorem Proving：用高阶逻辑 HOL 对程序及其性质建模，再用机器辅助证明一步步证明。主要缺陷是自动化程度较低，需要大量专业人力编写证明代码，对快速更新迭代不友好。典型工具：Coq（2014 获 ACM 软件系统奖）；用定理证明验证的 C 编译工具链 CompCert（2021 获 ACM 软件系统奖）。

#易混概念正确区分
1螺旋 vs 原型/演化螺旋 = 含风险分析的迭代；原型/演化 = 仅获取需求，无风险分析
2聚合 vs 组合聚合 = 部分可独立存在（空心菱形）；组合 = 同生共死（实心菱形）
3包含 vs 扩展包含 include = 必定执行；扩展 extend = 条件触发（箭头方向亦相反）
4用例图的归属属行为图，不是结构图（虽然它给的是静态用例视图）
5逆向工程 vs 再工程逆向 = 抽象出信息，不改系统；再工程 = 改造系统，产出新版本
6CMM 可重复 vs 已定义可重复 = 项目级能重复成功；已定义 = 组织级有标准过程
7RUP 架构在哪阶段细化阶段（Elaboration），不是构建阶段
8敏捷不做什么不做大量前期文档、不做严格阶段评审、不做固定不变更的合同
9CMMI 阶段式 vs 连续式阶段式评组织成熟度（5 级）；连续式评过程域能力（0~5 级）
10验证 vs 确认验证 Verification = 对规格（做得对不对）；确认 Validation = 对用户（是不是用户要的）

⚠️ 补充辨析：可管理级 vs 优化级 —— 可管理是量化控制当前过程；优化是主动改进过程本身。

⚠️ 补充辨析：顺序图 vs 通信图 —— 顺序图强调时序；通信图强调组织结构。

⚠️ 补充辨析：喷泉 vs 螺旋 —— 喷泉是面向对象、无间隙；螺旋是风险驱动。

1用例之间的 include（包含）与 extend（扩展）关系，下列说法正确的是：
Ainclude 表示基础用例必定执行被包含用例；extend 表示条件触发时才执行扩展用例，两者箭头方向相反
Binclude 是可选的，extend 是必选的
C两者箭头方向相同，都从基础用例指向被用用例
Dinclude 与 extend 含义完全相同
包含 = 必须做（"用户下单"必包含"用户登录"），箭头 基础 → 被包含；扩展 = 可能做/条件触发（"用户下单"在用券时才扩展"使用优惠券"），箭头 扩展 → 基础（方向相反！）；泛化 = 父子关系，箭头 子 → 父。题干出现"每次/必然/一定"→ include；"可选/如果…才/特定条件"→ extend。
第7章 · 7.7 用例三关系
2UML 的"五个系统视图"中，描述系统静态结构（类、对象、关系）的是：
A逻辑视图
B用例视图
C进程视图
D部署视图
UML 五视图（4+1 视图）：用例视图（系统功能，用例图；驱动其他视图）｜逻辑视图（静态结构与行为，类图/对象图/状态图/活动图）｜进程视图（并发与同步、性能与吞吐）｜实现视图（构件图，代码的静态组织）｜部署视图（部署图，软硬件物理分布）。
第7章 · 7.7 UML 五个系统视图
3UML 中"实现"（Realization）关系通常指的是：
A类与接口之间的关系（类实现接口）
B一个事物变化影响另一事物（依赖）
C对象之间的结构连接（关联）
D一般与特殊的关系（泛化）
UML 四种关系：依赖（偶发的、语义较弱的使用，虚线箭头）｜关联（结构连接，实线；聚合/组合是其特例）｜泛化（一般—特殊，实线空心三角，子→父）｜实现（类与接口、用例与实现它的协作之间的关系，虚线空心三角）。
第7章 · 7.7 UML 四种关系
4下列 UML 图中，属于"交互图"的是：
A顺序图 与 通信（协作）图
B类图 与 对象图
C状态图 与 活动图
D构件图 与 部署图
十四种图按教材分 5 类：用例图；静态图（类图·对象图·包图）；行为图（状态图·活动图）；交互图（顺序图·通信图/协作图·定时图·交互概览图）；实现图（构件图·部署图）。顺序图强调时间顺序，通信图强调对象间的结构关系——这是两者的选择依据。

5关于软件形式化方法，下列说法错误的是：
A形式化方法成本低、易于被一般开发人员掌握，可全面替代传统方法
B它能用数学方式严格描述系统性质，有助于发现规格说明中的歧义与不完整性
C净室软件工程强调正确性验证与统计质量控制，追求"零缺陷"
D形式化规格说明可以作为程序正确性证明的依据
形式化方法的缺点正是"学习成本高、难以被一般开发人员掌握、难以与现有开发过程平滑集成"，所以它不能全面替代传统方法，通常用于安全攸关的关键部分（如航空航天、核电、轨交信号）。B/C/D 都是它的优点或净室工程的特征。
第7章 · 7.8 软件形式化方法
6净室软件工程（CSE）的核心思想不包括：
A让程序员大量调试并靠测试发现缺陷
B用形式化的正确性验证代替单元测试
C采用增量式开发与统计质量控制
D把缺陷率作为过程改进的可度量指标
净室软件工程的核心是"第一次就写对"：用正确性验证（形式化推理）取代传统的单元测试与调试，程序员不做交互式调试；配合增量式开发与统计质量控制（基于使用模型的随机测试），以"零缺陷"为目标。所以 A 正好与它的思想相反。
