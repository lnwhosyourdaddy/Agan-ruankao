第 27 小时 · 软件架构设计（二）· 架构风格与 SOA

本学时覆盖 12.3 架构风格六大类 + SOA 关键技术与实现三方法 —— 本章主体，也是风格辨识题的来源。
风格类题目几乎每年出现在案例里，题干给场景问"属于哪种风格"。

考情定位

六类风格必须能一句话说出代表：① 数据流（批处理、管道-过滤器）② 调用/返回（主程序、面向对象、层次型、C/S）③ 以数据为中心（仓库、黑板）④ 虚拟机（解释器、规则系统）⑤ 独立构件（消息传递、管道）⑥ SOA/微服务。
SOA 三技术必背：UDDI 找人 · WSDL 说事 · SOAP 送信。

记忆口诀

六大类：数据流 · 调用返回 · 数据中心 · 虚拟机 · 独立构件 · SOA。
SOA 三技术：UDDI（注册中心，找人）· WSDL（描述接口，说事）· SOAP（消息格式，送信）。
SOA 三实现：Web Service（标准方式）· 注册表（解耦）· ESB（企业服务总线，协议转换+路由+安全）。
黑板风格：共享黑板 + 独立知识源，黑板不知道知识源存在（控制反转）。

易错陷阱

「管道-过滤器」属数据流，不属独立构件——虽然都叫"管道"，但考点分类是数据流风格。
「黑板」是以数据为中心，不是虚拟机。
SOAP 不是 REST 的升级版——两者定位不同：SOAP 强契约企业级集成，REST 互联网开放接口。
三层 C/S 相比二层的核心改进 = 客户端不再直接访问数据库。

论文可用句

在架构风格选型上，我选择了分层风格 + 管道—过滤器的组合：分层保证业务边界清晰、团队可分工并行开发；管道—过滤器用于日志清洗链路，各过滤器的处理逻辑可独立测试、独立替换。代价是跨层事务需要额外机制（如最终一致性），这一取舍已在架构决策记录（ADR）中登记。

本学时路线图：六类风格逐个拆

上一学时给了六大类的全景对照表，本学时按数据流 → 调用/返回 → 以数据为中心 → 虚拟机 → 独立构件 → SOA 的顺序逐类展开。
每类都按「核心特征 → 典型风格 → 适用场景 → 辨析陷阱」四段写，案例题通常就考最后一段。

12.3.2 数据流风格 · 批处理 + 管道-过滤器 ⭐

📦批处理风格

每个处理步骤是一个单独的程序；每一步必须在前一步结束后才能开始；数据必须是完整的、以整体方式传递。

· 基本构件 = 独立的应用程序

· 连接件 = 某种类型的媒介（定义数据流图、表达拓扑）

数据流体系没有概念上的程序计数器，指令执行顺序不可预测（行为不确定）

🚰管道-过滤器风格 ⭐

系统分解为几个序贯的处理步骤，步骤间通过数据流连接——一个步骤的输出是另一个步骤的输入。

· 基本构件 = 过滤器 Filter（从管道读取输入流 → 内部处理 → 产生输出流写入管道）

· 连接件 = 管道 Pipe（把一个过滤器的输出传到另一过滤器的输入）

⚙️管道-过滤器 · 优点与缺点（必背）

优点

可重用（过滤器独立、无状态、不知上下游）
可并发（过滤器可并行执行）
易维护、支持过滤器替换与组合
允许对输入数据吞吐量分析

缺点

不适合交互式应用（数据必须全部流过）
数据格式转换开销大
难以共享状态（过滤器无状态）
可能导致处理性能瓶颈

口诀：过滤器"独立无状态不知邻"，优点重用加并发，缺点不交互难共享

⚠️ 高频辨析：题干出现"编译器 / 数据转换 / 批量处理" → 管道-过滤器；出现"交互式 / 用户频繁输入" → 不选管道-过滤器。

12.3.3 调用/返回风格 · 主程序/子程序 + 面向对象 + 层次型

调用/返回风格：采用调用与返回机制，实质是分而治之的策略——把复杂大系统分解为若干子系统以降低复杂度、增加可修改性。程序从执行起点开始执行构件代码，执行结束将控制返回给调用构件。

🧩主程序/子程序

  • 一般采用单线程控制，把问题划分为若干处理步骤
  • 构件 = 主程序和子程序（子程序可合成为模块）
  • 连接件 = 过程调用，调用关系具有层次性
  • 语义逻辑：子程序的正确性取决于它调用的子程序的正确性

🧬面向对象

建立在数据抽象和面向对象的基础上；数据的表示方法和相应操作封装在一个抽象数据类型或对象中。

  • 构件 = 对象（抽象数据类型的实例）
  • 连接件 = 对象间的方法调用

封装增强了信息隐藏与可维护性

🪜层次型 ⭐

组成一个层次结构：每一层为上层提供服务，并作为下层的客户；除精心挑选的输出函数外，内部层接口只对相邻层可见。

  • 构件 = 层上实现的虚拟机
  • 连接件 = 决定层间如何交互的协议
  • 每一层最多只影响两层 + 相邻层提供相同接口即可换实现 → 软件重用支持强大

⚠️ 层次型的缺点（冲刺高频）：性能损耗（层层转发）；可能形成"污水池反模式"——某层只做透传、不含业务逻辑。

12.3.3 客户端/服务器 · 二层 C/S 架构 ⭐

C/S 架构基于资源不对等且为实现共享而提出（20 世纪 90 年代成熟）。

  • 服务器：有效管理系统资源，任务集中于对 DBMS 的管理和控制、数据备份与恢复
  • 客户应用程序：提供用户与数据库交互的界面、提交请求并接收信息、对客户端数据执行应用逻辑

这是一种"胖客户机（fat client）、瘦服务器（thin server）"的架构

✅C/S 的优点

①客户应用与服务器构件分别运行在不同计算机上 → 适应性和灵活性大

②易于扩充和缩小

③功能构件充分隔离：客户端集中数据显示分析，服务器集中数据管理（不必每个应用都写 DBMS）

④把大处理任务分布到低成本计算机上，节约费用；数据操作与事务处理能力强、模型思想简单

❌C/S 的八个缺点（教材列举，必背）

①开发成本较高——客户端软硬件配置要求高

②客户端程序设计复杂——工作量大多在客户端

③界面风格不一，使用繁杂，不利推广

④软件移植困难——不同开发工具互不兼容

⑤维护和升级困难——每个客户端都要更新

⑥新技术不能轻易应用——平台选定难更改

⑦可扩展性差——单一服务器、以局域网为中心，难扩展到广域网/Internet

⑧安全性难以保证——客户端程序可直接访问数据库服务器

💡 正因这八个缺点，三层 C/S 架构应运而生（传统 C/S 称为二层 C/S 架构）。

12.3.3 三层 C/S 架构 + B/S ⭐

🥪三层 C/S 架构（增加应用服务器）

表示层（客户机）

系统用户接口部分，担负用户与系统的对话功能；检查键盘输入数据、显示输出；检查内容只限数据形式与取值范围，不含业务逻辑

功能层（应用服务器）

也称业务逻辑层——具体业务处理逻辑编入程序（如计算合同金额、格式配置、打印）

数据层（数据库服务器）

相当于二层 C/S 中的服务器；负责对 DBMS 进行管理和控制

关键：将表示层和功能层分离成各自独立的程序，两层间接口简洁明了（通常只将表示层放在客户机 → 瘦客户机）。三层 C/S 架构中，中间件是最重要的构件。

✅三层 C/S 的四个优点 + 一个关键问题

①三层功能合理划分、逻辑相对独立 → 逻辑结构清晰，可维护性和可扩展性提高

②可灵活选用平台和硬件，各层可并行开发、各选最适合的语言，性价比高

③功能层有效隔离表示层与数据层 → 未授权用户难以绕过功能层访问数据层 → 安全管理基础

④功能层与数据层可放不同服务器 → 灵活性很高，适应客户机数目增加和负荷变动（追加业务时可增加应用服务器）

⚠️ 设计关键：若各层间通信效率不高，即使硬件很强整体也达不到要求性能 → 三层间的通信方法、通信频度和数据量是三层 C/S 架构设计的关键问题。

  • B/S 架构：三层 C/S 架构的一种实现方式——"浏览器 / Web 服务器 / 数据库服务器"。应用程序以网页形式存于 Web 服务器；系统安装、修改和维护全在服务器端解决，"零客户端"，很容易在运行时自动升级。
  • 不足：缺乏动态页面支持能力、没有集成有效的数据库处理功能；安全性难以控制；数据查询等响应速度远低于 C/S；数据提交以页面为单位、动态交互性不强，不利于 OLTP 应用。

12.3.4 以数据为中心 · 仓库 + 黑板 ⭐

🗄️仓库风格

仓库（repository）是存储和维护数据的中心场所。

两种不同构件：

· 中央数据结构——说明当前数据的状态

· 一组独立构件——对中央数据进行操作

连接件 = 仓库与独立构件之间的交互

🧠黑板风格 ⭐

适用于解决复杂的非结构化问题——在求解过程中综合运用多种不同的知识源，使问题的表达、组织和求解比较容易。

· 问题解空间组织成一个或多个分级结构（每层由唯一词汇描述，代表问题的部分解）

· 领域知识分成独立的知识模块（将某层信息转换成同层或相邻层信息）

传统应用：信号处理领域（语音识别、模式识别）；另一应用是松耦合代理数据共享存取

💡 黑板 = 中央数据结构（黑板）＋ 多个独立知识源（＋控制模块）；适合无确定解法的问题——AI 推理、语音识别、模式识别。

影响黑板系统设计的最大因素是应用问题本身的特性（教材原话）。

口诀：仓库存数据，黑板解难题；语音识别找黑板

⚠️ 辨析：题干出现"语音识别 / 模式识别 / AI 推理 / 无确定解法" → 黑板风格；出现"数据库为中心、构件操作中央数据" → 仓库风格（一般情形）。

12.3.5 虚拟机 + 12.3.6 独立构件 ⭐

🖥️虚拟机风格（两大类）

  • 基本思想：人为构建一个运行环境，在此环境上解析与运行自定义的语言，增加架构的灵活性。
  • ① 解释器风格：
  • 含有一个虚拟机，仿真硬件的执行过程和一些关键应用
  • 弥合程序语义与硬件语义之间的差异；缺点：执行效率较低
  • 组成：解释引擎 + 存储被解释代码的存储区 + 记录引擎当前工作状态的数据结构 + 记录解释执行进度的数据结构
  • 典型例子：专家系统

② 规则系统风格：包括规则集、规则解释器、规则/数据选择器、工作内存四部分（伪代码执行专家系统思路）

📡独立构件风格（两大类）

强调每个构件都是相对独立的个体，它们之间不直接通信，以降低耦合度、提升灵活性。

① 进程通信风格：

  • 构件 = 独立的过程；连接件 = 消息传递
  • 构件通常是命名过程；消息传递方式：点到点、异步/同步、远程过程调用

② 事件系统风格（隐式调用）⭐：

  • 构件不直接调用过程，而是触发或广播一个或多个事件
  • 其他构件的过程在事件中注册；事件被触发时，系统自动调用注册的所有过程
  • 事件触发者并不知道哪些构件会被影响——不能假定处理顺序，甚至不知道哪些过程会被调用 → 许多隐式调用系统也包含显式调用作为补充

💡 事件系统的应用（教材举例）：编程环境中集成各种工具 · DBMS 中确保数据一致性约束 · 用户界面系统管理数据 · 编辑器中语法检查（Debugger 断点事件 → 编辑器卷屏、变量监视器刷新，Debugger 只声明事件、不关心谁响应）。

口诀：虚拟机求灵活但低效；独立构件"不直呼、发事件"；隐式调用难保序

12.3.7 SOA · 定义与参考模型 ⭐

🧭SOA 的三个典型定义

W3C

一种应用程序架构：所有功能都定义为独立的服务，带有定义明确的可调用接口，能以定义好的顺序调用这些服务来形成业务流程

Service-architecture.com

服务是精确定义、封装完善、独立于其他服务所处环境和状态的函数；SOA 本质上是服务的集合，服务之间彼此通信

Gartner

一种 C/S 架构的软件设计方法；着重强调构件的松散耦合，并使用独立的标准接口

🏗️SOA 概述要点

①SOA 是一种在计算环境中设计、开发、部署和管理离散逻辑单元（服务）模型的方法

②SOA 并不是新鲜事物，只是面向对象模型的一种替代；SOA 基于对象，但作为一个整体却不是面向对象的

③SOA 系统原型的典型例子是 CORBA（概念与 SOA 相似）

④SOA 建立在 XML 等新技术基础上，用基于 XML 的语言描述接口 → 服务转到更动态且更灵活的接口系统（CORBA 的 IDL 无法相比）

⑤SOA 用本地计算模型实现分布式计算应用——"本地化设计，分布式工作"（CORBA、DCOM、EJB 都属此列）

💡 Gartner 定义 = "松散耦合 + 独立标准接口"，是选择题里最好认的一句。

12.3.7 SOA 关键技术 · UDDI / WSDL / SOAP / REST ⭐

📇UDDI · 统一描述、发现和集成

提供一种服务发布、查找和定位的方法，是服务的信息注册规范。

三部分内容：

  • 数据模型——描述业务组织和服务的 XML Schema
  • API——用于查找或发布 UDDI 数据的方法，基于 SOAP
  • 注册服务——SOA 中的基础设施，对应服务注册中心角色

📄WSDL · Web 服务描述语言

对服务进行描述的语言，基于 XML 的语法定义；描述重点 = 服务。

  • 服务接口定义——抽象的、可重用的定义；行业标准组织用它规定标准的服务类型
  • 服务实现定义——描述给定提供者如何实现特定接口；包含服务和端口描述（端口 = 服务访问入口的部署细节：访问地址、消息调用模式）

✉️SOAP · 简单对象访问协议

定义服务请求者和提供者之间的消息传输规范——用 XML 格式化消息、用 HTTP 承载消息；可在网络中进行数据交换和 RPC。

  • 四个部分：封装（整体框架：包含什么/谁处理/可选还是必须）· 编码规则（序列化机制）· RPC 表示（远程过程调用和应答的协议）· 绑定（底层传输协议交换封装的约定）
  • 消息三个部分：封装 Envelope（必须出现，顶层元素）· SOAP 头 Header（可选，出现则必须是封装的第一个直接子元素）· SOAP 体 Body（必须出现，紧跟头之后）

🪶REST · 表述性状态转移

只使用 HTTP 和 XML 进行基于 Web 通信；降低开发复杂性、提高系统可伸缩性；简单性 + 缺少严格配置文件 → 与 SOAP 很好地隔离开。

只支持几个操作：POST、GET、PUT、DELETE（适用于所有消息）。

设计概念与准则（5 条）：① 网络上所有事物都被抽象为资源 ② 每个资源对应一个唯一的资源标识 ③ 通过通用的连接件接口对资源进行操作 ④ 对资源的各种操作不会改变资源标识 ⑤ 所有的操作都是无状态的

💡 这些技术都以 XML 为基础发展起来；SOAP 消息必考：Envelope 必须 / Header 可选（第一子元素）/ Body 必须紧跟 Header。

12.3.7 SOA 实现三方法 · Web Service / 注册表 / ESB ⭐

🌐① Web Service

  • 三角色：服务提供者 / 服务请求者（必须）+ 服务注册中心（可选）；三操作：发布、查找、绑定（动态绑定 / 静态绑定）
  • 应用系统 6 个层次：

① 底层传输层——消息传输（HTTP 最广、JMS、SMTP）

② 服务通信协议层——SOAP 和 REST

③ 服务描述层——WSDL

④ 服务层——包装遗留系统，通过 WSDL 定位调用

⑤ 业务流程层——服务发现/调用/点到点；标准 WSBPEL

⑥ 服务注册层——UDDI

📇② 服务注册表

主要在 SOA 设计时使用（也有运行时功能）；提供策略执行点 PEP。

三个功能：

  • 服务注册——发布服务功能（服务合约）：身份、位置、方法、绑定、配置、方案、策略；要限制谁能发布、谁批准
  • 服务位置——帮助使用者查询已注册服务（检索服务合约）；规定谁能访问注册表、哪些属性可暴露
  • 服务绑定——用查到的服务合约开发代码并绑定调用

🚌③ 企业服务总线 ESB ⭐

从 SOA 发展而来；标准化通信基础结构；传统中间件技术与 XML、Web Service 结合的产物。

  • 核心价值：消除服务请求者与提供者之间的直接连接（避免网状结构的高维护费）→ 进一步解耦。
  • 功能（6 条）：支持异构环境中服务/消息/基于事件的交互 · 几乎不更改代码使现有系统具有全新服务接口（无缝非侵入）· 缓冲器（转换业务逻辑和数据格式）与服务逻辑分离 · 服务代理和协议转换（HTTP/SOAP/JMS 多种传输）· 可配置的消息转换翻译 + 基于消息内容的消息路由 · 安全和拥有者机制（认证授权完整性）

💡 ESB 的四点优势：扩展的基于标准的连接 · 灵活的服务导向应用组合 · 提高复用率降低成本 · 减少市场反应时间提高生产率。

口诀：Web Service 六层栈，注册表管设计期，ESB 消除直连解耦

2"黑板"（Blackboard）架构风格属于：
A以数据为中心风格
B数据流风格

3SOA（面向服务架构）的三项关键技术中，"UDDI" 的作用是：
A服务注册与发现（提供服务的描述与查询规范）
B描述服务如何被调用（WSDL）
C消息在网络中的传输格式（SOAP）
D缓存加速
SOA 三项核心技术：UDDI（Universal Description, Discovery and Integration）——服务注册中心，提供服务的描述与查询规范，支撑服务注册、发现与集成｜WSDL（Web Services Description Language）——服务描述语言，描述"服务提供什么、怎么调用"（用 WSDL 生成的 SOAP 服务才可被 UDDI 注册）｜SOAP（Simple Object Access Protocol）——消息传输格式，规定 XML 消息如何在网络上传送。⚠️ 记忆："UDDI 找人、WSDL 说事、SOAP 送信"。
第12章 · 12.3.7 SOA 关键技术
4关于 REST 与 SOAP，下列说法正确的是：
AREST 面向资源、用 HTTP 动词表达操作、轻量易用；SOAP 面向服务、用 XML 定义接口契约、适合企业级复杂交互
BREST 必须用 XML 传输，比 SOAP 更重
CSOAP 是 REST 的升级版本
D两者都是消息中间件协议
REST（Representational State Transfer，表述性状态转移）：面向资源架构风格，用 HTTP 动词（GET/POST/PUT/DELETE） 表达对资源的操作，用 URL 标识资源，轻量、无状态、只需 HTTP 协议。SOAP：面向服务，用 WSDL 定义接口契约，用 XML 作为消息格式，规范严谨但笨重。⚠️ 常见误区："SOAP 比 REST 先进"——两者定位不同，SOAP 适合强契约的企业级集成，REST 适合互联网开放接口。

5SOA 的实现方式中，"注册表（Registry）"方式指的是：
A通过注册中心管理服务的发布、查找与绑定
B在客户端代码里硬编码服务地址
C用消息队列削峰
D把服务打包成独立进程
SOA 三种实现方式：Web Service（用 WSDL 描述接口、SOAP 通信，是标准方式）｜注册表方式（用注册中心统一管理服务的发布/查找/绑定，服务提供者与消费者解耦）｜ESB（企业服务总线）（用消息总线统一做协议转换、路由、安全控制，是企业级整合的主流）。
第12章 · 12.3.7 SOA 实现三方法
6三层 C/S 架构与二层 C/S 架构相比，主要增加的是：
A表示层与应用层分离，客户端不直接访问数据库
B客户端数量增加
C网络带宽要求提高
D数据库服务器数量减少
二层 C/S：客户端直接访问数据库（胖客户端），数据库连接数受限、扩展性差。三层 C/S：表示层（客户端）→ 应用层（服务器）→ 数据层（数据库），客户端不再直接连数据库，好处是连接数降低、扩展性提升、安全性更好、便于集中管理。B/S 架构是三层 C/S 的特例（表示层用浏览器）。
