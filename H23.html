【导读小贴士】

这章内容多，但结构极其规整：先分层次（业务/用户/系统），再走流程（获取→分析→规格→验证→管理），

【基础知识点】

1. 需求的三个层次（业务 → 用户 → 系统）

记忆点：三个层次从目标到具体、从整体到局部、从概念到细节。
业务需求确定项目视图和范围（视图和范围文档）；用户需求建立在场景整理之上；
系统需求是需求规格说明书的直接对象。

2. 需求工程的五个阶段

阶段内容关键产出
① 需求获取与用户交流、观察现有系统、分析任务，开发/捕获/修订需求原始需求
② 需求分析为系统建立概念模型，抽象描述并捕获现实世界语义需求模型
③ 形成需求规格（文档化）按标准生成需求模型的文档描述需求规格说明书
④ 需求确认与验证确认需求的完整性、正确性、一致性、可测试性、可行性评审记录
⑤ 需求管理需求追踪管理、变更控制、版本控制需求基线（Baseline）
关键区分
  • 需求开发 = 阶段 ①②③④（获取、分析、规格、验证）
  • 需求管理 = 阶段 ⑤
  • 需求基线：最终文档评审批准后才定义出需求基线
  • 需求约定是需求开发与需求管理之间的桥梁

3. 需求获取的六种方法（重点：JRP）

3.1 JAD 与 JRP 的关系（高频易错）

项JAD（联合应用开发）JRP（联合需求计划）
英文Joint Application DevelopmentJoint Requirement Planning
定位以小组形式定义并建立系统的专题讨论组JAD 的一部分，是需求获取方法
参与者主管部门经理、会议主持人、用户、协调人员、IT 人员、秘书关键用户代表 + 系统分析师 + 开发团队代表
规模专题讨论组6～18 人，1～5 小时
核心意图定义需求 + 讨论可选技术方案只收集需求，不对需求分析和验证
成本比传统收集需求时间更短成本较高，但十分有效
记忆口诀

JRP 是 JAD 的一部分；JAD 讨论技术方案，JRP 只管收集不管验证。

3.2 JAD 四步骤

  1. 确定 JAD 项目（确定系统范围和规范）
  2. JAD 专题预备会（主持人介绍项目与讨论内容）
  3. 准备 JAD 专题讨论材料
  4. 进行专题讨论会（达成需求一致意见，并对可选技术方案讨论出几套方案）

3.3 JRP 会议四步骤

  1. 互相认识 + 逐项专题讨论（在轻松气氛下）
  2. 开放性交流——对现有系统/类似系统的不足说想法，这一过程不对想法发表任何评论
  3. 设想新方案——把想法、问题、不足记录下来，形成要点清单
  4. 整理要点清单 → 明确优先级 → 评审

JRP 会后：与会者完成评价性调查问卷；最后产出总结性报告，内容为
已达成一致的需求 和 未解决的问题。

3.4 JRP 实施的八条主要原则

  1. 实施前应制定详细议程，并严格遵照议程
  2. 按既定时间安排进行
  3. 尽量完整地记录会议期间的内容
  4. 讨论期间尽量避免使用专业术语
  5. 充分运用解决冲突的技能
  6. 会议期间设置充分的间歇时间
  7. 鼓励团队取得一致意见
  8. 保证所有人员遵守事先约定的规则

JRP 最适合的场景：最有歧义的问题、需求最不清晰的领域——群策群力效果好。
最大难点：会议的组织和相关人员的能力（要言之有物、气氛开放）。

4. 需求记录技术

  • 为什么需要：获取人员与分析人员可能不是同一团队；一个项目可能有多个系统分析师参与获取
  • 目的：需要统一需求记录工具，让所有人的获取结果是同一口径
  • 需求记录要求：能避免二义性、能被系统分析师和用户同时理解、便于追踪与查找

11.1.2 质量功能部署(QFD)

QFD 是把用户要求转化为软件需求的技术,目的是最大限度提升用户满意度。

类型特点影响
常规需求用户认为系统应做到的功能/性能实现越多越满意
期望需求想当然应具备,但常不能准确描述未实现则用户不满意
意外需求(兴奋需求)超出用户要求范围,开发人员乐意赋予实现更高兴,不实现不影响购买决策;是否实现由开发人员掌控(成本/周期)

11.2.6 需求记录技术

目的:统一工具,让多人获取的结果同一口径。常用:任务卡片、场景说明、用户故事、Volere 白卡。

1. 任务卡片(示例:开通课程)

项目说明备注
任务业务活动命名,用用户业务术语
目的活动的工作意义意图而非动作
触发进行该活动系统要判断的前置条件
前提触发时机和场景业务前提
频率发生频率非功能需求
关键情况特殊业务场景系统需专门处理

任务变体变体与异常处理≈用例扩展事件流

2. 场景说明

难以抽象子任务和变体时,整理用户对工作场景和过程的详细描述,抽象出子任务;后续用于测试用例和用户培训手册。

3. 用户故事

三方面:书面描述(计划备忘)、交谈(细化)、测试用例(验证)。故事是讨论的引子,不是详细规范;编写前建立用户角色模型;由用户团队按重要性安排开发、编写故事。

属性含义
独立性避免依赖,以免产生优先级和规划问题
可协商性不是必须实现的合同或需求
对用户有价值最好由用户编写
可预测性能大致估计规模和工作量
短小精悍规模取决于团队规模、能力和技术
可测试性必须可测试
口诀(INVEST)

独立、协商、价值、预测、短小、测试。

4. Volere 白卡

字段:需求编号、需求类型、事件/用例编号、描述、理由、来源、验收标准、顾客满意度、顾客不满意度、依赖关系、冲突、支持材料、历史。用户故事与 Volere 白卡定位最小需求项,量大,多用于敏捷方法。选工具时考虑开发方法、用户情况、分析师技能。

11.3 需求分析

获取的需求杂乱、重复、矛盾,不能直接做设计基础。好需求具备:无二义性、完整性、一致性、可测试性、确定性、可跟踪性、正确性、必要性。

11.3.1 需求分析的任务

把用户“要求”整理确认,形成完整、清晰、规范的文档,确定软件要实现的功能和完成的工作;并确定非功能需求(性能、可靠性、响应时间、可扩展性)、设计约束、运行时与其他软件的关系。

11.3.2 需求分析的方法

主要有 SA、OOA、PDOA,另有形式化方法如维也纳设计方法(VDM)。

1. PDOA 方法

PDOA 强调描述、较少强调建模;问题框架将问题域分为相互关联的子域,类似上下文范围关系图,但前者针对问题域,后者针对解系统。

2. SA、OOA、PDOA 对比

方法思维方式基本假设特点
SA功能分层分解,自顶向下;因果律、归纳法、逻辑法问题域可定义、有限,有限步骤可分解;分析师理解全部且能正确分解仍有大量成功系统,未过时
OOA抽象、信息隐藏、功能独立、模块化;观测外在表象→逻辑对象→接口通信不假定理解全部,只承诺持续“观测并理解”当前主流,工具和语言支持多
PDOA聚焦问题域和需求规格说明作为另外任务成果:问题域描述+需求列表;丰富 SA/OOA,但掌握有限

11.4 结构化分析方法

基本思想:自顶向下,逐层分解。分析模型以数据字典为核心,围绕数据模型(E-R 图)、功能模型(DFD)、行为模型/状态模型(STD)。三个模型联系密切,建立无严格时序,迭代进行。

11.4.1 数据流图(DFD)

表达系统内数据流动并通过数据流描述功能;采用结构化方法时,DFD 通常是 SRS 的组成部分。

1. 主要作用

  • 理解和表达用户需求的工具(简明易懂,可与用户交流)。
  • 概括系统内部逻辑,是需求分析结果的表达,也是系统设计的起点。
  • 作为存档材料,是修改充实开发计划的依据。

2. 四种基本符号

外部实体是系统之外的信息生产者或消费者(数据源和终点),不能由计算机处理。

3. DFD 的层次

4. 画图步骤

  1. 画系统输入输出(确定范围;可先多画再删减补漏)。
  2. 画内部:用一系列处理连接输入输出。
  3. 为数据流命名(避免空洞名字)。
  4. 为加工命名(动宾短语)。

5. 检查修改原则(案例找错重点)

1只限四种符号,每个元素必须有名字元素无名
2每个加工至少一进一出,数据守恒;输出流不应与输入流同名“黑洞”(只进不出)、“奇迹”(只出不进)、输出数据无来源

11.4.2 状态转换图(STD)

业务系统多为数据驱动,适合 DFD;实时控制系统多为事件驱动,适合行为模型。STD 通过状态和事件表示行为,还指出事件发生时执行的动作。

  • 状态:可观察到的系统行为模式,圆形或椭圆框,内标状态名;规定系统对事件的响应方式。
  • 事件:特定时刻发生的事,是引起转换的控制信息(时钟到时、鼠标单击)。
  • 转换:箭头线,线上标事件名,方括号内为转换条件,条件为真才转换。
  • 循环运行过程不关心如何启动;单程生命期需标初态(实心圆)和终态(同心圆,内圆实心)。

11.4.3 数据字典

DFD 无法反映数据的详细内容;数据字典定义 DFD 中所有命名元素,与 DFD 配合,从图形和文字两方面完整描述逻辑模型。

1. 六类条目

条目描述要点
数据元素名称、编号、别名、类型、长度、取值范围及含义、简要说明、相关数据结构
数据结构递归概念;描述元素间组合关系;特殊成分:任选项 [ ]、必选项 { }、重复项(如“课程细节*”)
数据流名称、编号、简要说明、来源、去处、组成、流通量(含高峰期)
数据存储结构、有关数据流、查询要求;只列数据结构不列内部构成;多层出现时列最底层图的数据流
加工逻辑编号、名称、简要功能、输入输出数据流;详细逻辑用判定树、判定表、结构化语言
外部实体名称、编号、简要说明、产生的与接收的数据流、数量(估计业务量)

2. 作用

数据字典是“关于系统数据的数据库”,是全过程统一标准,保证数据完整性和一致性。

  • 按要求列表,保证设计不遗漏。
  • 相互参照,便于修改。
  • 由描述内容检索名称。
  • 一致性、完整性检验(无来源去向的数据流、无输入输出的存储、加工与输入元素是否匹配等)。

3. 管理

必须由专人(数据管理员)管理;任何人(分析师、设计师、程序员)修改须经数据管理员,管理员及时通知最新版本。

11.5 面向对象分析方法

OOA 运用 OO 方法分析理解问题域,找出描述问题域和系统功能所需的类和对象,定义属性、职责和联系,产生符合需求的 OOA 模型。OOA 独立于具体实现:OOA 解决“做什么”,OOD 解决“怎么做”。

11.5.1 用例模型

用例方法是一种需求合成技术,关注系统提供的服务。

1. 用例图元素

  • 参与者:系统外部与系统交互的任何事物。
  • 用例:系统执行的一系列动作,为特定参与者生成可见价值结果。
  • 通信关联:参与者与用例、用例与用例之间的关系。

2. 识别参与者

可由人、其他系统(如 OA 系统)、硬件设备(如 IC 卡读写器)、时钟(如定时交卷)担任。

3. 合并需求获得用例

  • 命名:动词(短语)+名词(短语),并编号(便于需求跟踪)。
  • 不能把用例包含的步骤(验证学员信息、检查权限、保存记录等)当成独立用例,它们只是事件流。
  • 区分业务用例(含人工活动,如“编写教材”)与系统用例;信息系统只识别系统用例。

4. 细化用例描述

用例建模主要工作是写用例规约而非画图;至少含用例名、参与者、目标、前置条件、事件流、后置条件;可含非功能需求和优先级。

组成编写要点
用例名称与用例图相符,带编号
简要说明描述传递给参与者的价值,用自然语言
事件流简单语法、主语明确;写明“谁控制球”;俯视角度;写意图和职责,不写界面和技术细节。主事件流=典型成功路径,无条件分支;备选事件流=失败、分支、扩展路径。可分阶段迭代,高优先级先细化;复杂时引用顺序图、状态图、通信图
非功能需求可度量、可验证
前置/后置条件前置不满足则无法启动;后置为执行后状态;可后续细化
扩展点写出包含/扩展用例名及使用情形
优先级满意度/不满意度,如 1~5

案例:开通课程(UC02)用例描述

5. 调整用例模型:三种关系

关系何时用要点
包含两个及以上用例有公共行为公共部分=抽象用例;原始=基本/基础用例
扩展一个用例混合多种场景、有分支拆成基本用例+扩展用例
泛化多个用例有类似结构和行为子用例继承父用例的结构、行为、关系

这三种关系都会增加用例个数、提高复杂度,要谨慎使用;一般在模型完成后再调整。

11.5.2 分析模型

描述系统基本逻辑结构:静态模型(类/对象如何组成系统)、动态模型(如何通信实现行为)。建立过程:定义概念类 → 确定类关系 → 添加职责 → 建立交互图,前三步合称 CRC 建模(Class-Responsibility-Collaborator)。

1. 定义概念类:名词短语法

类别示例(开通课程)
显而易见的类课程、学习币、学员
明显无意义的类请求、界面、信息
不确定类别的类学员账户、课程类型、权限、用户名、费用、课程名称

结论:学员账户/用户名/权限→“学员”属性;课程类型/课程名称→“课程”属性;“费用”独立为“费用清单”类。最终4个类:课程、学习币、学员、费用清单。也可按人员、组织、物品、设备、事件、规格说明、业务规则或政策等名词类别发现候选类。

2. 确定类之间的关系

关系说明例子
关联对象实例间关系;关联名称(动词)、角色、多重性(*=0..*)、导向性(箭头,无箭头为双向或未定义)用户—测试—试卷
依赖B 的变化可能引起 A 变化发送消息、数据成员、操作参数
泛化父类与子类软考试卷、考研试卷是试卷的子类
聚合整体—部分,部分可属多个整体,生命周期可不同汽车—车轮
组合部分只属一个整体,生命周期相同公司—部门
实现说明与实现联系;多个类可实现同一接口接口—类
聚合 vs 组合

聚合“能分开”(车坏轮还能用),组合“同生共死”(公司倒闭部门消失)。

3. 为类添加职责

  • 职责=类维护的知识(属性)+能执行的行为(方法)。
  • 属性要简单:只定义与系统责任和目标相关的;用简单数据类型;不用可导出的冗余属性;不为类关联定义属性;说明名称、解释、数据类型。
  • 责任可由用例描述中的动词确定再筛选;通用性描述(如“交费”“组卷”)。
  • 封装性:信息及相关行为在同一类;适当时可共享责任。
  • 只找主要、明显、与业务规则相关的部分,避免引入数据库、分布式对象等实现技术。

4. 建立交互图

UML 2.0:顺序图、交互概览图、通信图、定时图。最常用顺序图,元素为对象、参与者、生命线、激活框、消息、消息路线,消息是灵魂;对象状态复杂时用状态图。

5. 分析模型的详细程度

文献说法不一;分析模型随开发演变,初期围绕领域知识,后期逐步加入设计元素。模型是辅助工具,能帮助团队开发的就是好模型。

11.7 需求验证

后期才发现需求错误代价高昂,所以在分析阶段验证 SRS(也称需求确认),确定:

  1. SRS 正确描述预期行为和特征。
  2. 软件需求正确来自系统需求、业务规格等。
  3. 需求完整且高质量。
  4. 表示处处一致。
  5. 为设计、实现、测试提供足够基础。

11.7.1 需求评审

需求评审是需求开发阶段结束前的技术评审,对象 SRS,可发现二义性、不确定需求并促成共识。通过后进入设计阶段,跨里程碑修改成本大。

1. 技术评审类型(IEEE)

类型特点
评审正式会议,向用户或干系人介绍工作产品,征求意见和批准
检查由非制作者本人的个人或小组详细检查,验证错误、是否违反标准
走查由开发人员领导团队成员检查其产品,其他成员提技术、风格、错误、标准等意见
正式评审非正式评审
形式评审会,多专家,明确角色职责邮件、文件汇签、网络聊天
特点遵循预定步骤,记录在案(材料、完整性判定、问题总结)反馈分散随机,但不系统、不彻底、不一致

2. 如何做好需求评审(九条经验)

  1. 分层次评审:不同层次需求描述形式和评审人员不同。
  2. 正式与非正式结合:非正式往往效率更高。
  3. 分阶段评审:拆大评审为小评审,降低返工风险。
  4. 精心挑选人员:各类型人员都要参与(建设单位管理/操作人员、IT/采购主管,承建单位市场/分析师/架构师/工程师/测试/QA/实施/项目经理,第三方领域专家),且要真正了解系统。
  5. 评审人员培训:领域专家不一定懂评审方法。
  6. 检查单:形式检查(QA 查格式)、内容检查(评审人员查目标、遗漏、错误,是重点)。
  7. 标准流程:进入条件、提交资料、职责分配、步骤、通过条件。
  8. 评审后跟踪:评估问题→书面变更申请→进入变更管理→变更后复审。
  9. 充分准备:提前下发 SRS,执行进入条件,事先沟通,准备检查单。

11.7.2 需求测试

测试应从需求定义开始,早制订测试计划和用例,防止错误“放大”,降低测试和维护费用;需求遗漏错误隐蔽,仅读 SRS 难以想象系统行为。

1. 概念测试用例

  • 需求阶段无可执行系统,只做“概念”测试,不真正执行。
  • 来源:功能需求(SA)或用例(OO);可发现 SRS 错误、二义性、遗漏,可用于模型分析,是用户验收测试基础,系统测试时再细化。
  • 覆盖:主事件流、备选事件流(OO)或功能描述(SA),以及获取分析期间的约束;独立于实现。
  • 另一种方式:对话图(Dialog Map),更直观,但不适合描述约束和复杂流程。
示例(开通课程)校验规则

用户名必须存在;所交费用为整数;交费时间在当前时间之前;选修课程必须已存在。费用多/少、人数超限均有对应测试分支;最后修改学员权限,课程人数加1。

2. 需求测试过程

需求测试人员应脱离开发部门、加入测试部门(不能既当运动员又当裁判员);也可用 RAD 工具建界面原型由用户确认,需求测试由测试人员和用户共同完成。

11.8 需求管理

包括追踪管理、变更控制、版本控制;评审批准的最终文档定义需求基线。

11.8.1 需求变更

变更是常态。原因:获取不完整有遗漏、理解偏差、业务变化等。合理变更不可避免,无控制的变更导致项目混乱。应确保:仔细评估建议变更;挑选合适人选判定;及时通知相关人员;按程序采纳并控制过程和状态。

1. 变更控制过程

要点

变更控制不是设置障碍,而是“渠道和过滤器”,确保采纳最合适的变更并将负面影响降到最低。

常见变更策略

  1. 所有需求变更必须遵循变更控制过程。
  2. 未获批准的变更不应做设计和实现。
  3. 由项目变更控制委员会决定实现哪些变更。
  4. 项目风险承担者应能了解变更内容。
  5. 绝不能从配置库删除或修改变更请求的原始文档。
  6. 每个集成的需求变更必须能跟踪到经核准的变更请求(水平可追踪性)。

工具:需求变更跟踪工具(收集、存储、管理变更);问题跟踪工具可按状态分类报告变更请求数目。

2. 变更控制委员会(CCB)

  • 项目所有者权益代表,负责裁定接受哪些变更;由多方成员组成,通常含用户和实施方决策人员。
  • 是决策机构,不是作业机构;通过评审决定是否变更,不提出变更方案。
  • 可能代表:产品或计划管理、项目管理、开发、测试或质量保证、市场部或客户代表、用户文档、技术支持、帮助桌面或用户支持热线、配置管理部门。
  • 应有总则:目的、授权范围、成员构成、决策过程和操作步骤、会议频度和事由;管理范围说明可做哪些决策、哪类上报更高一级委员会。
过程步骤内容
制定决策明确有效决定的出席人数、决策方法(投票/一致通过等)、主席是否可否决集体决定;权衡利弊——利:节省资金或额外收入、客户满意度、竞争优势、缩短上市时间;弊:开发费用增加、交付推迟、质量下降、功能减少、用户不满意
交流情况决策后指派人员及时更新请求状态
重新协商约定变更总有代价,拒绝的变更也耗费资源(提交、评估、决策);接受重要变更要与管理部门和客户重新协商:推迟交货、增加人手、推迟低优先级需求、质量折中

11.8.2 需求跟踪
