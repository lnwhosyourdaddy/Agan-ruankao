第 23 小时 · 软件需求工程（一）

章节考点分析

第 11 章是综合知识、案例分析、论文写作三科的共同地基——案例第 1 题常年考需求与建模，
论文"需求获取/需求管理"类题目也是高频。本学时覆盖需求层次、需求工程框架、需求获取六法。

【导读小贴士】

这章内容多，但结构极其规整：先分层次（业务/用户/系统），再走流程（获取→分析→规格→验证→管理），
每步有各自的工具与方法。抓住"层次 + 流程 + 工具"三条线，就不会记混。
案例题考你画图与找错，论文题考你用哪类方法、为什么选它——两科考的是同一套知识的不同侧面。

【基础知识点】

1. 需求的三个层次（业务 → 用户 → 系统）

记忆点：三个层次从目标到具体、从整体到局部、从概念到细节。
业务需求确定项目视图和范围（视图和范围文档）；用户需求建立在场景整理之上；
系统需求是需求规格说明书的直接对象。

2. 需求工程的五个阶段

阶段内容关键产出
① 需求获取与用户交流、观察现有系统、分析任务，开发/捕获/修订需求原始需求
② 需求分析为系统建立概念模型，抽象描述并捕获现实世界语义需求模型
③ 形成需求规格（文档化）按标准生成需求模型的文档描述需求规格说明书
④ 需求确认与验证确认需求的完整性、正确性、一致性、可测试性、可行性评审记录
⑤ 需求管理需求追踪管理、变更控制、版本控制需求基线（Baseline）
注意
  • 需求开发 = 阶段 ①②③④（获取、分析、规格、验证）
  • 需求管理 = 阶段 ⑤
  • 需求基线：最终文档评审批准后才定义出需求基线
  • 需求约定是需求开发与需求管理之间的桥梁

3. 需求获取的六种方法（重点：JRP）

3.1 JAD 与 JRP 的关系（高频易错）

项JAD（联合应用开发）JRP（联合需求计划）
英文Joint Application DevelopmentJoint Requirement Planning
定位以小组形式定义并建立系统的专题讨论组JAD 的一部分，是需求获取方法
参与者主管部门经理、会议主持人、用户、协调人员、IT 人员、秘书关键用户代表 + 系统分析师 + 开发团队代表
规模专题讨论组6～18 人，1～5 小时
核心意图定义需求 + 讨论可选技术方案只收集需求，不对需求分析和验证
成本比传统收集需求时间更短成本较高，但十分有效
要点

JRP 是 JAD 的一部分；JAD 讨论技术方案，JRP 只管收集不管验证。

3.2 JAD 四步骤

  1. 确定 JAD 项目（确定系统范围和规范）
  2. JAD 专题预备会（主持人介绍项目与讨论内容）
  3. 准备 JAD 专题讨论材料
  4. 进行专题讨论会（达成需求一致意见，并对可选技术方案讨论出几套方案）

3.3 JRP 会议四步骤

  1. 互相认识 + 逐项专题讨论（在轻松气氛下）
  2. 开放性交流——对现有系统/类似系统的不足说想法，这一过程不对想法发表任何评论
  3. 设想新方案——把想法、问题、不足记录下来，形成要点清单
  4. 整理要点清单 → 明确优先级 → 评审

JRP 会后：与会者完成评价性调查问卷；最后产出总结性报告，内容为
已达成一致的需求 和 未解决的问题。

3.4 JRP 实施的八条主要原则

  1. 实施前应制定详细议程，并严格遵照议程
  2. 按既定时间安排进行
  3. 尽量完整地记录会议期间的内容
  4. 讨论期间尽量避免使用专业术语
  5. 充分运用解决冲突的技能
  6. 会议期间设置充分的间歇时间
  7. 鼓励团队取得一致意见
  8. 保证所有人员遵守事先约定的规则

JRP 最适合的场景：最有歧义的问题、需求最不清晰的领域——群策群力效果好。
最大难点：会议的组织和相关人员的能力（要言之有物、气氛开放）。

4. 需求记录技术

  • 为什么需要：获取人员与分析人员可能不是同一团队；一个项目可能有多个系统分析师参与获取
  • 目的：需要统一需求记录工具，让所有人的获取结果是同一口径
  • 需求记录要求：能避免二义性、能被系统分析师和用户同时理解、便于追踪与查找

补充知识点

用户访谈的两种形式

形式做法特点
结构化事先准备好一系列问题，有针对性地进行可控、可比
非结构化只列一个粗略想法，根据访谈情况发挥灵活
最佳实践结合这两种方法最有效——不可能把什么都计划清楚，应保持良好灵活性

A业务需求
B用户需求

D非功能需求

第11章 · 11.1.1 需求的层次
4下列关于需求工程活动的说法，错误的是：
A需求开发包括需求获取、需求分析、形成需求规格、需求确认与验证
B需求基线在需求开发的最终文档评审批准后才定义
C需求约定是需求开发与需求管理之间的桥梁
D需求分析与定义仅发生在软件开发的最初阶段，不贯穿整个生命周期
错误在 D：人们逐渐认识到需求分析活动不再仅限于软件开发的最初阶段，而是贯穿于系统开发的整个生命周期。A、B、C 均为教材原文表述。
第11章 · 11.1.4 需求工程
5以下关于情节串联板技术的说法，正确的是：
A它是最生动的需求获取技术，优点是用户友好、交互性强，缺点是花费时间多、降低获取速度
B它只能由系统分析师单方面演示，用户不参与
C它主要用于需求变更控制阶段
D它是一种完全不涉及解决方案探讨的技术
情节串联板让用户直观了解"系统如何做"，帮助消除盲区、达成共识，是最生动的技术；优点是用户友好、交互性强、对界面提供早期评审；缺点是花费时间很多，使需求获取速度大大降低。它恰恰会涉及解决方案的探讨（B、D 错），也不属于变更控制（C 错）。

6在确定用例的过程中，用例的命名应当采用的形式是：
A动词（短语）+ 名词（短语），如"开通课程"
B名词（短语）+ 动词（短语），如"课程开通"
C仅用名词短语，如"课程"
D仅用动词短语，如"开通"
用例命名应采用"动词（短语）+名词（短语）"的形式，如"开通课程""课程测试"。最好还能对用例进行编号，这是实现需求跟踪管理的重要技巧，可将用户需求落实到特定用例中去。
