第 8 小时 · 分布式系统、构件与云计算

本学时覆盖 4.5 分布式系统 → 4.6 构件与中间件 → 4.7 Web 服务 → 4.8 云计算。
这一学时以概念辨析与缩写为主，是性价比很高的记忆型得分区。

考情定位

必背三张清单：① 透明性八种（访问 位置 并发 复制 故障 移动 性能 伸缩）；② 构件组装三方式（顺序 层次 叠加）；③ 云计算三模型（SaaS/PaaS/IaaS）与四种部署模式（公有 私有 社区 混合）。

易错陷阱

第 4 章知识骨架（下）

4.5 分布式系统

  • 分布式系统：其组件分布在联网的计算机上，组件之间通过消息传递进行通信和动作协调的系统。
  • 关键特征：组件的并发性（进程间并发）、缺乏全局时钟和组件故障的独立性。构建和使用的主要动力来源于对共享资源的期望（硬件：磁盘打印机；软件：文件、数据库、应用服务）。

🏔️构建分布式系统的八大挑战

① 异构性

网络 · 硬件（大端/小端）· OS · 编程语言差异；靠相同网络协议、高级语言、公共标准（gRPC）屏蔽

② 开放性

能否以不同方式被扩展和重新实现；关键 = 发布关键接口（RFC 征求意见文档）

③ 安全性

机密性（防泄露）· 完整性（防改变破坏）· 可用性（防干扰如 DDoS）

④ 可伸缩性

用户负载或数量增加时系统能正常运行；规模问题是分布式系统开发的主要问题

⑤ 故障处理

故障是部分的（有些组件坏了有些正常）；四技术见下页

⑥ 并发性

允许多个客户并发访问共享资源；用分布式锁保证顺序性、不同粒度锁保证一致性

⑦ 透明性

对用户和开发人员屏蔽组件分离性，使系统被认为是一个整体；8 种（下页）

⑧ 服务质量 QoS

影响用户体验的主要非功能特性：可靠性 · 安全性 · 性能（及时性与吞吐量）

口诀：「异开安伸故，并透加服务」——异构、开放、安全、伸缩、故障、并发、透明、QoS

4.5.1 透明性八种 ⭐（必背）

👻ANSA 参考手册 / RM-ODP 识别出的 8 种透明性

  • ① 访问透明：用相同的操作访问本地资源和远程资源；隐藏不同数据表示形式及资源访问方式
  • ② 位置透明：为资源分配逻辑名，用户不需要知道资源的物理位置或网络位置就能访问
  • ③ 并发透明：几个进程能并发地使用共享资源且互不干扰，不破坏资源的一致状态
  • ④ 复制透明：使用资源的多个实例提升可靠性和性能，用户无须知道副本的相关信息
  • ⑤ 故障透明：屏蔽错误——用户不会注意到资源的故障以及系统对该故障的恢复过程
  • ⑥ 移动透明：资源和客户能够在系统内移动而不会影响用户或程序的操作（使用更广泛，替换了迁移透明性）
  • ⑦ 性能透明：当负载变化时，系统能被重新配置以适配性能
  • ⑧ 伸缩透明：系统和应用能够扩展而不改变系统结构或应用算法

💡 访问透明性 + 位置透明性 = 网络透明性（教材原话，常考）。

教材补充：移动透明性是使用更广泛的说法，替换了"迁移透明性"。

口诀：访位并复故，移性加伸缩——记"访问+位置=网络"这条组合

4.5.2 故障处理四技术 + 典型分布式系统

🛠️故障处理四技术

  • ① 检测故障：如校验和检测消息或文件中出错的数据
  • ② 掩盖故障：隐藏或降低严重程度；如消息重传、文件写两个磁盘（一个坏另一个仍正确）
  • ③ 容错：试图检测并隐藏所有故障不现实 → 服务的客户被设计成容错的（浏览器告知用户问题）
  • ④ 故障恢复：服务器崩溃后永久数据的状态能被恢复或回滚；单机靠事务，多机靠分布式事务

💡 典型类型：分布式文件系统、分布式数据库、分布式缓存系统、分布式协调服务系统、分布式计算框架。

📁分布式文件系统（分布式存储最早由谷歌提出）

系统要点
GFSGoogle 基于 Linux 的专有分布式文件系统；运行于廉价普通硬件并提供容错；未开源
HDFS高度容错，适合廉价机器；采用主从（Master/Slave）结构——一个 NameNode（管理命名空间与客户端访问）+ 若干 DataNode（管理存储的数据）
TFS淘宝；海量小文件存储（通常不超过 1MB）；HA 架构 + 平滑扩容；扁平化数据组织将文件名映射到物理地址
MooseFS四部分：管理服务器 Master · 数据服务器 Chunk Server · 元数据备份服务器 Metalogger · 客户机；基于 FUSE 机制；元数据存于 Master 内存并保存至磁盘

分布式存储：扩展能力强，容量随节点数线性上涨，可达 EB 级；但网络时延会成为对外服务的瓶颈。

4.5.3 分布式缓存 · Memcache / Redis / Tair

🧊Memcache

内存里维护一个统一且巨大的哈希表；用键值对存储；每个进程最大 2GB（可开多进程/分布式）

  • 淘汰策略：LRU（先失效的数据，再最近未使用）
  • Lazy Expiration：不监控是否过期，获取 key 时查看时间戳，减轻服务器负载
  • 不支持持久化，重启数据丢失
  • 服务器之间彼此不通信——分布式能力依赖客户端实现

⚡Redis

开源高性能键值对存储；支持字符串、哈希、列表、集合、有序集合等多种数据结构；分布式缓存用一致性哈希

优点：高性能读写 · 多数据类型 · 数据持久化 · 高可用架构 · 支持自定义虚拟内存 · 支持分布式分片集群 · 单线程读写性能极高

缺点：多线程读写较 Memcache 慢

🏷️Tair（阿里）

由中心控制节点 Config Server + 一系列服务节点 Data Server 组成；中心节点单点、一主一备；所有服务节点地位等价，以心跳汇报状态

负载均衡用一致性哈希：所有 key 分到 Q 个桶（桶 = 负载均衡和数据迁移的基本单位）

分持久化（fdb）与非持久化（mdb）两种；存储引擎有抽象层可替换

🗺️Memcache 选取集群节点的三种算法

  • ① 哈希取余：Hash(key) % N 计算数据映射到的节点
  • ② 一致性哈希：所有存储节点排列在首尾相接的 Hash 环上，key 按哈希值顺时针找邻接节点存放；节点加入/退出只影响环上顺时针相邻的后续节点
  • ③ 虚拟 Hash 槽：数据映射到固定范围的整数集合 = 槽（slot）；槽是集群内数据管理和迁移的基本单位；范围远大于节点数，方便拆分与扩展

口诀：Memcache 不持久不互通，Redis 单线程持久化，Tair 主备分桶

⚠️ 常考对比：Memcache 与 Redis 的本质差异——是否支持持久化、数据结构丰富度、单线程 vs 多线程读写性能。

4.6 构件与中间件

构件 · 定义与模型

构件（组件）是一个自包容、可复用的程序集，通过源程序或二进制代码的方式提供，整体向外提供统一的访问接口——构件外部只能通过接口来访问构件，而不能直接操作构件的内部。

构件两个最重要的特性：自包容 与 可重用

🧩CBSE 与构件模型三要素

  • CBSE 基于构件的软件工程：基于分布对象技术、强调通过可复用构件设计与构造软件系统的软件复用途径。构件可以是 COTS（商用现成）构件，也可自行开发。
  • ① 接口：规定如何定义构件接口及应包含的要素（操作名、参数、异常）
  • ② 使用信息：构件需全局唯一的名字或句柄；构件元数据（接口与属性信息）供用户发现服务；部署时须配置以适应应用系统
  • ③ 部署：规格说明指出应如何打包构件使其部署为独立的可执行实体

🏛️三大主流构件模型

Web Services

跨平台、基于标准

EJB（Sun）

Java 体系

.NET（微软）

Windows 体系

  • 构件模型的通用服务：平台服务（允许构件在分布式环境下通信和互操作）+ 支持服务（很多构件需要的共性服务，如身份认证）。
  • 容器：支持服务的一个实现 + 一个接口定义——构件被部署在一个容器中，必须提供该接口定义以便和容器整合。

口诀：自包容、可重用；接口、使用信息、部署；模型三大家 Web/EJB/.NET

构件组装三方式 + 接口不兼容 ⭐

➡️① 顺序组装

按顺序调用已经存在的构件，用两个已有构件创造一个新构件。

需要特定的胶水代码，使上一个构件的输出与下一个构件的输入相兼容。

适用于：构件是程序元素或服务

🪜② 层次组装

发生在一个构件直接调用另一个构件所提供的服务时。

被调用构件的"提供"接口必须和调用构件的"请求"接口兼容；不匹配则需编写胶水代码转换。

调用者 → 被调用者（提供服务）

🥞③ 叠加组装

两个或以上构件放在一起创建新构件；新构件合并原构件的功能，对外提供新接口。

外部通过新接口调用原有构件接口；原有构件之间不互相依赖、也不互相调用。

适用于：构件是程序单元或服务

🔧接口不兼容三情况 → 适配器

  • ① 参数不兼容：接口每一侧的操作名字相同，但参数类型或参数个数不相同
  • ② 操作不兼容：提供接口和请求接口的操作名不同
  • ③ 操作不完备：一个构件的提供接口是另一个构件请求接口的子集，或者相反
  • 解法：必须编写适配器构件——使两个可复用构件的接口相一致，将一个接口转换为另一个接口

口诀：顺序接输出、层次看接口、叠加合并出新；不兼容三情况 → 参数、操作、不完备

💡 选择组装方式要考虑：功能性需求、非功能性需求、以及一个构件能被另一个构件替代的难易程度。

中间件 · 定义、六功能与分类

🧱中间件定义 + 六大功能

中间件是一种独立的系统软件或服务程序，分布式应用软件借助这种软件在不同的技术之间共享资源；位于操作系统之上，管理计算资源和网络通信，实现应用之间的互操作。

六功能：

①负责客户机与服务器之间的连接和通信，以及客户机与应用层间的高效通信机制

②提供应用层不同服务之间的互操作机制，及应用层与数据库之间的连接和控制

③提供多层架构的应用开发和运行平台、应用开发框架，支持模块化开发

④屏蔽硬件、操作系统、网络和数据库的差异

⑤提供负载均衡和高可用性、安全机制与管理、交易管理机制（保证交易一致性）

⑥提供一组通用服务，避免重复工作并使应用之间可以协作

🗃️按层次划分（自底向上三层）

  • 底层中间件：JVM（Java 虚拟机）· CLR（公共语言运行库）· ACE（自适应通信环境）
  • 通用型中间件：也称平台；RPC · ORB · MOM（面向消息的中间件）
  • 集成型中间件：WorkFlow · EAI

🗂️按职责划分（8 类）

  • ① 通信处理（消息）：保证可靠、高效、实时的跨平台数据传输；市面上销售额最大的中间件产品（eLink、MQSeries、TongLINK）
  • ② 事务处理（交易）：OLTP 大量事务多服务器协调；监视和调度整个系统、负载平衡、故障自动切换（永不停机）
  • ③ 数据存取管理：虚拟缓冲存取、格式转换、解压
  • ④ Web 服务器：弥补浏览器会话能力差、不擅长数据写入、受 HTTP 限制
  • ⑤ 安全中间件：军事/政府/商务安全保密；必须用国产产品
  • ⑥ 跨平台和架构：CORBA（功能强大可跨任意平台但过于庞大）、JavaBeans（灵活简单适合浏览器但效率有待改善）、COM+（适合 Windows 平台）
  • ⑦ 专用平台：为特定应用领域设计领域参考模式
  • ⑧ 网络中间件：网管、接入、网络测试、虚拟社区、虚拟缓冲

中间件与构件的关系 ⭐

本质：中间件是对分布式应用的抽象——抛开与应用相关的业务逻辑细节，保留典型的分布交互模式的关键特征，以统一的形式呈现给应用。

中间件遵循特定的构件标准，为构件互连提供支持，并提供相应的公共服务。

🤝中间件支持的连接子实现的 2 个优势 + 七个方面解释

优势 ①

提供构件之间跨平台交互的能力，遵循特定工业标准（CORBA、J2EE、COM），保证构件间通信完整性

优势 ②

产品化中间件提供强大的公共服务能力，更好保证最终系统的质量属性；由此产生新架构风格：中间件导向的体系结构风格

① 面向需求设计师集中于业务逻辑本身，不必为非功能质量属性耗费精力

② 业务的分隔和包容性按不同业务划分功能，独立设计开发；业务的分类运行与管理是中间件的任务

③ 设计与实现分离构件交互通过接口；IDL 接口定义语言描述接口（DCE → CORBA、DCOM、RMI）

④ 隔离复杂的系统资源中间件屏蔽多样的系统资源；提供与环境隔离的构件开发模式

⑤ 符合标准的交互模型中间件实现了架构的模型、标准的协议（如 CORBA 规范）

⑥ 软件复用提供构件封装、交互规则、与环境隔离机制；可封装以往应用 → 对遗留系统的继承性复用

⑦ 提供对应用构件的管理通过标识机制划分；COM 用 Windows 注册表；CORBA 有接口池、实现池

总结基于中间件开发的应用是构件化的；中间件就是架构，是构件存在的基础

口诀：中间件 = 分布式应用的抽象；IDL 描述接口；中间件就是架构，是构件存在的基础

4.7 Web 服务 · 体系结构 ⭐

Web 服务：由企业发布的、完成其特别商务需求的在线应用服务，其他公司或应用软件能够通过互联网来访问并使用这种在线服务。

其核心是面向服务的架构 SOA（Service Oriented Architecture）——通过完善的接口实现远程访问应用。从技术角度讲，Web 服务是一种解决跨越网络的应用集成问题的开发模式，为实现"软件即服务"提供技术保障。

服务提供者（必需）

Web 服务的所有者（企业、ICP）
定义并实现 Web 服务 → 用服务描述语言描述 → 发布到服务注册中心

服务请求者（必需）

Web 服务的使用者（可由浏览器担当，由人或程序控制）
查找、绑定并调用服务或与服务交互

服务注册中心（可选）

连接提供者和请求者的纽带
使用静态绑定时可不需要——提供者直接把描述发给请求者；也可从文件、FTP、Web 站点等来源得到描述

SOAP · 消息传输协议

目前被广泛接受的消息传输协议，用于在网络应用程序之间交换结构化数据，是一种基于 XML 的机制；在分布的、分散的环境中提供跨互联网调用服务的框架结构，提供独立于编程语言和分布对象底层基础结构的跨平台集成机制

WSDL · 服务描述（基于 XML）

提供应用访问指定 Web 服务所必需的全部信息：描述服务提供了什么功能、服务位于何处、服务如何调用；将服务描述为在消息上进行操作的一组端点；可扩展——允许描述任何端点和消息

UDDI · 注册与发现

解决"在哪里以及如何找到需要的信息"；一套基于 Web 的、分布式的信息注册中心实现标准规范 + 一组使企业能注册自身服务以使别的企业能够发现的访问协议实现标准

🪶XML 与 RESTful

XML（可扩展标记语言）：一种数据存储语言，使用一系列简单标记描述数据；是跨平台的、依赖于内容的技术，是当前处理结构化文档信息的有力工具。

RESTful：基于 HTTP、资源导向、轻量级——与 SOAP 重量级相对。

详尽版对比：SOAP = 重量级协议；REST = 轻量 HTTP 风格

口诀：WSDL 描述、SOAP 消息、UDDI 注册发布——三要素顺序"描述 → 消息 → 注册"

⚠️ 常考辨析："哪个描述服务如何调用" → WSDL；"哪个负责注册与发现" → UDDI。

4.8 云计算

4.8.1 云计算 · 三种服务方式 ⭐

云计算：通过计算机网络（多指因特网）形成的计算能力极强的系统，可存储、集合相关资源，并可按需配置，向用户提供个性化服务。狭义上是一种提供资源的网络——随时获取"云"上的资源、按需求量使用、"云"可看成无限扩展、按使用量付费。

🖥️IaaS · 基础设施即服务

服务提供商将多台服务器组成的"云端"基础设施作为计量服务提供给客户。

将内存、I/O 设备、存储和计算能力等整合为一个虚拟的资源池，提供存储资源、虚拟化服务器等服务。

例：ECS、云主机

🧱PaaS · 平台即服务

服务提供商将分布式开发环境与平台作为一种服务来提供。

提供开发环境、服务器平台、硬件资源等；客户在平台基础上定制开发自己的应用程序。

例：云数据库、容器平台

📧SaaS · 软件即服务

应用软件统一部署在云计算平台上，客户通过互联网订购应用软件服务；按订购软件的数量、时间长短等因素收费，通过标准浏览器向客户提供应用服务。

例：邮箱、CRM、钉钉

⚖️三种方式的两个方向 ⭐

  • 灵活性依次增强：SaaS → PaaS → IaaS——用户可控制的资源越来越底层、粒度越来越小，控制力增强
  • 方便性依次增强：IaaS → PaaS → SaaS——IaaS 只提供底层基本计算能力、工作量大；SaaS 直接给基本功能的应用软件，简单配置即可上线
  • PaaS 最关键：PaaS 是云计算服务模式中最为关键的一层，起支撑作用；地位相当于系统软件，为上层 SaaS 提供 API

口诀：越底层越灵活，越上层越方便；PaaS 承上启下最关键

⚠️ 方向别背反：

灵活性：S → P → I 增强

方便性：I → P → S 增强

（正好是相反的两个方向）

4.8.2 云计算 · 四种部署模式（NIST）

🌍① 公有云

云基础设施是公开的，可以自由地分配给公众。

企业、学术界与政府机构都可以拥有和管理公有云并实现对公有云的操作。

能够以低廉的价格为最终用户提供有吸引力的服务；作为支撑平台还能整合上游服务（增值业务、广告）提供商和下游终端用户，打造新的价值链和生态系统。

🏘️② 社区云

云基础设施分配给一些社区组织所专有——这些组织共同关注任务、安全需求、政策等信息；由社区内的一个或多个组织拥有、管理及操作。

是公有云范畴内的一个组成部分；在一定的地域范围内，由云计算服务提供商统一提供计算、网络、软件和服务能力，结合社区内用户需求共性，面向区域用户

🏢③ 私有云

云基础服务设施分配给由多种用户组成的单个组织。

它可以被这个组织或第三方组织所拥有、管理及操作。

安全可控性最高，核心业务数据通常放这里

🔀④ 混合云

公有云、私有云和社区云的组合。

出于安全和控制原因，并非所有企业信息都能放在公有云上 → 企业将公有信息和私有信息分别放置在公有云和私有云环境中。

大部分企业选择同时使用公有云和私有云，也有一些会同时建立社区云

💡 部署模式划分依据：美国国家标准与技术研究院 NIST 的定义（常考出处）。

口诀：公社私混——谁的云、给谁用、怎么组合

IP地址10.10.33.66/16的网络地址是（69）。

  • A 10.10.0.0
  • B 10.0.0.0
  • C 10.10.33.0
  • D 10.10.33.1

2021年5月3 题
第 70 题某公司的员工区域使用的IP地址段是172.16.133.128/23，该地址段中最多能够容纳的主机数量是（ ）台。

某公司的员工区域使用的IP地址段是172.16.133.128/23，该地址段中最多能够容纳的主机数量是（ ）台。

  • A 254
  • B 510
  • C 1022
  • D 2046
显示答案与解析

答案：B

主机位共9位，理论总地址数2^9=512，减去网段的网络地址和广播地址2个不可用地址，最终可容纳主机数量为510台。

第 67 题以下关于AES加密算法的描述中，错误的是（ ）。

以下关于AES加密算法的描述中，错误的是（ ）。

  • A AES的分组长度可以是256比特
  • B AES的密钥长度可以是128比特
  • C AES所用S盒的输入为8比特
  • D AES是一种确定性的加密算法
显示答案与解析

答案：A

AES标准规定明文分组长度固定为128比特，不支持256比特分组；密钥可选用128比特规格，S盒输入输出均为8比特，加密过程无随机数参与属于确定性加密，A选项描述错误。

第 9 题对一个新的QoS通信流进行网络资源预留，以确保有足够的资源来处理所请求的QoS流，该规则属于IntServ规定的4种用于…

对一个新的QoS通信流进行网络资源预留，以确保有足够的资源来处理所请求的QoS流，该规则属于IntServ规定的4种用于提供QoS传输规则中的（ ）规则。

  • A 准入控制
  • B 路由选择
  • C 排队
  • D 丢弃策略
显示答案与解析

答案：A

IntServ体系的准入控制机制，就是对新请求的业务流做资源校验与预留，若剩余资源无法满足需求则拒绝该流接入网络，保障已有业务流的服务质量。

案例背景
背景：老陶把耳机递给甘工："你听听，跟电流声似的，客户还以为我们信号不好。总部那边倒没事，就我们这层楼。" 邓经理查了平台侧：语音流从 SBC 进来一切正常，RTP 丢包率在总部侧只有 0.2%。 运营商工程师（第三方·电信公司）远程看了专线："我们这段没问题，丢包为零。" 甘工绕着职场走了一圈，发现：坐席电脑和 IP 话机接在同一个交换机上，监控摄像头、大屏、十几台电脑全在一个网段；早高峰时有人在批量导出报表；无线 AP 就装在话机旁边。他把交换机配置调出来一看——没配 VLAN，也没配 QoS。
补充资料：终端→接入交换机 → 8 ms → 42 ms → 0.9% → 异常（瓶颈）；接入→汇聚 → 5 ms → 6 ms → 0.1% → 正常；专线（电信公司） → 12 ms → 3 ms → 0% → 正常；SBC→平台 → 6 ms → 4 ms → 0.2% → 正常；语音要求 → ≤150 ms → ≤30 ms → ≤1% → — 接入段现状：语音/办公/监控/大屏同一网段，无 VLAN、无 QoS；AP 距话机 1.5 m。
