第 32 小时 · 软件实现与测试（二）· 测试阶段与部署发布

本学时覆盖 14.4 测试分类（按对象 / 按阶段 / 七种新形态 / 回归-冒烟）+ 14.5 测试过程与管理
+ 14.6 软件部署，并附全章易错辨析 + 速记卡 + 自测清单。
测试四阶段（单元→集成→系统→验收）与四种发布方式是案例与论文的高频素材。

考情定位

四块必拿：① 四阶段顺序（单元 → 集成 → 系统 → 验收，含各阶段谁来做、用什么方法）；② α vs β 测试（α 在开发场地有指导，β 在用户真实环境无指导）；③ 回归 vs 冒烟（回归验证"没改坏"，冒烟验证"能跑起来"）；④ 四种发布（蓝绿秒回滚但资源翻倍 / 灰度最常用 / 滚动无停机 / 影子不影响用户）。

记忆口诀

四阶段：单元（白盒，开发做）→ 集成（接口，黑+白）→ 系统（完整，纯黑盒，测试团队）→ 验收（用户主导，α 开发场地 / β 用户场地）。
集成策略：一次性 · 自顶向下 · 自底向上 · 三明治。
回归 vs 冒烟：回归防改坏，冒烟验能跑（先冒烟 → 详细 → 回归）。
四发布：蓝绿（双环境，秒回滚）· 灰度/金丝雀（放量观察，最常用）· 滚动（逐批替换）· 影子（流量副本，不影响用户）。

易错陷阱

α 在开发场地（用户在开发方指导下），β 在用户场地（用户自行使用）——方向别记反，两者都属验收测试。
蓝绿部署资源开销翻倍（两套完整环境），换来的是秒级回滚。
回滚预案必须在"制定部署计划"这一步就写好，不能等出问题才想。

论文可用句

在上线发布上，我采用灰度发布 + 蓝绿部署的组合：先通过蓝绿方式将新版本部署到绿环境并用影子流量验证核心链路（不影响真实用户），确认无误后将 5% 的真实流量切至绿环境观察 30 分钟，监控响应时间、错误率与业务指标无异常后，再按 20% → 50% → 100% 逐步放量；全程保留蓝环境，一旦关键指标劣化可在 1 分钟内整体切回。上线后按回归测试集对存量功能做一轮全量验证，确认未因本次变更引入功能回退。

第 14 章知识骨架

14.4 按测试对象 · 功能/性能/安全 ⭐

⚡功能测试 + 性能测试家族

功能测试：又来数据驱动测试——只考虑功能不考虑内部结构；6 步 = 预期编写 → 编案例 → 备数据 → 执行 → 比对报告 → 判断是否满足用户需要

性能测试 = 模拟多种正常/峰值/异常负载测性能指标，含五类：

负载测试

各项性能指标已达到瓶颈的情况下继续运行一段时间，观察指标

压力测试

不断加压直到某些指标达到瓶颈（如 CPU 100%）

并发测试

负载+压力结合——逐渐增加负载找瓶颈，分析交易与资源指标

容量测试

预先分析极限值（最大并发用户数/数据库记录数），极限下不出故障

🛡️安全测试 + 指标

安全测试：验证保护机制能否防非法侵入；两个层面 = 应用程序本身的安全性（漏洞/后门） + 数据安全（存储 + 传输）

手段：渗透测试 · 流量攻击 · SQL 注入 · 跨域攻击；须能经受正面/侧面/背后的攻击

  • 可靠性测试：最有效发现对可靠性影响大的缺陷；也是评估/验证可靠性水平的途径
  • 性能指标五件套：TPS（每秒事务数）· 响应时间 · 并发用户数 · 资源利用率 · 错误率

⚡ 辨析锚：负载 = "到瓶颈后继续跑"；压力 = "不断加压直到瓶颈"；容量 = "找极限值"。

按测试对象 · 兼容/界面/易用/稳定性

🧩兼容性测试（核心五内容）

① 不同操作系统平台兼容 ② 同平台不同版本兼容 ③ 向前/向后兼容 ④ 与其他相关软件兼容 ⑤ 数据兼容（数据共享）

最常见 = 浏览器兼容——CSS/JS 解析差异导致页面显示不同

🖥️界面测试 + 易用性测试

界面测试：布局合理 · 风格一致 · 控件位置符合客户使用习惯 · 便捷性 · 导航易懂 · 文字正确 · 美观

易用性测试（= 用户体验测试）：交互的适应性、功能性、有效性集中体现；流程 = 裁剪易用性检查清单 → 达成一致 → 按表排查 → 评估记入报告

⏳稳定性测试（长时间运行）

通过长时间运行测试软件是否出现问题；常用测试点：

① 长时间运行观察是否正常 ② 反复开启关闭 ③ 长时间执行某业务后切换业务 ④ 长时间挂起不操作后能否正常执行 ⑤ 长时间日常用户数运行观察内存占用/是否溢出

💡 记忆锚：稳定性 = "时间维度"的压力测试（疲劳测试）；易用性 = "用户体验"；界面 = "长相与习惯"。

按阶段 · 单元测试 → 集成测试 ⭐⭐⭐

🧪单元测试（白盒为主）

对最小可测单元检查验证（C = 函数、Java = 类、GUI = 窗口/菜单）；与程序其他部分隔离测试

六项规定

阶段 = 编码后/中；对象 = 模块；人员 = 白盒工程师或开发；依据 = 代码 + 详细文档；方法 = 白盒为主黑盒为辅；内容 = 模块接口 · 局部数据 · 路径 · 错误处理 · 边界

通常不用真实数据（或用正式数据的小样本）

🧷集成测试（模块间接口）

又称子系统/组装/部件测试；对象 = 模块间的接口；三层次 = 模块内集成 → 子系统内集成 → 系统集成

一次性集成

全部模块一次组装——发现问题难定位

自顶向下增量

需要桩模块（Stub）——模拟下层模块

自底向上增量

需要驱动模块（Driver）——模拟上层调用

三明治 / 混合式

两者结合，同时使用桩和驱动

⚡ 高频辨析：桩 = 替身在下（模拟被调用者）；驱动 = 替身在上（模拟调用者）——自顶向下要桩、自底向上要驱动。

按阶段 · 系统测试 → 验收测试 ⭐⭐⭐

🌐系统测试（整体 · 黑盒）

将硬件、软件、操作人员看作整体；在实际运行环境测试；黑盒测试工程师按需求规格说明书执行

典型系统测试：恢复测试（导致失败的条件 + 验证恢复过程；系统须有容错）· 安全测试（扮演入侵者突破防线；设计准则 = 使侵入代价更昂贵）· 压力测试（异常访问量/频率/数据量）

测试内容：功能 · 界面 · 可靠性 · 易用性 · 性能 · 兼容性 · 安全性等

✅验收测试（交付测试 · 用户参与）

部署前最后一个测试；人员 = 最终用户/需求方；依据 = 用户需求 + 验收标准；方法 = 黑盒

① 正式验收

管理严格，系统测试的延续——用例是系统测试的子集；用户代表参与或独立小组

② 非正式验收（α 测试）

开发环境下、无特定用例、内容由测试员决定；较主观

③ Beta 测试

多个用户在实际使用环境下测试；开发者不在现场；不能由程序员或测试员完成；控制最少、最主观

⚡ 辨析：α = 内测（开发环境）；β = 公测（用户实际环境、开发者不在场）。

按被测软件（七种新形态）+ 回归/冒烟

🚀七种新形态测试

  • App：逻辑/功能/界面/兼容/漏洞/压力/中断/弱网测试
  • Web：分布、异构、并发、平台无关 → 比普通程序复杂
  • 物联网：围绕安全、设备、网络、平台、标准
  • 车联网 V2X：V2V / V2P / V2N / V2I 互联互通
  • 大数据：数据维度 + 系统/应用维度；含基准测试（对比框架性能）
  • AI：不确定性/概率性/大数据依赖/自我学习 → 传统方法不够；测算法健壮性、模型评估、模型安全
  • 小程序：权限/UI/功能/兼容；与 App 区别 = 免安装、周期短审核快

🔁回归测试 + 冒烟测试

回归测试：修改旧代码后重新测试——确认修改没引入新错误；迭代开发中更频繁（XP 每天多次）；自动化大幅降成本

四策略

再测试全部用例（最安全、成本最高）· 基于风险选择（先测关键可疑）· 基于操作剖面（按使用频率；预算内最有效提升可靠性）· 再测试修改的部分（依赖性分析；信心足时用）

冒烟测试：源自硬件行业（加电没冒烟就通过）；对象 = 每个新编译需正式测试的版本；执行者 = 版本编译人员；预测试——确认更改不破坏版本完整性与稳定性；特点是注重通过性、轻细节

14.5 测试过程与管理

🧭测试过程六阶段

① 需求分析（确定测什么 + 预期结果）→ ② 制订测试计划（测哪些/用什么方法/人员安排）→ ③ 设计测试文档（核心阶段——编写测试用例）→ ④ 搭建测试环境 → ⑤ 执行测试（单元/集成/系统/验收/回归）→ ⑥ 缺陷管理（收集/管理/沟通缺陷）

过程管理五阶段：启动 → 计划（范围/策略/风险/日程）→ 设计（方案/用例/工具/脚本+评审）→ 执行（环境/数据/缺陷跟踪）→ 结果审查与分析

🗃️四大管理域

配置管理

测试配置管理是软件配置管理的子集；对象 = 测试计划/方案（用例）/测试版本/工具环境/测试结果；目标 = 控制审计变更 · 里程碑建基线 · 记录跟踪变更请求

缺陷管理

按严重程度 = 严重 · 一般 · 次要 · 建议；按优先级 = 立即解决/高/正常排队/低；评估维度 = 影响范围 + 严重级别；修复完及时同步状态

风险管理

识别 → 评估 → 应对 → 上报（超能力时上报）；应对 = 规避（裁剪特性）/ 转移（外包第三方）/ 减轻（回退合入）/ 接受（低优先级）——与 CH08 四应对同源

14.6 软件部署 · 四步 + 四种发布方式 ⭐

🚀部署定义 · 目标 · 步骤

部署 = 将软件项目（含配置文件、用户手册、帮助文档）进行收集、打包、安装、配置、发布的过程

  • 四目标：保障正常运行 · 简化操作提高效率 · 满足个性化需求 · 支持运行可直接使用
  • 四步骤：环境准备（依赖项/运行环境/网络）→ 软件安装（组件复制+权限配置）→ 数据库和文件配置 → 测试和验证

🕊️四种发布方式（冲刺补充·高频）

灰度发布

先放一部分流量给新版本

金丝雀 Canary

先放少量用户/流量验证（比灰度更小步）

蓝绿部署

两套环境（蓝旧绿新），整体切换流量——回滚快

滚动更新

逐批替换实例，节约资源

⚡ 辨析：蓝绿 = 两套环境一键切换；滚动 = 逐批替换同一套环境；金丝雀 = 小流量先探路。

全章易错辨析 TOP 10

1测试目的 = 发现错误，不是证明无错；"证明无错"是错误理解

2好测试用例 = 能发现尚未发现的错误的用例

3白盒覆盖强度：语句<判定<条件<判定条件<条件组合<路径

4边界值五点：min / min+1 / 正常 / max−1 / max

5桩 vs 驱动：桩在下模拟被调用者；驱动在上模拟调用者

6α vs β：α 内测（开发环境）；β 公测（用户环境，开发者不在场）

7负载 vs 压力：到瓶颈后继续跑 vs 不断加压到瓶颈

8静态测试不运行程序（代码检查 + 静态分析）；对象含文档

9蓝绿 vs 滚动：两套环境切换 vs 逐批替换

10缺陷严重度 ≠ 优先级（严重程度 vs 修复紧急度）

💡 补充三陷阱：自动化不适用探索性/一次性/频繁变更 · 冒烟测试 = 预测试（编译人员执行） · 回归四策略全量最安全但成本最高。

全章速记卡 · 考前 5 分钟

🔑清单卡（必背）

  • 测试目的 = 发现错误，不能证明无错；好用例 = 发现尚未发现的错误
  • 八原则：尽早持续 / 含预期输出 / 不测自己程序 / 组织不测自己 / 无效输入也测 / 避免重设计用例 / 不假定无错 / 不穷举（+追溯需求）
  • 冲刺版：缺陷集群（二八）· 杀虫剂悖论
  • 三分类：黑盒/白盒/灰盒（看内部）｜静态/动态（跑不跑）｜手工/自动
  • 黑盒六法：等价类 / 边界值 / 错误推测 / 因果图 / 判定表 / 正交试验
  • 边界值五点：min·min+1·正常·max−1·max
  • 白盒六级：语句<判定<条件<判定条件<条件组合<路径
  • 静态 = 代码检查+静态结构分析+质量度量（发现 30%~70% 缺陷）
  • 自动化：✅回归/性能/重复；❌探索/一次性/频繁变更

🔢数字卡

  • 结构化三结构：顺序/选择/循环（单入口单出口）
  • 可视化 5 概念：表单/部件/属性/事件/方法
  • 代码重用 3 层次：代码/设计结果/分析结果
  • 测试对象 = 程序 + 文档 + 配置数据
  • 性能 5 类：负载/压力/并发/容量/可靠性；指标 5：TPS/响应时间/并发数/资源利用率/错误率

2"回归测试"的主要目的是：
A验证修改后的软件未引入新缺陷，且原有功能仍正常
B测试新功能

3关于 α 测试与 β 测试，下列说法正确的是：
Aα 测试在开发场地由用户在开发方指导下进行；β 测试在用户实际使用环境中由最终用户进行
Bα 测试在用户场地，β 测试在开发场地
C两者都由开发人员完成
Dα 测试就是单元测试
α 测试：在开发方的场地，由用户在开发人员的指导下进行（可控环境，问题能及时反馈修复）。β 测试：软件交付候选版本后，在一个或多个用户的实际使用环境中由最终用户自行测试（不可控、真实场景），开发方通常不在场；β 测试收集到的反馈用于正式发布前的最后修正。⚠️ 二者都属于验收测试范畴。

4软件部署的四种发布方式中，"蓝绿部署"的特点是：
A同时运行新旧两套环境，切换时把流量整体从旧（蓝）切到新（绿），可瞬间回滚
B逐步把流量从旧版本切到新版本
C先发布给一小部分用户试用
D直接停机替换
四种发布方式：① 蓝绿部署——准备两套完全相同的环境（蓝=当前线上、绿=新版本），发布时把流量整体切换到绿；回滚只需把流量切回蓝，秒级完成；代价是资源开销翻倍。② 金丝雀/灰度发布——先放一小部分流量到新版本，观察无异常再逐步放大，风险最小、最常用。③ 滚动发布——逐批替换实例，无停机但回滚较慢。④ 影子/暗部署——新版本接收真实流量副本但不返回给用户，只用于验证（不影响用户体验）。

5软件部署的四个步骤，正确顺序是：
A部署计划 → 环境准备 → 部署实施 → 部署验证（及回滚预案）
B部署实施 → 部署计划 → 环境准备 → 部署验证
C环境准备 → 部署实施 → 部署计划 → 部署验证
D部署验证 → 部署计划 → 环境准备 → 部署实施
软件部署四步：① 制定部署计划（确定版本、时间窗、责任人、回滚预案、影响范围）→ ② 环境准备（服务器/中间件/配置/数据迁移脚本就绪，确认依赖）→ ③ 部署实施（按计划安装/配置/数据迁移/灰度切流）→ ④ 部署验证（功能验证、性能验证、监控对账，异常则按预案回滚）。⚠️ 回滚预案必须在第①步就写好，不能等到出问题才想。

6按测试对象划分，"压力测试"与"负载测试"的主要区别是：
A负载测试是逐步增加负载看系统在各类负载下的表现；压力测试是在极限/超负荷下看系统的极限与恢复能力
B两者完全相同
C压力测试只测网络设备
D负载测试只测数据库
负载测试：逐步增加并发用户/数据量，观察系统在不同负载下的响应时间、吞吐、资源占用，找到性能拐点。压力测试：在极限甚至超负荷（超出预期最大负载）条件下运行，考察系统的极限承受能力、稳定性与故障后的恢复能力（会不会崩、崩了能不能自愈）。此外还有容量测试（系统能支持的最大用户数/数据量）与可靠性/稳定性测试（长时间运行的稳定性）。

- 🟢 加分：点出项目与本题主题的直接关联（如本项目正是因 XX 痛点才需要 XX 方法）

- 🔴 核心：详细描述传统测试与自动化测试相融合的三个趋势的具体内容——须展开「是什么 + 本项目为何适用」，不能只列名词

- 🔴 核心：给出可量化的落地效果（缺陷率/响应时间/迭代周期/资源成本等具体数据），而非「取得了良好效果」
- 🔴 核心：诚实分析存在的 2~3 个真实问题，并给出对应的改进措施——教材强调这才是用心的内容
- 🟡 支撑：结合具体实例说明措施的实施过程（怎么做的，而非教科书式罗列）
- 🟢 加分：总结经验教训与后续演进方向，体现复盘能力
